# 定时任务方案设计评审：不足、漏洞与模糊点

> 纯设计层面评审，不涉及技术实现细节。关注方案逻辑是否自洽、边界是否清晰、用户体验是否闭环。

---

## 一、核心逻辑漏洞（高风险）

### 1. 脚本生成后「数据源变化」导致任务静默失败

**问题描述：**
- LLM 生成脚本时，根据「当时的」数据源 Schema 写了死字段名、死接口路径
- 下次定时执行时，数据源接口可能已变更（字段改名、路径调整、返回结构变化）
- 脚本本身不会自适应，用户也没有修改任务，但任务持续失败

**设计矛盾：**
> 脚本是一次性生成的静态产物，但依赖的外部环境是动态变化的。

**风险：**
- 用户发现「最近几天都没收到报表」，查看才发现执行连续失败
- 运维排查时需要人工对比脚本中的字段名和数据源最新 Schema

**建议方向：**
- 数据源 Schema 变更时，是否需要主动通知相关任务？
- 或者脚本执行失败时，自动尝试用 LLM「修复」字段映射（Auto-fix）？
- 或者要求脚本内做「字段存在性检查」，缺失时走降级逻辑？

---

### 2. 语义变化检测把关键决策交给 LLM 黑盒

**问题描述：**
- 用户修改 description 后，系统用 LLM 判断 change_score（0-100）来决定是 Ignore / Patch / Regenerate
- 这个判断本身不稳定，且用户无感知

**设计矛盾：**
> 系统用另一个不可解释的黑盒（LLM）来决定主黑盒（脚本）是否需要重建。

**风险场景：**
- 用户把「昨日」改成「前日」→ LLM 可能判为轻微变化（Ignore），但脚本里硬编码了 `timedelta(days=1)`，实际需要改
- 用户把「异常客户」改成「高风险客户」→ 词义相近，LLM 可能判为轻微变化，但业务定义完全不同
- Patch 后的脚本语法正确但逻辑错误，验证执行可能发现不了（比如数据能跑但结果不对）

**建议方向：**
- change_score 是否只作为「建议」而非「决策」？最终是否重新生成应由用户显式确认
- Patch 模式是否有必要？是否直接简化为两种状态：「无需更新」或「全量重生成」？

---

### 3. 验证执行通过 ≠ 正式执行可靠

**问题描述：**
- 重新生成脚本后，系统做一次「验证执行」来确认脚本可用
- 但验证执行用的是「当前时刻」的数据和环境
- 定时任务的核心价值是「在未来的某个时间点执行」，那时的数据环境可能完全不同

**设计矛盾：**
> 用一次「即时测试」来验证一个「未来定时执行」的可靠性，逻辑上不构成充分条件。

**风险：**
- 验证时「昨日对账接口」正常返回，但真实执行时（每天早上 9 点）接口可能还没准备好数据
- 验证通过给用户「虚假安全感」，正式上线后仍可能失败

**建议方向：**
- 验证执行的价值应重新定位：它验证的是「脚本语法正确 + 能调通接口」，而非「业务逻辑永远正确」
- 是否需要「灰度执行」机制？比如新脚本先跑一次真实定时，但产物只推送给用户本人（不推群）

---

### 4. 产物类型由 LLM 隐式决定，用户无法预期

**问题描述：**
- 用户说「给我一份客户分析」→ LLM 可能生成 Excel，也可能生成 markdown 表格
- 用户说「做个汇报材料」→ LLM 可能生成 PPT，也可能生成 Word
- 产物格式完全取决于 LLM 对 description 的理解

**设计矛盾：**
> 用户交付物的形态是需求的一部分，但当前设计里没有让用户表达「我要什么格式」的入口。

**风险：**
- 用户期望收到 Excel，结果收到 markdown，需要反复修改 description 来「引导」LLM
- 钉钉群推送时，markdown 和文件的呈现方式差异很大，用户体验不一致

**建议方向：**
- 创建表单时是否应增加「产物类型」选项？（至少让用户选：文本报告 / 表格 / PPT / 不指定让 AI 决定）
- 或者执行后让用户可以「一键转换格式」？

---

## 二、边界模糊（中风险）

### 5. 「模型问问题」与「sai-cli 取数」的分支边界不清晰

**问题描述：**
- 用户的 description 到底走「纯模型分支」还是「取数分支」，完全由 LLM 在生成脚本时自行判断
- 两个分支的产物形态差异巨大：一个是分析结论，一个是原始数据

**模糊场景：**
| 用户描述 | 期望分支 | LLM 可能走的分支 |
|---------|---------|-----------------|
| "分析一下昨天的情况" | 取数+分析 | 纯模型（没有取数） |
| "查一下昨天的数据" | 取数+展示 | 取数 |
| "看看有没有问题" | 取数+分析 | 不确定 |

**风险：**
- 用户以为任务会「拉取数据并分析」，结果脚本只是问了一下模型，得到的是通用回答而非基于真实数据的分析

**建议方向：**
- 是否需要显式区分「基于数据的分析」和「通用知识问答」？
- 或者脚本生成后，前端展示脚本摘要（「本任务将调用 HQ 对账接口」），让用户确认是否符合预期？

---

### 6. 单任务脚本内隐含「多步骤」，但无步骤级可见性

**问题描述：**
- 当前设计把「取数 → 计算 → 生成文件 → 推送」全部打包在一个 Python 脚本里
- 脚本内部是一个黑盒，用户看不到执行链路

**与用户诉求的矛盾：**
> 你之前提到工作流要让用户「看到执行的链路」，但单任务的设计其实是把链路藏在一个脚本里。

**风险：**
- 脚本执行失败时，用户无法知道是「取数失败」还是「计算逻辑报错」还是「生成文件报错」
- 调试全靠看 stderr 日志，对用户不友好

**建议方向：**
- 即使 v1 是单脚本，是否应在执行记录中拆解「步骤里程碑」？（如：取数完成 2s / 计算完成 5s / 文件生成完成 8s）
- 或者这本身就是工作流要解决的问题，单任务不追求链路可见性？

---

### 7. 推送失败与执行成功的状态割裂

**问题描述：**
- 脚本执行成功（status='success'），但钉钉推送失败（notify_dingtalk_ok=false）
- 用户看到的是「执行成功」，但实际没收到通知

**设计矛盾：**
> 从系统角度，「执行」和「推送」是两个独立操作；但从用户角度，「没收到推送 = 任务没完成」。

**风险：**
- 用户好几天没收到钉钉消息，以为任务没执行，查看才发现每次都是「执行成功、推送失败」
- 推送失败的重试是后台自动的，用户完全无感知，也没有主动重试入口

**建议方向：**
- 是否需要「端到端成功」状态？（执行成功且推送成功 = 任务完成）
- 推送失败时，是否应在 Claw 前端显示警告徽章？

---

### 8. 本地历史任务迁移的语义断层

**问题描述：**
- 本地 Gateway cron 的任务内容是 `message`（发给 Agent 的 prompt）
- 云端新任务的内容是 `description`（生成脚本的依据）
- 迁移时把 `message` 映射为 `description`，但两者的语义和使用方式完全不同

**风险：**
- 原任务 message 是「请帮我查一下昨日对账」→ 这是给 Agent 的指令
- 迁移后 description 也是「请帮我查一下昨日对账」→ 这是给 LLM 生成脚本的依据
- 生成的脚本行为和原 Gateway Agent 的执行结果可能完全不同

**建议方向：**
- 迁移是否应明确告知用户「迁移后的任务行为可能与原任务不同」？
- 或者本地任务不迁移，只提供「参考创建」？（预填表单，用户确认后新建）

---

## 三、缺失的设计（方案未覆盖）

### 9. 任务执行失败后的用户感知与干预

**当前设计：**
- 执行失败 → 记录 task_run → 更新 last_run_status='failed'
- 用户需要主动打开 Claw 查看才知道失败了

**缺失：**
- 连续失败 N 次后，是否应主动通知用户？（如钉钉 @ 用户）
- 失败的任务是否应自动暂停？（避免持续失败浪费资源）
- 用户是否有「一键重试失败任务」的入口？

---

### 10. 多环境（测试/预发/生产）的行为一致性

**缺失：**
- 用户在测试环境创建的定时任务，用的是测试数据源，生成的是针对测试环境的脚本
- 用户想在生产环境用同样的任务，是否需要重新创建？
- 脚本中的 `sai-cli` 调用，测试环境和生产环境的命令路径/参数是否完全一致？

**风险：**
- 测试环境验证通过的任务，到生产环境可能直接失败
- 没有「任务跨环境复制/升级」的设计

---

### 11. 产物生命周期与合规

**缺失：**
- 产物（Excel/Word 含业务数据）保存 30 天后删除
- 但业务上某些数据可能需要保存更长时间（如财务审计要求 1 年）
- 用户删除任务后，历史产物是否级联删除？
- 含敏感数据的产物，是否有访问权限控制？（当前只有签名 URL 有效期限制）

---

### 12. 并发场景下的竞态条件

**缺失：**
- XXL-JOB 正在执行某任务的 v2 脚本（执行时间较长）
- 此时用户触发重新生成，v3 验证通过并上线
- v2 的执行结果应以哪个版本记录？
- 如果 v2 执行失败，是否会影响 v3 的调度？

---

## 四、与「工作流」的潜在冲突

### 13. 单任务能力过强，可能模糊工作流的边界

**当前单任务已经能做的事：**
- 取数（sai-cli）
- 计算（Python）
- 模型分析（调用 LLM）
- 生成文件（Excel/PPT/Word）
- 推送（钉钉/对话）

**问题：**
- 如果单任务已经能串起「取数→计算→生成→推送」的完整链路，工作流的差异化价值是什么？
- 用户是否会认为「单任务已经够用了，不需要工作流」？

**建议提前明确边界：**
| 能力 | 单任务（MONITOR_TASK） | 工作流（WORKFLOW） |
|------|----------------------|-------------------|
| 步骤数 | 单脚本内串行 | 显式多节点 DAG |
| 分支判断 | 脚本内 if/else（黑盒） | 可视化条件分支 |
| 人工介入 | 不支持 | 支持审批/确认节点 |
| 步骤复用 | 不支持 | 节点可复用 |
| 链路可见 | 无（或日志） | 可视化 DAG |
| 失败处理 | 整体失败 | 单节点失败可跳过/重试 |

如果单任务把「多步骤」都做了，工作流的价值会被稀释。

## 五、建议的决策清单

以下问题需要在编码前确认，否则会导致返工：

| # | 问题 | 当前状态 | 建议 |
|---|------|---------|------|
| 1 | 数据源 Schema 变化后，脚本如何自适应？ | 未设计 | 明确是「人工修复」还是「Auto-fix」 |
| 2 | 用户修改 description 后，是否必须用户确认才重新生成？ | LLM 自动决策 | 建议改为「系统建议 + 用户确认」 |
| 3 | 验证执行的价值定位是什么？ | 验证脚本可用 | 明确为「语法+接口连通性验证」，不保证业务正确 |
| 4 | 产物类型是否让用户显式选择？ | LLM 隐式决定 | 建议增加「产物格式」选项 |
| 5 | 执行失败时如何通知用户？ | 仅记录，被动查看 | 建议连续失败 3 次后主动通知 |
| 6 | 单任务 vs 工作流的边界在哪里？ | 模糊 | 提前明确分工，避免单任务能力膨胀 |
| 7 | 跨环境（测试/生产）任务如何迁移？ | 未设计 | 明确是否需要「任务导出/导入」能力 |
| 8 | 历史产物合规保留策略？ | 统一 30 天 | 是否按任务类型差异化保留？ |

## 六、总体判断

**方案的核心价值很明确：** 自然语言驱动定时任务，降低使用门槛。整体架构逻辑自洽。

**但以下三点如果不在设计阶段解决，上线后会变成高频客诉：**

1. **产物类型不可控** → 用户反复修改 description 来「猜」LLM 会生成什么格式
2. **执行失败无感知** → 用户不知道任务已经失败好几天了
3. **脚本与数据源的耦合** → 数据源一变更，大量任务静默失败

**建议优先级：**
- P0：明确产物类型的用户表达机制（选项或确认环节）
- P0：明确执行失败的主动通知机制
- P1：明确数据源变化后的应对策略
- P1：明确单任务与工作流的边界
- P2：其余问题可上线后迭代

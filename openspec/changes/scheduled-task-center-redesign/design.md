## Context

StoClaw 当前 Cron 页面（`src/pages/Cron/index.tsx`）以技术导向呈现：创建表单使用 cron 表达式预设按钮，非技术用户门槛高。后端分为两套体系——Gateway 本地 cron（RPC）和 Cloud Task API（`/agent/v1/cloud-cron`），架构分散。

设计团队提供了新版任务中心方案（见 `stoclaw-design/scheduled-tasks.html`），采用业务语义卡片布局、自然语言描述导向的创建流程、推荐任务快速 onboarding 机制。同时后端建设了独立的 **STO Scheduled Tasks API**（`baseinfo-aimemory*.sto.cn`），提供完整的云端脚本生成 → 存储 → 执行 → 产物交付链路。

本设计覆盖定时任务中心的前端 UI 改版、后端 API 对接、云端脚本执行体系及历史任务迁移方案。

> **注**：工作流（WORKFLOW）相关设计暂不包含，待后续单独变更确定。当前变更仅聚焦定时任务中心（MONITOR_TASK）。详细技术设计见同目录下 `design-technical.md`。

---

## Goals / Non-Goals

**Goals:**
- 基于 STO Scheduled Tasks API 重建定时任务中心页面，替换现有 `/cron` 路由实现
- 采用设计团队新版 UI：Hero 区域 + 卡片网格 + 频率联动选择器 + 推荐任务 onboarding
- 建立前端友好的频率选择（一次性/每天/工作日/每周/每月）到标准 5 段 cron 表达式的转换层
- 妥善处理用户历史本地 Gateway cron 任务的半自动迁移引导
- 对接云端脚本生成、执行、产物交付全链路的状态展示

**Non-Goals:**
- 工作流（WORKFLOW）类型的任务创建与编辑（后端接口调整中，待后续变更）
- 脚本生成 LLM Prompt 的业务细节调优（由后端/业务方负责）
- Sandbox 执行引擎的底层实现（属于后端基础设施）
- 完全自动化的本地任务迁移（采用半自动引导策略，不强制同步）

## Decisions

### 1. 新页面独立建设，逐步替换 `/cron`

**决策**：新建 `src/pages/ScheduledTasks/` 页面组件，不直接覆盖现有 `src/pages/Cron/index.tsx`。

**理由**：
- 允许灰度过渡，新旧页面可并行存在 2-3 个版本
- 现有 Cron 页面的 Gateway RPC + Cloud Task API 逻辑需要逐步废弃，直接重写比渐进改造更可控
- 独立的目录结构便于后续彻底删除旧代码

**替代方案考虑**：在现有 Cron 页面内通过条件渲染切换新旧 UI。否决原因：旧页面的状态管理、API 调用逻辑与新体系差异大，条件渲染会导致代码高度耦合，维护成本更高。

### 2. 前端本地完成搜索排序，后端仅提供全量列表

**决策**：`GET /list` 无搜索/排序参数，前端拉取全量后本地处理过滤与排序。

**理由**：
- 定时任务数量级预期为单用户 < 100 条，前端本地处理性能完全足够
- 减少后端接口复杂度，避免分页、搜索参数设计分歧
- 与技能广场（Skills）页面现有的前端搜索过滤模式保持一致

**替代方案考虑**：后端支持分页 + 服务端搜索排序。否决原因：过早优化，当前业务规模不需要；且设计稿中的排序仅支持按创建时间/名称等简单维度，前端实现成本远低于协调后端扩展接口。

### 3. 频率选择器前端转 cron，不直接暴露 cron 表达式给用户

**决策**：用户在友好的频率选择器（一次性/每天/工作日/每周/每月）中配置，前端转换为标准 5 段 cron 表达式提交给后端。

**理由**：
- 设计稿明确要求消除 cron 表达式对用户的认知负担
- 转换逻辑简单且确定（如每天 09:00 → `0 9 * * *`），前端完全可承担
- 一次性任务若后端 v1 不支持 `at` 类型，可采用创建后立即自动禁用的兼容方案

**替代方案考虑**：后端直接支持结构化频率参数。否决原因：后端 v1 接口已确定以 `cron_expr` 为核心字段，增加结构化参数会延迟联调时间；前端转换层可在后续后端支持结构化参数时无缝移除。

### 4. 历史本地任务采用"检测 + 半自动迁移"策略

**决策**：不自动同步本地 Gateway cron 任务到云端，首次进入页面时检测并提示迁移；迁移过程预填已有信息，但要求用户补全云端必填字段（网点、通知方式等）。

**理由**：
- 本地任务的 `target`（channelType/channelId）与云端 `notify_mode` 无直接映射，自动同步会创建大量配置不完整的任务
- 云端创建需要 `site_code`、`dingding_id` 等 SSO 信息，本地任务缺失
- 半自动迁移让用户有机会重新确认任务配置，减少误迁移

**替代方案考虑**：自动全量同步 + 后续编辑补全。否决原因：可能创建大量无效云端任务，且用户无感知迁移违背最小惊讶原则；后端也可能因批量创建触发限流。

### 5. 状态管理：扩展 Zustand 而非新建独立 Store

**决策**：在 `src/stores/cron.ts` 中扩展新字段和 action，支持 `scheduled-tasks` API 的 CRUD，而非新建独立的 `scheduledTasks.ts`。

**理由**：
- 新旧体系在业务概念上都是"定时任务"，共享 Store 避免状态碎片化
- 过渡期需要同时展示云端任务和本地历史任务，统一 Store 便于交叉逻辑（如迁移检测）
- 废弃旧代码时，可以逐步替换 Store 中的旧字段，而不需要合并两个 Store

**替代方案考虑**：新建 `src/stores/scheduledTasks.ts`。否决原因：新旧任务数据在 UI 上需要同时展示（过渡期），两个 Store 会增加同步复杂度；且最终目标仍是统一为"定时任务"单一概念。

### 6. 主题与 Token 遵循 `docs/sto-design.md`

**决策**：所有可见 UI 的颜色、状态色、按钮层级统一使用 STO Design Token，不引入设计稿中的临时 hex。

**映射原则**：
- 主按钮/新建按钮：`--color-brand` → Brand-6 `#FF6F00`
- 启用状态/Success：`--color-success` → Green-6 `#00B54B`
- 危险操作/删除：`--color-danger` → Red-6 `#FA3C3C`
- 警告/待处理状态：`--color-warning` → Yellow-6 `#FAAD14`
- 卡片背景/边框：`--color-fill-light` / `--color-border` → Grey-1~Grey-4 阶梯
- 正文/标题文本：`--color-text` / `--color-text-bold` → Grey-9 / Grey-10

## Risks / Trade-offs

- **[Risk]** 后端 v1 `scheduled-tasks` API 仅支持 `cron_expr`，一次性任务表达困难  
  → **Mitigation**：前端采用"创建后立即自动禁用"的兼容方案；与后端确认 v2 是否支持 `kind: "at"`，若支持则前端无缝切换

- **[Risk]** 本地历史任务迁移流程复杂，用户可能忽略迁移提示  
  → **Mitigation**：迁移横幅在检测到可迁移任务时固定在页面顶部，且不过期自动隐藏；提供"稍后处理"和"不再提醒"选项；过渡期（2-3 版本）内保留本地任务读取逻辑

- **[Risk]** 脚本生成异步链路长（LLM 调用 + 安全扫描 + OSS 上传），用户感知延迟  
  → **Mitigation**：创建/编辑弹窗关闭后立即显示"脚本生成中"轻提示；提供脚本状态指示器（pending/ready/stale/error）；支持用户保存任务后离开页面，不阻塞操作

- **[Risk]** 后端接口字段（如 `task_type: WORKFLOW`）调整时间节点不确定  
  → **Mitigation**：v1 前端表单中"关联工作流"字段仅展示 UI（disabled 或 placeholder），实际提交固定为 `MONITOR_TASK`；待后端接口就绪后通过独立变更解锁

- **[Risk]** 全量拉取任务列表在极端场景下（用户任务数 > 500）可能产生性能问题  
  → **Mitigation**：当前业务场景下预期单用户任务数 < 100；若后续出现性能反馈，再协调后端增加分页参数（接口兼容性好，前端改动小）

- **[Trade-off]** 前端本地搜索排序 vs 服务端搜索排序：选择了前者以降低后端复杂度，代价是极端数据量下性能下降

## Migration Plan

1. **Phase 1（当前变更）**：新建 `ScheduledTasks` 页面，对接 `scheduled-tasks` API，与旧 Cron 页面并存
2. **Phase 2**：内部测试 + 设计走查，完善交互细节
3. **Phase 3**：默认路由切换到新页面，旧 Cron 页面保留但隐藏入口（通过 feature flag）
4. **Phase 4（2-3 版本后）**：移除旧 Cron 页面代码、Gateway RPC 调用逻辑、本地历史任务读取逻辑

**Rollback**：若新页面出现严重问题，通过 feature flag 切回旧 Cron 页面，云端任务数据不受影响（已持久化在云端）。

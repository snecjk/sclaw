# 产品功能层面评审：缺失、矛盾与体验断点

> 完全从产品经理和用户视角出发，不谈技术实现。只关心：功能是否完整、体验是否闭环、用户场景是否被覆盖。

---

## 一、创建环节：用户完全在黑盒里

### 问题：用户创建任务后，不知道系统将要做什么

**当前流程：**
用户填名称 + 写描述 → 保存 → 系统说"脚本生成中" → 脚本生成完成 → 结束

**用户此时的困惑：**
- "系统生成的脚本到底要做什么？"
- "它会调用哪些数据源？"
- "最终给我的是什么格式的产物？"
- "如果生成的不是我想要的，我怎么改？"

**缺失的功能：**

| 缺失功能 | 用户场景 | 优先级 |
|---------|---------|--------|
| **生成预览/确认** | 用户保存前，系统展示「系统将执行以下操作：1. 调用 HQ 对账接口 2. 比对异常数据 3. 生成 Excel 报表」，用户确认后才保存 | P0 |
| **产物格式选择** | 用户明确说"我要 Excel"或"我要文字报告"，而不是让系统猜 | P0 |
| **描述辅助/模板提示** | 用户不知道怎么写描述，系统提供示例："每天 9 点查询昨日 XX 数据，标记异常项，推送到钉钉群" | P1 |
| **生成失败时的引导** | 脚本生成失败，系统不应只提示"失败"，而应告诉用户"描述中缺少网点信息，请补充后重试" | P1 |

**核心矛盾：**
> 系统用自然语言降低了输入门槛，但因为没有确认环节，反而提高了「预期不符」的风险。用户输入的是模糊的，系统产出的是确定的，中间没有对齐过程。

## 二、产物交付：用户无法预期收到什么

### 问题：产物形态完全不可控

**用户场景 A：**
- 用户说"给我一份客户分析"
- 第一天收到的是 Excel 表格
- 用户觉得挺好
- 后来用户修改了描述里的一个词
- 重新生成后变成 markdown 文字报告
- 用户困惑：为什么变了？

**用户场景 B：**
- 用户说"做个汇报材料"
- 系统生成了 PPT
- 但用户想要的是 Word（因为要在里面写批注）
- 用户只能反复改 description 来「引导」系统生成 Word

**缺失的功能：**

| 缺失功能 | 用户场景 | 优先级 |
|---------|---------|--------|
| **产物格式显式选择** | 创建时让用户选：文字报告 / 数据表格 / PPT / Word / 不指定 | P0 |
| **产物模板选择** | 选 Excel 后，让用户选模板：简洁版 / 带图表版 / 财务版 | P2 |
| **产物预览** | 第一次执行后，用户在 Claw 端预览产物内容，确认是否符合预期 | P1 |
| **产物历史对比** | 用户修改任务后，能对比「修改前 vs 修改后」的产物差异 | P2 |

**核心矛盾：**
> 自然语言是模糊的，产物形态是具体的。用模糊输入决定具体输出，没有给用户「校正权」。

## 三、执行失败：用户是最后知道的人

### 问题：任务失败了，用户可能好几天才发现

**用户场景：**
- 用户创建了一个「每天推送日报」的任务
- 第三天同事问"这两天怎么没收到日报？"
- 用户打开 Claw 才发现，原来从昨天开始任务就执行失败了
- 用户看了错误信息，但看不懂（是脚本错了？还是数据源挂了？还是钉钉群变了？）

**当前方案的问题：**
- 失败只记录在「执行历史」里
- 用户不主动打开查看，就完全不知道
- 即使查看了，错误信息对非技术用户也不友好

**缺失的功能：**

| 缺失功能 | 用户场景 | 优先级 |
|---------|---------|--------|
| **失败主动通知** | 任务连续失败 2 次后，钉钉 @ 创建者或推送到 Claw 对话提醒 | P0 |
| **失败原因解读** | 不是展示原始错误，而是翻译成：「数据源接口暂时不可用」或「脚本中的查询条件有误」 | P1 |
| **一键重试** | 用户看到失败后，能直接点「重试」，而不是去编辑任务再保存 | P1 |
| **自动暂停** | 连续失败 5 次后自动暂停任务，避免持续报错浪费资源 | P2 |

**核心矛盾：**
> 定时任务是「设置后就忘记」的，但失败时需要「及时被提醒」。当前设计只有「忘记」，没有「提醒」。

## 四、任务管理：功能过于单薄

### 问题：只有增删改查启停，缺少任务运营能力

**用户场景 A：**
- 用户创建了一个很复杂的任务，想给同组的同事也创建一个同样的
- 当前只能重新填写一遍表单
- 用户期望：复制这个任务，改个名称就能用

**用户场景 B：**
- 用户想查看过去一周的日报产物
- 当前只能点进每次执行记录看
- 用户期望：有个「产物中心」，按任务维度查看历史产物

**用户场景 C：**
- 用户离职了，他创建的定时任务没人管
- 当前任务只属于创建者
- 用户期望：任务可以转交、可以设置共同维护人

**缺失的功能：**

| 缺失功能 | 用户场景 | 优先级 |
|---------|---------|--------|
| **复制任务** | 快速创建相似任务 | P1 |
| **产物中心** | 按任务查看历史产物，支持下载、对比、批量删除 | P1 |
| **任务移交/共享** | 离职转交、团队共享、设置接收人 | P2 |
| **任务标签/分组** | 用户有几十个任务，需要按业务域分组管理 | P2 |
| **执行日历** | 日历视图看每天有哪些任务要执行、已执行、失败了 | P2 |

## 五、调试体验：没有「试错」空间

### 问题：用户创建任务后，要么等定时触发，要么点「测试运行」

**用户场景：**
- 用户写了一个描述，保存后生成了脚本
- 用户不确定这个脚本跑出来的结果是不是自己想要的
- 点「测试运行」后，如果真的推送到了钉钉群，可能把半成品发给了全群
- 用户期望：先「预览」结果，确认无误后再正式运行

**缺失的功能：**

| 缺失功能 | 用户场景 | 优先级 |
|---------|---------|--------|
| **预览模式** | 测试运行时，产物只展示给创建者本人，不推送到钉钉群 | P0 |
| **分步查看** | 测试执行后，展示「取了哪些数据」「计算结果是什么」「最终产物预览」 | P1 |
| **模拟数据测试** | 用户可以用 mock 数据测试脚本逻辑，不依赖真实接口 | P2 |

**核心矛盾：**
> 「测试运行」_currently_ 和「正式运行」没有区别，都是全链路执行。用户没有「沙盒预览」空间。

## 六、用户分层：新手和老手没有差异化体验

### 问题：所有用户都用同一套流程

**新手用户场景：**
- 完全不知道定时任务能做什么
- 不知道怎么写 description
- 不知道 sai-cli 能查哪些数据
- 期望：系统推荐几个常用任务，一键添加

**老手用户场景：**
- 已经熟悉系统，知道要什么数据、要什么格式
- 不想每次都等 LLM 生成脚本
- 期望：直接编辑脚本、保存为个人模板、快速复用

**当前方案的缺失：**
- 没有「新手引导」和「推荐任务」的运营机制
- 没有「高级模式」让老手跳过 LLM 生成环节
- 没有「我的模板库」沉淀个人常用任务

**缺失的功能：**

| 缺失功能 | 用户场景 | 优先级 |
|---------|---------|--------|
| **推荐任务** | 新手首页看到「每日对账」「异常监控」「成本分析」等推荐卡片，一键创建 | P1 |
| **高级模式** | 老手可以直接编辑/上传脚本，不走 LLM 生成 | P2 |
| **个人模板库** | 用户把常用任务保存为模板，下次从模板创建 | P2 |
| **团队模板市场** | 团队内共享模板，好的任务可以推广给同事 | P3 |

## 七、与钉钉/群的衔接体验断点

### 问题：任务和钉钉群的绑定关系不清晰

**用户场景 A：**
- 用户创建任务时选了推送到「华东大区群」
- 后来用户被调到了华南大区
- 用户想批量把推送到「华东大区群」的任务改成「华南大区群」
- 当前只能逐个任务编辑

**用户场景 B：**
- 钉钉群解散了
- 任务继续往这个群推送，一直失败
- 系统没有提醒用户「群已不存在」

**缺失的功能：**

| 缺失功能 | 用户场景 | 优先级 |
|---------|---------|--------|
| **推送目标统一管理** | 查看所有推送到某群的任务，批量修改推送目标 | P2 |
| **群状态检测** | 定时检测钉钉群是否有效，群解散后主动提醒用户更换 | P2 |
| **@指定人** | 不仅推送到群，还可以 @ 具体负责人 | P3 |

## 八、本地任务与云端任务的体验断层

### 问题：用户可能在两个地方看到定时任务，体验不一致

**用户场景：**
- 用户之前用 Gateway 创建了几个本地定时任务
- 现在用了新的云端定时任务页面
- 用户不知道之前的本地任务还在不在、怎么管
- 有些任务在旧页面，有些在新页面，混乱

**缺失的功能：**

| 缺失功能 | 用户场景 | 优先级 |
|---------|---------|--------|
| **统一入口** | 所有定时任务（本地+云端）在一个页面管理，本地任务标记为「本地」 | P0 |
| **迁移引导** | 检测到本地任务时，清晰告知用户「这些任务在本地运行，可迁移到云端统一管理」 | P0 |
| **迁移预览** | 迁移前展示「迁移后的任务将变成这样」，让用户确认差异 | P1 |

---

## 九、数据权限与合规：完全没有设计

### 问题：谁可以看到谁的定时任务？产物里的敏感数据怎么管？

**用户场景 A：**
- A 用户创建了「查看全公司成本」的任务
- B 用户（另一个网点）理论上不应该看到 A 的任务
- 但 B 如果知道任务 ID，能否看到执行结果？

**用户场景 B：**
- 任务产物里有客户名单和金额
- 产物在 OSS 上保存 30 天
- 这 30 天内，有权限的人都可以下载
- 但「谁有权限」没有明确定义

**缺失的功能（产品层面）：**

| 缺失功能 | 用户场景 | 优先级 |
|---------|---------|--------|
| **任务可见范围** | 仅自己 / 同部门 / 全公司 | P2 |
| **产物访问权限** | 产物链接是否可转发？转发后能否打开？ | P2 |
| **敏感数据水印** | 产物文件（Excel/PPT）自动添加下载人信息水印 | P3 |

## 十一、总结：产品层面的 3 个核心矛盾

### 矛盾 1：自然语言的「模糊性」 vs 产物交付的「确定性」
- 用户输入是模糊的（自然语言）
- 但用户期望收到的是确定的（格式、内容、范围）
- **当前方案缺少「对齐」环节**：用户没有机会确认「系统理解的对不对」

### 矛盾 2：定时任务的「设置后忘记」 vs 失败时的「及时感知」
- 用户创建任务后就不关注了
- 任务失败时，用户是最后知道的人
- **当前方案缺少「兜底」机制**：没有主动通知、没有自动暂停、没有失败保护

### 矛盾 3：系统生成的「黑盒性」 vs 用户需要的「可控性」
- 系统生成脚本、决定产物格式、决定推送内容
- 用户全程没有「干预点」，只能被动接受结果
- **当前方案缺少「用户校正权」**：没有预览、没有格式选择、没有分步查看

## 建议的 MVP 功能优先级（产品视角）

| 优先级 | 功能 | 理由 |
|--------|------|------|
| **P0** | **产物格式选择** | 解决「用户收不到预期格式」的核心客诉 |
| **P0** | **生成预览/确认** | 解决「黑盒生成」的信任问题 |
| **P0** | **失败主动通知** | 解决「设置后忘记，失败不知道」的兜底问题 |
| **P0** | **统一任务列表（本地+云端）** | 解决用户任务散落在两个系统的混乱问题 |
| **P1** | **预览模式（测试运行不推送）** | 解决「测试不敢点」的顾虑 |
| **P1** | **失败原因解读 + 一键重试** | 降低用户排查成本 |
| **P1** | **产物历史中心** | 用户高频需求：查看/下载历史产物 |
| **P1** | **复制任务** | 提升效率，降低重复创建成本 |
| **P2** | **推荐任务/新手引导** | 降低新用户上手门槛 |
| **P2** | **任务标签/分组** | 任务数量多后的管理需求 |

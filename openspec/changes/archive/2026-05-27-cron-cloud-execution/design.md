## Context

StoClaw 当前的定时任务功能完全基于本地 OpenClaw Gateway 的 `cron.*` RPC 接口。用户在前端创建任务后，配置经 Main-process 转换为 `CronSchedule` 对象并提交给 Gateway，Gateway 负责调度和执行。执行结果通过本地会话历史或 `cron/runs/*.jsonl` 日志文件展示。

这一模式的核心限制是：**Gateway 随 StoClaw 进程生命周期绑定**。用户关机、休眠、退出应用或网络断开时，Gateway 停止运行，所有待触发的定时任务失效。

本次变更引入「云端执行」模式：用户在 StoClaw 本地创建任务，任务配置提交到**外部云端服务**托管，由云端调度器在用户离线时继续触发，执行结果在用户重新在线时同步回客户端。**云端 Task API 和云端 Agent 运行时为外部依赖，不在 StoClaw 代码库范围内。**

## Goals / Non-Goals

**Goals:**
- 架构上保留「本地执行」和「云端执行」双模式能力，但本期 UI 默认使用云端执行，隐藏本地执行选项（为后续开放预留）。
- 云端执行的任务在用户电脑关机/离线期间仍能按调度触发，执行结果不丢失。
- 用户打开电脑后，离线期间产生的云端执行结果自动拉取并合并到任务的运行历史中。
- 用户正在使用 App 时，云端执行完成的结果实时推送到前端（Toast 通知 + 会话视图更新）。
- 云端任务的运行历史、状态、日志在 UI 上的展示体验与本地任务保持一致。

**Non-Goals:**
- 本次设计不替换本地 Gateway 的 cron 功能；本地执行模式继续保留。
- 不涉及将本地文件系统、本地数据库或局域网资源暴露给云端执行环境。
- 不实现云端 Agent 运行时的完整镜像（如技能文件、自定义代码的上传）；云端 Agent 使用已同步到云端的配置子集运行。
- 不实现用户对云端执行环境的自定义（如选择区域、计算规格）。
- 不修改 Gateway 自身的 cron 引擎实现。
- **不实现云端 Task API 和云端 Agent 运行时本身**；这些由外部团队提供，StoClaw 仅作为客户端集成调用。

## Decisions

### 1. 本地 Agent 与云端 Agent 的关系

**决策**：本地 Agent（通过 OpenClaw Gateway 运行）与云端 Agent（由云端服务托管）是**两套完全独立的系统**。云端任务不绑定本地 Agent ID，而是绑定到用户云端 Agent 列表中的某个云端 Agent。用户在创建云端任务时，从云端 Agent 列表中选择目标 Agent。本地任务和云端任务在 UI 上统一展示，但底层分别路由到 Gateway RPC 和云端 Task API。

**理由**：
- 云端 Agent 拥有独立的模型接入、技能配置和运行环境，与本地 Gateway 解耦，避免关机即失效的问题。
- 本地和云端模型可以不同（如本地用 Claude，云端用 GPT-4），满足不同场景的性能/成本需求。
- 不需要在本地和云端之间同步复杂的 Agent 配置，降低架构复杂度。

**替代方案**：将本地 Agent 的配置映射到云端，让云端"模拟"本地 Agent 运行。
- **拒绝理由**：模型可能不同，配置映射无法保证行为一致性；需要持续同步配置变更，复杂度高；用户无法独立管理两套环境的 Agent。

**替代方案**：云端复用本地 Gateway 的 Agent ID，但由云端从平台获取对应配置。
- **拒绝理由**：本地 Agent 和云端 Agent 的模型、技能、参数可能完全不同，复用 ID 会造成混淆；用户无法直观区分两套 Agent 的能力差异。

### 2. 结果同步机制：轮询 + 启动拉取

**决策**：采用 **HTTP 轮询**（客户端在线时定期查询）+ **启动时增量拉取**（客户端离线后恢复）的双通道策略，**不依赖 WebSocket 或 SSE**。

**轮询策略**：
- **前台轮询**：Cron 页面处于活跃状态时，每 30 秒调用一次 `GET /results?since={lastSyncAt}` 查询增量结果。
- **后台轮询**：StoClaw 运行时（即使 Cron 页面未打开），每 60 秒静默轮询一次，有新结果时触发系统通知。
- **启动拉取**：StoClaw 启动时，调用 `GET /results?since={lastSyncAt}&limit=50` 拉取离线期间的所有未同步结果，支持游标分页。
- **手动刷新**：用户在 Cron 页面下拉刷新时，主动触发一次结果查询。

**理由**：
- 轮询实现简单，客户端和云端均无需维护长连接，降低双方复杂度。
- 定时任务的结果对延迟容忍度较高（秒级到分钟级均可接受），30-60 秒轮询足够。
- 游标分页保证增量同步，避免重复数据传输。
- 与现有 `hostapi:fetch` HTTP 代理模式一致，无需新增通信通道。

**替代方案**：WebSocket 实时推送。
- **拒绝理由**：需要云端维护客户端连接状态，增加云端复杂度；Electron 环境下网络切换时重连逻辑复杂；定时任务结果对实时性要求不高，轮询足够满足需求。

**替代方案**：SSE（Server-Sent Events）。
- **拒绝理由**：SSE 在 Electron 的网络恢复场景下重连逻辑较复杂；相比轮询无显著优势。

### 3. 云端结果的本地存储策略

**决策**：云端执行结果拉取到本地后，写入与本地任务相同格式的存储——即 `cron/runs/{cloudJobId}.jsonl` 或等效的本地缓存结构。前端渲染运行历史时不区分数据来源（本地 vs 云端），统一按时间线合并展示。

**理由**：
- 复用现有 `cron-session-utils.ts` 的会话回退和历史渲染逻辑，前端改动最小。
- 本地缓存保证用户在弱网环境下仍能浏览历史结果。
- 统一的存储格式便于后续导出和备份。

**替代方案**：云端结果仅保存在云端，前端每次查看历史时都请求云端 API。
- **拒绝理由**：历史查看延迟高；离线时无法查看；与现有本地历史体验割裂。

### 4. 任务状态的一致性模型

**决策**：采用「本地主控、云端从属」的一致性模型。用户在 UI 上的所有写操作（创建、编辑、删除、开关、手动触发）都先作用于本地状态，再通过 Main-process 异步同步到云端 Task API。云端返回的确认或错误通过通知反馈给用户，但不阻塞 UI 交互（乐观更新）。

**理由**：
- 保持前端交互的即时响应，避免网络延迟影响用户体验。
- 本地状态作为"单点真相"，用户在离线时仍可浏览和管理任务列表（只读）。
- 与现有本地 Cron store 的更新模式一致，降低认知负担。

**替代方案**：云端主控——UI 所有操作直接调用云端 API，本地仅做缓存。
- **拒绝理由**：网络抖动时 UI 卡顿明显；离线时完全无法查看任务列表；与现有架构差异大。

### 5. 云端 Agent 的模型接入与 Provider Key 管理

**决策**：云端 Agent 使用**平台统一管理的 Provider Key**接入模型，用户不需要将自己的 Provider Key 同步到云端。云端 Agent 的模型选择、参数配置（temperature、maxTokens 等）在云端 Agent 管理界面中独立设置，与本地 Gateway 的 Agent 配置完全隔离。云端执行的 Token 消耗由平台统一结算（或按套餐/配额扣减），用户在 StoClaw 中可查看云端执行的用量统计。

**理由**：
- 云端 Agent 与本地 Agent 是独立系统，各自管理自己的模型接入，架构清晰。
- 用户无需将个人 Provider Key 授权给云端，消除敏感信息泄露顾虑。
- 平台可统一谈判模型 API 价格，可能提供比个人开发者更优惠的费率。

**替代方案**：要求用户将 Provider Key 授权给云端使用。
- **拒绝理由**：增加用户信任门槛；与「云端自己有独立 Agent」的架构矛盾；Key 泄露风险由用户承担，平台责任边界模糊。

**替代方案**：云端 Agent 直接使用本地 Gateway 的模型配置和 Key。
- **拒绝理由**：本地关机时 Gateway 不可达；本地和云端模型可能不同，配置无法通用。

### 6. 执行位置的 UI 表达

**决策**：在创建/编辑任务的表单中，以 **Radio 按钮组** 展示「执行位置」选项（本地执行 / 云端执行），默认选中「本地执行」。选择「云端执行」后，下方动态展示云端 Agent 选择器（从云端 Agent 列表中选择目标 Agent）和云端执行的相关说明。任务卡片上通过图标或标签（如一个小云图标）标识云端任务，hover 时 tooltip 提示「云端执行」。

**理由**：
- Radio 按钮直观清晰，用户明确知道自己在做二选一。
- 默认本地执行避免现有用户行为被意外改变。
- 视觉标识帮助用户在列表中快速区分两种任务类型。

**UI Token 对齐**：
- 执行位置选项的选中态使用 **Brand-6** (`#FF6F00`)，未选中态使用 **Grey-6** (`#C9CDD4`)，符合 `docs/sto-design.md` 的 Token 命名（`--color-brand-6`, `--color-border`）。
- 云端标识标签使用 **Info/Blue-6** (`#4760FE`) 的浅色变体（Blue-1 背景 + Blue-6 文字），表示「信息/状态」语义。

## 协作模型：本地/云端任务与本地/云端 Agent

### 1. 任务实体的组织方式

**本地任务**和**云端任务**是**两套独立的实体**，各自有独立的 ID 空间：
- **本地任务**：ID 由 OpenClaw Gateway 生成（如 `job-local-xxx`），状态、调度、执行全由 Gateway 托管。本期 UI 中隐藏本地任务的新建入口，但已存在的本地任务仍可在列表中查看和管理（如有）。
- **云端任务**：ID 由外部云端 Task API 生成（如 `job-cloud-xxx`），状态、调度、执行全由云端托管。本期所有新建任务均为云端任务。
- **本地聚合层**：StoClaw 在本地 electron-store 中维护一个 `cloudCronJobs` 数组，存储云端任务的引用（id、name、schedule、targetAgentId、enabled 等）。Cron Store 在 `fetchJobs()` 时同时调用 `Gateway RPC (cron.list)` 和 `Cloud Task API`，将两套任务合并为统一的任务列表供前端渲染。

**任务不可在执行位置之间切换**：本地任务和云端任务是独立实体，不支持直接切换执行位置。若用户想变更，需删除旧任务并重新创建。

### 2. Agent 的选择与绑定

| 执行位置 | Agent 来源 | Agent ID 空间 | 配置管理 |
|----------|-----------|--------------|---------|
| 本地执行 | 本地 Gateway Agent 列表 | 本地 Agent ID（Gateway 生成） | 本地 Gateway 管理 |
| 云端执行 | 云端 Agent 列表（外部 API 获取） | 云端 Agent ID（云端生成） | 外部云端平台管理 |

- **任务创建时**：选择「本地执行」后，Agent 选择器展示本地 Agent 列表；切换为「云端执行」后，Agent 选择器动态切换为云端 Agent 列表（通过 Cloud Agent API 获取）。
- **同名允许**：本地 Agent 和云端 Agent 允许同名（如都叫「日报助手」），因为它们的 ID 空间独立，且 UI 上会通过环境标签区分。
- **Agent 变更感知**：若本地 Gateway 中的 Agent 被删除，关联的本地任务标记为「Agent 缺失」；若云端 Agent 被删除，关联的云端任务由云端标记为异常，StoClaw 拉取状态时同步展示。

### 3. 任务列表的统一展示

```
┌─────────────────────────────────────────┐
│  Cron 任务列表（统一视图）                │
├─────────────────────────────────────────┤
│ [☁️] 每日报表  → 云端Agent-A  每天 9:00  │
│ [💻] 代码审查  → 本地Agent-B  每小时     │
│ [☁️] 数据备份  → 云端Agent-C  每周一     │
│ [💻] 日志清理  → 本地Agent-D  每天 0:00  │
└─────────────────────────────────────────┘
```

- **排序**：默认按「下次执行时间」排序。
- **筛选**：本期隐藏按执行位置筛选（所有可见任务均为云端任务；本地遗留任务如有则继续展示但不强调）。
- **操作**：每条任务的操作按钮（编辑、删除、开关、手动触发、查看历史）行为一致。
- **统计卡片**：任务总数、运行中、已暂停、失败四个统计维度同时统计本地遗留任务（如有）和云端任务，UI 上不区分来源。

### 4. 写操作的路由

| 操作 | 本地任务 | 云端任务（本期默认） |
|------|---------|---------------------|
| **创建** | `Gateway RPC: cron.add`（本期隐藏入口） | `Cloud Task API: POST /tasks` |
| **编辑** | `Gateway RPC: cron.update` | `Cloud Task API: PUT /tasks/{id}` |
| **删除** | `Gateway RPC: cron.remove` | `Cloud Task API: DELETE /tasks/{id}` |
| **开关** | `Gateway RPC: cron.update` (patch enabled) | `Cloud Task API: PATCH /tasks/{id}/enabled` |
| **手动触发** | `Gateway RPC: cron.run` | `Cloud Task API: POST /tasks/{id}/trigger` |

**关键原则**：
- 本期前端表单中**不展示执行位置选择器**，`createJob()` 直接调用 Cloud Task API 创建云端任务。
- 对于已存在的本地任务（如有），编辑/删除/开关/触发操作仍路由到 Gateway RPC，保证向后兼容。
- Cron Store 的每个 action 在内部根据任务的 `executionLocation` 字段决定调用 Gateway Client 还是 Cloud Task Client。若调用失败，错误统一包装为标准化错误对象，前端通过 Toast 展示。

### 5. 运行历史的聚合与展示

- **本地任务历史**：Gateway 执行完成后，结果写入本地 `cron/runs/{localJobId}.jsonl`，前端直接读取。
- **云端任务历史**：云端执行完成后，结果先存储在云端。StoClaw 通过 **HTTP 轮询**（前台 30s / 后台 60s）和 **启动时增量拉取**（`GET /results?since={lastSyncAt}`）获取新结果，写入本地缓存 `cron/runs/{cloudJobId}.jsonl` 和对应会话的 `.jsonl`。
- **统一渲染**：前端渲染运行历史时，只读取本地缓存（无论是本地任务还是云端任务），按时间倒序展示。每条历史记录展示执行环境标签（本地/云端）、执行时间、耗时、状态和结果摘要。

### 6. 会话与通知的协作

#### 6.1 会话入口

- **任务卡片操作区**展示「会话」按钮（仅云端任务），点击后通过 `switchSession(agent:{cloudAgentId}:cron:{cloudJobId})` 跳转到 Chat 页面的对应会话。
- **Toast 通知**中的「查看」按钮同样跳转到对应会话。
- 任务卡片主体点击仍为**编辑操作**，不与入口冲突。

#### 6.2 结果注入时机与格式

- 云端执行完成后，轮询发现新结果 → 将云端返回的 **Markdown 格式**执行结果直接包装为 `assistant` 消息写入对应会话的 `.jsonl` 文件。
- **不走 StoClaw 本地 AI 模型生成**，消息内容就是云端执行结果本身（文本/报表链接等）。
- 失败结果也包装为 `assistant` 消息，内容前缀标注 `**执行失败**` 及错误原因。

#### 6.3 会话生命周期

- **延迟创建**：任务创建时不自动创建会话；**第一次执行完成后**，`cloud-session-writer` 才在 `sessions.json` 中注册会话并创建 `.jsonl` 文件。
- **删除后重建**：用户在 Chat 页面删除会话后，该任务的历史结果不再可见；下次云端执行完成、结果推送时，`cloud-session-writer` 检测到会话不存在，**自动重新创建一个全新空会话**并注入最新结果（不带历史记录）。
- **一任务一会话**：每个云端任务对应一个长期会话（`agent:{cloudAgentId}:cron:{cloudJobId}`），每次执行结果追加为新的 `assistant` 消息。

#### 6.4 通知推送

- **在线时**：轮询发现新结果后，前端展示 Toast 通知（如「☁️ 每日报表执行完成」），点击 Toast 跳转到对应会话。
- **离线后恢复**：启动拉取完成后，若有新结果，批量展示通知摘要（如「您有 3 个云端任务在离线期间执行完成」）。

## Risks / Trade-offs

**[Risk] 同一任务在本地和云端执行时，因 Agent 配置、模型不同导致结果差异大，用户感到困惑。**
→ **Mitigation**：
  - 在任务创建页和任务卡片上**明确标注**该任务绑定的 Agent 名称、所属环境（本地/云端）和模型信息。
  - 运行历史中的每条记录都展示「执行环境」标签（本地 Gateway / 云端），便于用户对比。
  - 提供「测试运行」功能，允许用户在保存任务前先在目标环境（本地或云端）手动触发一次，预览结果。
  - 在文档/引导中说明：本地 Agent 和云端 Agent 是独立配置，结果差异是预期行为。

**[Risk] 云端 Agent 因平台配额耗尽、模型服务故障或配置错误导致执行失败。**
→ **Mitigation**：
  - 云端执行结果中返回详细的错误分类（平台配额不足 / 模型服务不可用 / Agent 配置错误 / 超时），前端根据错误类型展示对应的引导文案。
  - 平台侧实现熔断机制：连续失败时暂停调度，通知用户排查。
  - StoClaw 在云端 Agent 列表页面展示各 Agent 的健康状态（在线/异常）。

**[Risk] 云端 Agent 配置变更后，已创建的云端任务仍使用旧配置执行，造成预期外行为。**
→ **Mitigation**：
  - 云端 Agent 配置变更时，平台自动通知 StoClaw（推送或下次拉取时携带变更标记），StoClaw 在任务列表中展示「关联 Agent 配置已更新」提示。
  - 提供「将最新配置应用到任务」的一键操作，用户确认后更新云端任务的执行模板。
  - 运行历史中展示执行时使用的 Agent 配置版本号，便于追溯。

**[Risk] 轮询间隔设置不当，导致结果延迟感知或不必要的资源消耗。**
→ **Mitigation**：
  - 前台轮询 30 秒、后台轮询 60 秒，兼顾实时性和资源效率。
  - 轮询频率可通过 Settings 中的「云端同步频率」选项让用户自定义（可选：15s/30s/60s/手动）。
  - 若轮询连续多次无新结果，后台轮询可自动降频（如退避到 120 秒），直到检测到新结果后恢复。

**[Risk] 大量云端任务的执行结果同步导致客户端启动时请求量过大。**
→ **Mitigation**：
  - 拉取接口支持分页（cursor-based pagination），每次限制返回条数（如 50 条）。
  - 仅拉取「当前任务列表中关联的云端任务」的结果，而非全量历史。
  - 结果数据在本地缓存，启动拉取只取增量。

**[Risk] 用户隐私顾虑：任务消息内容和执行结果存储在云端。**
→ **Mitigation**：
  - 传输全程 TLS 加密；云端存储加密（AES-256）。
  - 在 Settings 中提供「云端数据保留策略」选项（如 7 天 / 30 天 / 永久），到期自动清理。
  - 隐私协议中明确告知云端执行模式的数据处理范围。

## Migration Plan

**部署阶段**：
1. **外部团队**先部署云端 Task API（v1）和云端 Agent 运行时，支持任务托管、调度、执行、结果查询和推送。StoClaw 团队需参与接口评审。
2. StoClaw 侧新增 Cloud Task Service（Main-process），通过外部 API 集成云端任务功能，灰度开启（可通过 feature flag 控制）。
3. 前端 UI 在执行位置选择器后展示「Beta」标签，收集早期反馈。

**Rollback**：
- 云端 Task API 故障时，feature flag 关闭云端执行选项，已有云端任务标记为「暂停（云端服务不可用）」，不自动降级为本地执行（避免调度冲突）。
- 本地执行模式不受影响，始终可用。

## Open Questions

1. **云端 Task API 的接口契约**：端点、认证方式、任务 CRUD 格式、结果查询格式是否已由外部团队定义？StoClaw 侧需参与接口评审，何时可以开始？
2. **云端 Agent 管理体系**：用户在 StoClaw 中如何查看和管理云端 Agent（列表、配置、模型选择）？是否有独立的云端 Agent 管理页面，还是复用现有 Agents 页面并增加「环境」筛选？
3. **本地 Agent 与云端 Agent 的映射**：用户是否可能在两个环境中创建同名 Agent？任务创建时的 Agent 选择器如何区分本地和云端 Agent？
4. **计费模型**：云端执行的 Token 消耗是平台统一结算（套餐/订阅制），还是按量从用户账户扣费？是否需要在前端展示云端执行的预估费用？
5. **多设备推送**：同一账号多设备登录时，云端任务结果推送到所有在线设备，还是仅活跃设备？
6. **任务数量上限**：单个用户的云端任务数量是否有限制？前端是否需要预校验？

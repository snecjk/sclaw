## Context

上传技能弹窗目前使用同一个拖拽/点击区域表达文件与文件夹两种来源。拖拽事件能够获得文件或目录路径，但 Electron 的系统打开对话框在 Windows 上必须明确使用文件模式或目录模式，因此点击入口无法在一个系统窗口内稳定实现混选。目标交互稿要求保留现有弹窗上半部分，在拖拽区下方增加两个易理解的选择入口。

现有技能路径进入预览后已有统一的格式校验和上传流程。本变更只负责取得一个文件或目录路径，不改变后续业务协议。可见样式必须遵循 `docs/sto-design.md`，避免为交互稿新增散落的硬编码颜色。

## Goals / Non-Goals

**Goals:**

- 让用户无需理解系统选择器限制，也能明确选择技能文件或技能文件夹。
- 保留拖拽文件与文件夹并自动识别的快捷方式。
- 让三种入口复用同一套预览、校验、上传和错误处理流程。
- 在 Windows、macOS 和 Linux 上提供一致的应用内入口与可访问性行为。
- 仅改造交互稿红框对应的下半部分，不改变弹窗已有信息和业务流程。

**Non-Goals:**

- 在单个原生系统窗口中混合选择文件和文件夹。
- 引入 native addon 或修改 Electron/Chromium。
- 支持批量上传、增加新的技能格式或改变上传接口。
- 重做上传预览、进度、成功或失败状态。

## Decisions

### 1. 使用两个显式选择入口

点击“选择技能文件”时使用文件模式，点击“选择技能文件夹”时使用目录模式。这样每个入口的文案与系统窗口行为一致，用户在点击前即可理解选择目标。

**Rationale:** Windows 原生对话框无法通过现有 Electron API 稳定提供文件与目录混选，拆分入口能在不增加平台代码的前提下消除歧义。

**Alternative considered:** 同时传入 `openFile` 和 `openDirectory`，或开发 native addon 调用系统底层接口。前者在 Windows 上行为不满足需求，后者增加原生编译、签名、打包和维护成本，因此不采用。

### 2. 保留统一拖拽区并自动识别来源

拖拽区继续接收一个 `.zip`、一个 `SKILL.md` 或一个技能目录。本变更不得用新增点击选择逻辑替换现有 drag enter/over/leave/drop 处理，也不得移除当前浏览器默认行为拦截、复制态反馈及 Electron 文件路径兼容获取方式。拖入后仍按原链路提取路径并交给现有预览入口，来源类型由现有校验流程确认。

**Rationale:** 拖拽本身已经可以覆盖文件和目录，继续统一入口比人为拆成两个拖拽区更直接。

**Alternative considered:** 为文件和目录分别增加拖拽区。这会扩大弹窗、增加用户决策，并破坏当前已可用的拖拽习惯，因此不采用。

### 3. 三种来源汇合到同一个路径处理流程

文件选择、目录选择和拖拽成功取得路径后，统一调用现有预览/校验入口。系统对话框取消时不触发状态切换；校验失败时沿用现有错误展示，并允许用户重新选择。

**Rationale:** 来源只影响路径如何取得，不应产生三套上传状态机；汇合可降低回归风险并保持错误语义一致。

**Alternative considered:** 分别为文件和目录维护独立的预览与错误状态。该方案重复业务逻辑，容易造成不同入口行为漂移，因此不采用。

### 4. 下半部分使用可操作行而非下拉菜单

在“或选择”分隔线下直接显示两个完整操作行，每行包含语义图标、标题、辅助说明和箭头；文件行附带“推荐”标识。整行作为一个可聚焦、可点击的操作目标，并提供 hover、focus-visible 和 active 状态。

**Rationale:** 两个选项同时可见，用户无需先理解下拉菜单，也更符合交互稿的低学习成本目标。

**Alternative considered:** 点击拖拽区后弹出下拉菜单或二次确认弹窗。额外步骤会隐藏关键差异，键盘路径也更长，因此不采用。

### 5. 使用 STO 语义 Token 同时适配深色与浅色模式

两个来源操作行的标题、辅助文字和图标使用 Text 层级 Token，容器与分隔线使用 Border/Fill Token，悬停、按下和聚焦使用对应 Interaction modifier；“推荐”标识使用 Brand 语义 Token。所有颜色必须来自可随应用主题切换的现有主题变量，使两个操作行及其状态在深色和浅色模式下分别获得合适的背景、边框和前景对比度，不直接复制交互稿颜色值。

**Rationale:** 这能让新增区域跟随应用当前主题即时切换，并在深色与浅色背景下保持可读性和状态辨识度，同时满足 `docs/sto-design.md` 的主题规范。

**Alternative considered:** 直接按截图写入固定 hex。该方式会绕过主题系统且可能导致对比度和多主题不一致，因此不采用。

## Risks / Trade-offs

- [Risk] 两个入口让弹窗高度增加，在低分辨率窗口中可能超出可视区域。 → Mitigation：保持操作行紧凑，并验证弹窗最大高度与必要的内容滚动行为。
- [Risk] 用户仍可能选择不包含 `SKILL.md` 的目录或无效文件。 → Mitigation：继续由现有预览校验提供明确错误，不在选择阶段复制文件系统校验逻辑。
- [Risk] 点击操作行可能与窗口拖拽区域或事件捕获发生冲突。 → Mitigation：沿用弹窗中的 `no-drag` 约定，并为选择与拖拽交互分别增加回归测试。
- [Risk] 重构 idle 状态布局时可能意外改变拖拽区域的事件绑定或覆盖层命中范围。 → Mitigation：保留现有拖拽节点和处理函数，只在其后追加来源选择区域；以变更前拖拽用例作为强制回归基线。
- [Risk] 仅按深色交互稿实现可能导致浅色模式下边框、辅助文字或 hover 状态对比不足。 → Mitigation：禁止固定深色值，使用主题语义 Token，并将两套主题的默认及交互状态纳入视觉验收。
- [Risk] 文件过滤器可能让用户误以为任意 Markdown 文件都有效。 → Mitigation：辅助文案明确写为 `SKILL.md`，最终仍由现有校验确认文件名和内容。

## Migration Plan

1. 在现有上传弹窗中加入两个来源入口，并复用当前路径预览函数。
2. 补充中、英、日文案及组件交互测试。
3. 在 Windows 上验证两个系统选择窗口，在至少一个其他桌面平台验证入口一致性和拖拽回归。
4. 如需回滚，只移除新增下半部分并恢复原点击入口；上传接口和存储无需迁移。

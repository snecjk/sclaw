### 1.SAI-CLI 测评集机制
> 背景思考：随着后续 CLI 接入越来越多，线上的调用率与执行成功率都是事后数据——只能反映已经发生的问题，无法预防上线翻车。   
> 用户随便问一句:AI 到底能不能选对 CLI、拼对参数、返回可用答案？   

每个 CLI 在接入到 CLI 池后，需要在正式上线前就回答这个问题。因此，每个 CLI 应该有自己的测试集，用于验证单个 CLI 接入池后是否能按预期被调用和执行。

#### 价值与目标
```text
┌─────────────────────────────────────────────────┐
│  当前：人工接入 → 线上看数据 → 出问题再补救      │
└─────────────────────────────────────────────────┘
                      ↓ 引入测评集
┌─────────────────────────────────────────────────┐
│  目标:CLI 从「人工接入」走向                    │
│        ✓ 可测试：上线前就知道能不能用            │
│        ✓ 可迭代：基于失败案例反推 tag / 参数优化 │
│        ✓ 可评估：每个 CLI 都有命中率基线         │
└─────────────────────────────────────────────────┘
```

测评集不仅是上线门禁，也是长期 tag 优化的训练 / 回归数据集——后续 prompt 调整、tag 重构都能拿这套数据做 A/B 验证。

#### 测评集结构

每个 CLI 至少配置 10 条真实问法，覆盖以下维度：

| 字段 | 说明 |
|------|------|
| 用户自然语言 | 真实用户可能的问法 |
| 期望命中 CLI | 该问法应该命中哪个 CLI |
| 期望参数 | 期望解析出的参数 (时间、组织、维度等) |
| 是否命中 | ✅ 命中 / 🔄 部分命中 / ❌ 未命中 |
| 问题原因 | 未命中时的根因分析 |



#### 测评集样例

| 用户自然语言 | 期望命中 CLI | 期望参数 | 是否命中 | 问题原因 |
|------------------|----------------|------------|------------|------------|
| 查一下昨天浙江网点时效差的原因 | 全链路时效诊断 | 日期=昨天，区域=浙江 | ✅ | - |
| 看看上海转运中心交货滞留怎么样 | 交货滞留率 | 中心=上海转运中心 | 🔄 | 组织 code 未识别 |
| 哪些网点最近派件履约差 | 派件履约 | 时间=近 7 天 | ❌ | Tag 缺少"履约差" |

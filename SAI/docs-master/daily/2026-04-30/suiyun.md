## 二、方案一：`/discover` 自适应智能增强 v2.0

**解决的问题**：当前命令发现（Discover）是静态搜索引擎——不同用户搜同一个词，得到完全相同的候选结果。系统没有用户画像、没有反馈闭环、没有会话感知，"用多少次都不会变聪明"。

**核心思路**：在现有三层混合检索（向量语义 + 关键词 + 融合排序）之上，叠加 **第四层「个性化重排序」** ，引入四大智能引擎：

| 引擎 | 能力 | 业务价值 |
|------|------|----------|
| **记忆引擎** | 记住每个用户的常用命令、偏好业务域 | 搜"查询"时，运单组和财务组看到不同排序 |
| **语境引擎** | 感知会话上下文，根据上一个命令预测下一个 | 执行完A后，系统知道你可能需要B/C/D |
| **协同引擎** | 与你相似的用户选了什么，推荐给你 | 新员工直接受益于同组老员工的使用经验 |
| **进化引擎** | 权重随用户数据量自动调优，冷启动→个性化平滑过渡 | 新用户靠基础检索，越用越个性化 |

**关键设计决策**：
- **不破坏现有架构**，完全向后兼容，仅新增第四层
- 引入反馈闭环（`/feedback` 接口），隐式采集用户选择信号
- 引入 **语义簇（Semantic Cluster）**，将"查遗失件"/"丢失包裹"/"遗失件数量"归为同一意图
- 个性化权重随使用量动态增长：新用户 5% → 成熟用户 35%

## 三、方案二：用户专属命令进化系统 v1.0

**解决的问题**：标准 API 命令是"原材料"（如 `order.lost.query --site=深圳 --date=today`），用户需要的是"成品"。大量重复的参数输入、多步骤手动串联、个人命名习惯差异——这些痛点需要系统层面解决。

**核心思路**：在标准命令底座之上，构建 **四级进化金字塔** ，让系统从用户行为中自动"长"出专属命令：

| 层级 | 能力 | 示例 |
|------|------|------|
| **① 快捷命令** | 高频参数组合一键固化 | 用户每天输入同一条带参命令 → 自动建议"深圳遗失件日报" |
| **② 语义别名** | 自然语言习惯 → 标准命令 | 用户搜3次"丢失"都选了 `order.lost.query` → 下次"丢失"直接命中 |
| **③ 智能预设** | 参数默认值自动学习 | 用户95%情况下 site=深圳 → 自动预填，无需每次输入 |
| **④ 编排命令** | 多步骤操作一键串联 | A→B→C 重复3次 → 一条"深圳晨报"命令自动串联 + 聚合输出 |

**关键设计决策**：
- **90% 由系统自动发现和创建**，用户只需"确认/命名/忽略"
- **全生命周期管理**：创建 → 活跃 → 衰减 → 自动清理，不用的命令自动回收
- 标准命令注销时，依赖它的专属命令自动降级，不报错
- 编排命令支持 JSONPath 数据流转（上一步的输出 → 下一步的输入）

**预期效果**：命令输入耗时减少 40%~80%，专属命令最终占据用户日常操作的 70%。

## 四、两个方案的关系

```
方案一（Discover 重排序）        方案二（命令进化）
        │                              │
        │  "帮你找到对的命令"            │  "帮你创造专属命令"
        │                              │
        ▼                              ▼
   个性化排序结果              ──反馈──▶  快捷命令/语义别名/编排命令
                                             │
                                             ▼
                                    反哺 Discover（专属命令天然排第一）
```

方案一是 **发现层面** 的智能化，方案二是 **执行层面** 的自主进化。两者共享同一套行为日志基础设施（`user_command_behavior` / `user_command_sequence`），形成数据闭环。


## 五、核心结论

这两个方案共同定义了 SAI 命令体系从 **"静态工具"** 到 **"会学习的智能助手"** 的进化路线。**不靠人工规则，靠用户真实行为数据驱动**；**不推翻现有架构，在成熟底座上渐进增强**。

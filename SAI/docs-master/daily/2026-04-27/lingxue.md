## 今日进展

### 一、API 调用率与执行成功率分析方案讨论

今日围绕“用户 NL → Agent → CLI → API”调用链路，讨论后续如何采集与分析 API 调用率、执行成功率数据，并明确平台侧整体能力由 @谋定 负责建设。

#### 1. 链路口径初步明确


| 链路节点        | 核心关注点                                  | 指标口径  |
| ----------- | -------------------------------------- | ----- |
| 用户 NL → CLI | 用户自然语言是否能命中对应 API Tag                  | 调用率   |
| Agent → API | Agent 根据语义和 help 文档拼接 cmd 后，API 是否成功执行 | 执行成功率 |


> 说明：调用率主要看 NL 语义与 Tags 的匹配效果；执行成功率主要看 Agent 拼接 cmd 并调用 API 的成功情况。

#### 2. 调用率与执行成功率分析口径

**调用率分析**

调用率主要判断用户原始 NL 是否能够命中可调用的 API 能力，需要平台侧提供用户原始问题与命中情况，用于后续分析语义识别与 Tag 体系是否完整。


| 分析项      | 说明                                         | 依赖内容         |
| -------- | ------------------------------------------ | ------------ |
| 原始 NL 采集 | 记录用户原始提问内容                                 | 平台提供用户原始 NL  |
| Tag 命中判断 | 判断用户语义是否匹配到 API Tags                       | 平台提供命中/未命中结果 |
| 未命中分析    | 对未命中的问题进行归因，判断是 Tag 缺失、语义表达不一致，还是 API 能力缺口 | 后续人工/平台结合分析  |


**执行成功率分析**

执行成功率主要判断 Agent 在识别用户语义后，是否能根据 CLI help 文档正确拼接 cmd，并成功调用 API 返回数据。


| 场景                | 判断方式                  | 处理方式         |
| ----------------- | --------------------- | ------------ |
| API 未返回数据         | Agent 可直接打标为未成功       | 平台自动记录       |
| API 返回报错          | 根据错误信息判断执行失败原因        | 平台记录错误码/错误信息 |
| cmd 拼接错误但 API 有返回 | 可能返回错误数据，无法完全依赖系统自动判断 | 需要人工抽检或规则校验  |
| API 正常返回          | 记录为执行成功               | 平台自动统计       |


> 当前难点：`cmd` 拼接错误但仍返回数据的场景，需要人工判断或引入结果校验规则，不能简单按“有返回”视为成功。

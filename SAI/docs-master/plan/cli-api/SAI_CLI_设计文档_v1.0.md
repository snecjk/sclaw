## 一、整体架构框架

SAI（Smart Agent Interface）采用四层分层架构，实现 AI Agent 与各业务域后端服务的标准化接入。

```
┌─────────────────────────────────────────────────────────────────┐
│  调用层   统一 AI Agent（指令理解 → 调用 CLI → 结果返回）         │
└─────────────────────────────────────────────────────────────────┘
                             ↓
┌─────────────────────────────────────────────────────────────────┐
│  网关层   CLI 路由转发、负载均衡、同步机制、权限校验               │
└─────────────────────────────────────────────────────────────────┘
                             ↓
┌─────────────────────────────────────────────────────────────────┐
│  CLI 核心层  统一命令规范、入参/出参 JSON、公共能力（认证/日志）   │
│  ┌─────────────┐    ┌─────────────┐    ┌─────────────┐          │
│  │   昆仑 CLI  │    │   网络 CLI  │    │   政策 CLI  │          │
│  └─────────────┘    └─────────────┘    └─────────────┘          │
└─────────────────────────────────────────────────────────────────┘
                             ↓
┌─────────────────────────────────────────────────────────────────┐
│  后端 API 层  各域现有后端 API（无需改造前端 GUI）                 │
└─────────────────────────────────────────────────────────────────┘
```

**各层职责说明：**


| 层级            | 核心职责                        | 关键约束         |
| ------------- | --------------------------- | ------------ |
| 调用层（AI Agent） | 理解自然语言指令，映射为 CLI 命令，返回结构化结果 | 不直接调用后端 API  |
| 网关层           | 路由转发、鉴权校验、负载均衡、命令清单同步       | 不包含业务逻辑      |
| CLI 核心层       | 命令解析、参数校验、调用后端 API、结构化输出    | 不感知 Agent 存在 |
| 后端 API 层      | 提供业务功能的 HTTP 接口             | 无需改造，零侵入     |

## 二、CLI 设计原则与规范

### 原则 1：GUI 零改造

只抽取 GUI 背后的后端 API，CLI 直接调用 API，不修改任何前端 GUI 代码。后端 API 以只读方式被 CLI 复用，业务功能保持原样运行。

---

### 原则 2：架构解耦

调用链路为：**Agent → 网关 → CLI → API**，层层解耦，每一层只依赖下一层的接口契约，不穿透调用。

- Agent 不直接调用 API
- CLI 不感知 Agent 的存在
- 网关负责路由和鉴权

此分层设计使每一层可以独立演进、独立部署、独立测试。

---

### 原则 3：协议统一

所有 HTTP 调用及 CLI 的入参/出参统一使用 **JSON 格式**，禁止使用非结构化文本输出（错误输出同样遵循此约定，见原则 6）。

---

### 原则 4：统一命令规范

**命令格式：**

```
{product} {module} {action} [params]
```

**格式说明：**


| 字段      | 含义            | 示例值                                     |
| ------- | ------------- | --------------------------------------- |
| product | 产品域标识         | `kunlun`、`network`、`policy`             |
| module  | 功能模块          | `timeliness`（时效）、`route`（路由）、`rule`（规则） |
| action  | 操作类型          | `query`、`create`、`update`、`delete`      |
| params  | 命令参数（JSON 格式） | `--type 出港滞留`                           |


**各域命令示例：**

```bash
# 昆仑域 - 查询出港滞留时效
kunlun timeliness query --type 出港滞留 --date 2026-04-21

# 网络域 - 查询网络路由配置（示例，待补充）
network route query --origin 上海 --dest 北京

# 政策域 - 查询运费政策规则（示例，待补充）
policy rule query --product 标快 --region 华东
```

### 原则 5：可被 Agent 调用

每个 CLI 命令必须满足以下两个条件，以确保 Agent 能够正确理解和调用：

1. **无交互式输入**：所有参数通过命令行传入，禁止运行时弹出交互式提示（如 `prompt` 等待用户输入）
2. **结构化 Tag 元数据**：每个命令附带 Tag 信息，描述功能、参数说明和调用示例，供 Agent 在调用前理解命令能力

**Tag 示例：**

```json
{
  "command": "kunlun timeliness query",
  "description": "查询昆仑时效数据，支持按类型、日期、区域筛选",
  "params": [
    { "name": "--type", "type": "string", "required": true, "description": "时效类型，如：出港滞留、到港超时" },
    { "name": "--date", "type": "string", "required": false, "description": "查询日期，格式 YYYY-MM-DD，默认今日" }
  ],
  "example": "kunlun timeliness query --type 出港滞留 --date 2026-04-21"
}
```

---

### 原则 6：结构化错误输出

所有错误输出必须为结构化 JSON，包含以下四个固定字段：


| 字段        | 类型     | 说明                                       |
| --------- | ------ | ---------------------------------------- |
| `type`    | string | 错误类型（如 AUTH_ERROR、PARAM_ERROR、API_ERROR） |
| `code`    | string | 错误码（与后端 API 错误码对齐）                       |
| `message` | string | 人类可读的错误描述                                |
| `hint`    | string | 修复建议，指导用户或 Agent 下一步操作                   |


**错误输出示例：**

```json
{
  "type": "AUTH_ERROR",
  "code": "401",
  "message": "Token 已过期或无效",
  "hint": "请执行 sai login 重新获取 Token，或检查 STO_CLI_TOKEN 环境变量是否正确配置"
}
```

```json
{
  "type": "PARAM_ERROR",
  "code": "400",
  "message": "缺少必填参数 --type",
  "hint": "请通过 --type 指定时效类型，可选值：出港滞留、到港超时"
}
```

```json
{
  "type": "API_ERROR",
  "code": "500",
  "message": "后端服务暂时不可用",
  "hint": "请稍后重试，如问题持续请联系 STO 运维团队"
}
```

---

### 原则 7：开发语言统一

所有 CLI 工具链统一使用 **Golang** 开发。

**选型依据：**

- 飞书 CLI、GitHub CLI 均采用 Go，生态成熟
- 编译为单一二进制文件，无运行时依赖，部署简单
- 跨平台支持良好，适合在 Agent 容器环境中运行

---

### 原则 8：Tag 自动化生成

CLI 命令的 Tag 元数据由 AI 根据 API 描述自动生成，**不人工手写**。

**生成流程：**

```
后端 API 描述文档
       ↓
AI 自动生成 Tag（命令描述、参数说明、示例）
       ↓
业务系统/团队 Review 确认
       ↓
Tag 发布至网关命令清单
```

### 原则 9：安全与鉴权

#### Token 获取优先级（从高到低）

1. **命令行参数**：`--token <JWT_TOKEN>`
2. **环境变量**：`STO_CLI_TOKEN=<JWT_TOKEN>`
3. **本地配置文件**：`~/.sai/sso-auth.json`（由 Agent 登录后自动写入）

CLI 在执行每条命令前，按此顺序依次尝试获取 Token，取到即停止。

#### Token 机制说明


| 维度   | 说明                                          |
| ---- | ------------------------------------------- |
| 认证标准 | JWT Token，全链路统一使用 SSO Token                 |
| 权限控制 | Scope 权限控制，每个命令对应一组所需 Scope                 |
| 身份体系 | Bot Token（Agent 应用级权限）+ User Token（人工用户级权限） |
| 高危操作 | 批量修改、删除类操作需要更高权限 Token 或额外二次确认              |


#### 配置文件格式（`~/.sai/sso-auth.json`）

```json
{
  "token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "identity_type": "bot",
  "scopes": ["kunlun:read", "network:read", "policy:read"],
  "expires_at": "2026-04-22T10:00:00Z"
}
```

---

### 原则 10：可测试性与 Dry-Run

#### Dry-Run 模式

每个**写操作命令**（create/update/delete）必须支持 `--dry-run` 参数：

```bash
# 示例：Dry-Run 模式下预览将要执行的操作，不实际执行
policy rule update --id R001 --fee 12.5 --dry-run
```

Dry-Run 返回"将要执行的操作描述"，而非实际执行，让 Agent 和操作人员在执行前确认影响范围。

**Dry-Run 返回示例：**

```json
{
  "dry_run": true,
  "action": "UPDATE",
  "target": "policy.rule",
  "changes": [
    { "field": "fee", "from": "10.0", "to": "12.5" }
  ],
  "affected_count": 1,
  "warning": null
}
```

#### 单元测试可测性要求

CLI 核心逻辑通过接口抽象实现，确保在无真实 API 环境下可单元测试：


| 依赖项      | 抽象方式                    |
| -------- | ----------------------- |
| 文件系统     | 使用 `vfs` 虚拟文件系统封装       |
| HTTP 客户端 | 通过 interface 注入，支持 Mock |
| Token 读取 | 通过接口抽象，支持注入测试 Token     |

## 四、CLI 与 Harness Manager、Agent 对接及运维职责

### 4.1 与 Harness Manager 对接及运维

#### 部署方式

采用 **OSS 挂载**形式，将业务 CLI 包挂载至 Agent 运行环境，由公共 `sai-cli` 负责统一路由。

**CLI 发布流程：**

```
业务 CLI 代码更新
       ↓
打包为二进制（Go build）
       ↓
上传至约定的 OSS 路径（路径详见接口文档）
       ↓
调用网关"发布通知"接口，同步更新命令清单
       ↓
网关生效，Agent 可调用新版命令
```

#### 鉴权机制（任选其一，优先级见原则 9）


| 方式     | 说明                                         |
| ------ | ------------------------------------------ |
| 配置文件读取 | 读取本地 `~/.sai/sso-auth.json`（Agent 登录后自动生成） |
| 参数传入   | CLI 网关通过参数注入，格式：`--sso-auth {xxxxx}`       |


---

### 4.2 CLI 网关与 Agent 职责划分

#### CLI 网关能力

网关向下游 CLI 提供以下核心支持：


| 能力     | 说明                                                |
| ------ | ------------------------------------------------- |
| 元数据生成  | 支持通过自然语言描述，AI 自动生成命令元数据及 Tag 信息；业务系统 Review 确认后生效 |
| 发布通知接口 | 接收业务 CLI 上报请求，触发命令清单同步更新                          |
| 路由转发   | 根据 product 字段将请求路由至对应域的 CLI                       |
| 权限校验   | 验证 Token 合法性及 Scope 是否满足命令所需权限                    |


#### Agent 职责


| 职责     | 说明                                |
| ------ | --------------------------------- |
| SSO 认证 | 通过 SSO 单点登录接口获取 Token 及用户身份信息     |
| 信息持久化  | 将认证信息保存至本地 `~/.sai/sso-auth.json` |
| 命令调用   | 理解自然语言意图，映射至标准 CLI 命令并执行          |
| 鉴权标准   | 全链路权限认证统一使用 SSO Token             |

## 二、跨文档矛盾与不一致

### 🔴 矛盾 1：LLM Gateway 管理接口工具名不一致

- `LLM-Gateway建设方案.md` 第三章："触发 Webhook 调用 **New API** 的管理接口，自动创建对应渠道和唯一 Token"
- 但第五章节选型结论明确选的是 **LiteLLM**

**影响**：开发者不知道对接 New API 还是 LiteLLM 的管理 API。两者 API 完全不同。
**建议**：全文统一为 LiteLLM，删除 New API 管理接口的描述。

---

### 🔴 矛盾 2：CLI 开发职责在两版方案中完全相反

| | v1.0 / 会议纪要 | v1.2（最新） |
|--|--|--|
| CLI 开发方 | 各业务域各自开发 Go CLI | Harness Manager 统一构建单一 CLI |
| 业务域职责 | 开发 CLI + 提供 API | 只提供 API，不参与 CLI 开发 |
| 发布方式 | 各域自行上传 OSS | HM 统一打包上传 |

**影响**：如果还有业务域按 v1.0 在开发自己的 CLI，全部返工。
**建议**：确保所有成员（尤其是淩雪和各业务域）已明确 v1.2 方案。

---

### 🔴 矛盾 3：OSS 挂载在 Agent Runtime 中是 Block 点，在 CLI v1.2 中假设已可用

- Agent Runtime 方案："当前 block 的点，OSS 的挂载逻辑是在 Agent 层配置，无法根据用户实现个性化挂载"
- CLI v1.2 部署方式："采用 OSS 挂载形式，将统一打包的 SAI-CLI 二进制文件挂载至 Agent 运行环境"，且列出了详细路径规范

**影响**：如果个性化 OSS 挂载在 4/30 前无法交付（阿里云评估中），HM 的整个 CLI 分发方案无法实施。
**建议**：确认阿里云评估结果时间。如 4/28 前无结论，立即启动 B 方案（Agent 层自行实现文件权限）。

---

### 🟡 矛盾 4：Tag 生成方式不一致

- 整体架构文档：暗示由业务方注册上报
- Harness Manager review（4/20）："Tag 是业务方手动注册上报的"
- CLI v1.2（4/24 更新）："由 AI 根据各域 API 描述文档自动生成，不人工手写"

**影响**：业务域不知道是手动写 Tag 还是等 AI 生成。
**建议**：v1.2 的描述更合理，但需明确生成工具何时交付、业务域如何提交 API 描述。

---

### 🟡 矛盾 5：冷启动方案在不同文档/日报中描述不一致

- `LLM-Gateway建设方案.md`：Kubernetes 集群部署
- Agent Runtime 方案：基于阿里云函数计算，冷启动 <1s
- 徐春辉 4/24 日报：ACS（20-30s）vs 宿主机（~5s），AgentRun 模块

**影响**：冷启动到底用函数计算还是 Kubernetes Pod？5s 目标能否达成？
**建议**：明确 Agent Runtime 的底层基础设施（函数计算 vs K8s CloneSet vs ACS）。

---

### 🟡 矛盾 6：Agent Runtime 文档完全不提及 Harness Manager

- Agent Runtime 方案中写 "看隋云那边 skill 分发的策略"
- 但没有任何对 HM 接口的引用或依赖描述
- 整体架构文档中 `AR -.->|"拉取Skill"| HM` 是明确的依赖

**影响**：奕杭开发 Agent Runtime 时不知道如何从 HM 拉取 Skill/CLI。
**建议**：在 Agent Runtime 方案中增加 "与 Harness Manager 的接口契约" 章节。

## 三、关键缺失

### 🔴 缺失 1：Channel（申懂懂 App）设计文档

**现状**：弘宇负责整个用户接入层，但无任何设计文档。
**需要**：
- 前端交互架构（如何引入 Agent SDK）
- 消息协议（流式/非流式、SSE/WebSocket）
- 会话管理（多会话、会话历史）
- 生成式 UI 方案（如有）
- 与 Agent Runtime 的接口定义（`POST /agent/session` 等）

**整体架构文档中标注为 ⚠ 未写入文档，至今未补齐。**

---

### 🔴 缺失 2：Agent Runtime ↔ Harness Manager 接口契约

需要定义的具体接口：

| 接口 | 调用方 | 提供方 | 需要定义 |
|------|--------|--------|---------|
| `GET /hm/skills/list` | Agent Runtime | HM | 请求参数、响应 schema、分页、缓存策略 |
| `POST /hm/kb/search` | Agent Runtime | HM | 查询语法、返回格式、相似度阈值 |
| `GET /hm/cli/meta` | CLI Client | HM | 版本查询、增量同步 |
| SkillCompiler 输出 | HM | Agent Runtime | Agent 可读的 Tool 定义格式 |

---

### 🔴 缺失 3：LLM Gateway 逃生方案

文档写了"待确认"但至今未定义。

**建议至少两个方案**：
1. 业务侧 fallback 直连百炼原生 API
2. Gateway bypass 模式，一键关闭所有路由规则

---

### 🟡 缺失 4：全局错误码与状态码规范

各模块各自定义错误码，没有全局统一标准。

**建议**：定义一套跨模块的错误码体系，至少覆盖：
- 认证错误（401/403）
- 参数错误（400）
- 服务不可用（503）
- 限流（429）
- 业务错误（带 code + message）

---

### 🟡 缺失 5：HM 知识库（KB）设计

整体架构文档列了知识库作为 HM 子模块，但没有任何文档描述：
- 知识库的数据源（文档导入？API 同步？）
- 向量存储方案
- 检索算法
- 更新机制

---

### 🟡 缺失 6：Skills 分发设计

整体架构文档列了 Skills 作为 HM 子模块，但：
- Skill 的格式是什么？（YAML？JSON？）
- Skill 如何版本管理？
- Agent 如何加载和执行 Skill？
- Skill 与 CLI 的关系是什么？（Skill 内部调用 CLI？还是独立？）

---

### 🟡 缺失 7：性能与容量规划

没有文档提到：
- 预期 QPS / 并发用户数
- Token 消耗预估
- 存储容量规划（OSS、RDS、Redis）
- Agent 实例数量预估
- 1500 个 API Tag 元数据量级对 Agent 启动速度的影响

---

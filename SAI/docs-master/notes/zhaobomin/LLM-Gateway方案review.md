# LLM Gateway 方案 Review

> Review 日期：2026-04-20
> Review 人：赵柏敏
> 原始文档：`llm-router/design/LLM Gateway 建设方案.md`、`llm-router/design/LLM gateway 一期功能规划及430上线目标.md`

---

## ✅ 做得好的

1. **痛点抓得准** — 5个痛点（接口不统一、成本难管、安全风险、无优先级、纯人工）都是实打实的问题，不是凭空想象
2. **LiteLLM 选型合理** — 功能丰富度、限流、告警、降级都比 New API 强，适合企业级使用
3. **三期规划清晰** — 4/30 个人用户 → 5/15 DevOps 打通 → 5/30 全量推广，节奏递进
4. **额度预警熔断机制** — 80%/90%/100% 三级告警 + 自动熔断，成本可控
5. **环境路由策略** — 测试用便宜模型、生产核心用旗舰，这个策略省钱

---

## ⚠️ 需要关注的风险

### 1. 4/30 上线时间太紧

- 从现在到 4/30 只剩 10 天，但文档里写了 5 个功能模块（审批流、令牌管理、监控告警、网关配置、测试），而且前端 + 后端 + RDS 都要搞定
- 文档自己写了「Web 端尚未适配 BaseURL 路由」，前端工作还没开始
- **建议：** 4/30 的 scope 先砍到最小可用：LiteLLM 网关跑通 + 手动创建 key + 基础告警。审批流和令牌管理页面可以放到 5/15

### 2. 前后文矛盾

- 建设方案里写的是「调用 **New API** 的管理接口」自动创建 token，但选型结论是 LiteLLM。到底是 New API 还是 LiteLLM 的管理接口？
- **建议：** 全文统一，确定 LiteLLM 就写 LiteLLM 的 API

### 3. 逃生方案不明确

- 文档最后写了「待确认：逃生方案」，但没给出具体方案
- 网关一旦故障，所有 AI 调用都会断
- **建议：** 至少要有两个方案：
  - 业务侧支持 fallback 直连百炼/OpenAI 原生 API（绕过网关）
  - 网关支持 bypass 模式，一键关闭所有路由规则

### 4. 计费误差未给出量化评估

- 写了「误差无法避免」（分词规则差异、不支持阶梯计费），但没给误差范围
- 如果计费偏差 10%+，预算管控就失去意义
- **建议：** 先做一轮实测对比：同样的请求走网关 vs 走百炼控制台，统计偏差比例，心里有数

### 5. 安全方案有缺口

- 数据脱敏写的是「可选配」，但高敏数据应该是强制拦截
- 没有提到 **prompt 长度/内容限制**（防止 prompt 注入、超大 prompt 消耗大量 token）
- 没有提到 **审计日志留存周期**（多久过期？谁有权限看？）
- **建议：** 高敏场景脱敏改为默认开启；加 prompt 输入限制规则

### 6. 前端技术选型缺失

- 建设方案里只有 LiteLLM 后端，前端用什么？文档里没提
- LiteLLM 自带的 UI 是英文管理员界面，如果要给普通用户用，大概率要自己开发
- **建议：** 明确前端是「LiteLLM 自带 UI + 二次开发」还是「从零自研」，这直接影响 4/30 的可行性

### 7. 百炼账号迁移的建议需要评估

- 文档写了「建议申通百炼账号迁移到申雪」，但没写迁移成本和风险
- 历史 key 的兼容性问题怎么处理？
- **建议：** 加一个迁移风险评估，先小范围试点

---

## 💡 总体评价

方向对，方案扎实，但 **4/30 的 scope 偏大**。建议先把「网关 + 手动发 key」跑通，审批流和前端管理页面可以往后推。第一周能跑通网关、验证路由和告警，就是很好的里程碑。

# Agent Runtime 方案 Review

> Review 日期：2026-04-20
> Review 人：赵柏敏
> 原始文档：`agent-runtime/design/Agent.md`

---

## ✅ 做得好的

1. **用户隔离思路清晰** — 基于 serverless（AgentRun）按 session 分配实例，一实例一 session，干净
2. **热启动数据扎实** — 冷启动 <1s，热启动 100ms，有实测数据，说明不是拍脑袋
3. **Skill 隔离方案有备选** — OSS 挂载走不通就走 Agent 层自己实现文件权限，有 B 计划
4. **ACP 协议考虑了向前兼容** — 虽然当前不做，但设计时留了口子，技术判断合理（等 Python SDK、不分散精力）

---

## ⚠️ 需要关注的风险

### 1. 方案粒度太粗，更像思考笔记

- 不是完整的设计文档，没有架构图、接口定义、数据流
- OSS 挂载 block 点写了「待评估」，但没有给出评估时间线和决策人
- **建议：** 补一份正式的 Agent Runtime 设计文档，至少包含：系统架构图、核心接口定义、session 生命周期、错误处理机制

### 2. 与老徐的接口依赖没写清楚

- 早会上确认的两个核心接口（`get_session` / `send_request`）在文档里没有体现
- serverless 层不感知 user id 这个原则也没写进来
- **建议：** 把跟老徐对齐的接口定义写进文档，明确谁依赖谁

### 3. Skill 分发的依赖关系模糊

- 写了「看隋云那边 skill 分发的策略」，但隋云的设计文档还没出
- systemspace 的组织方式（用户/领域/公共）没有定论
- **建议：** 跟隋云约个时间对齐 Skill 分发策略，否则两边的对接会返工

### 4. 「本月目标」不够量化

- 「架构调整成通用 Agent 和业务 SKILL、CLI 完全隔离」—— 怎么算完成？
- 「前端能够在申懂懂上跑起来」—— 跑通什么场景？
- **建议：** 加上可验收的标准，比如「完成 X 个接口的联调」「支持 Y 个 Skill 的挂载」

### 5. Claude Agent SDK 的依赖风险

- 整个通用 Agent 基于 Claude Agent SDK 构建，这是强依赖
- 如果后续 SDK 有 breaking change 或阿里云函数计算环境不兼容，影响大
- **建议：** 考虑做一层 SDK 抽象，不要直接耦合到 Claude SDK

---

## 💡 总体评价

思路对，技术选型合理，但文档完整度不够。当前更像内部讨论笔记，不是可评审、可执行的设计文档。建议尽快补齐接口定义和架构图，特别是跟老徐、隋云对接的部分要明确。

## 一、会话总结

### 1. 目标
定时任务系统两引擎（openclaw + claude）的创建/存储/调度/执行/呈现路径分叉。重构目标：收敛为**单一真相源**，同时保留两引擎执行能力。

### 2. 锁定架构（5 点，已与代码核对一致）

| # | 维度 | 方案 |
|---|---|---|
| 1 | 创建 | 统一经 `ScheduledTaskService`（主进程，唯一创建真相源）。NL 调用方式略有不同：claude NL 主进程内直调；openclaw NL 经 runtime 内置 `cron` 工具 → HostApi `case:'cron'` → service；MyTask 经 HTTP 路由 → service |
| 2 | 存储 | SQLite 统一表 `scheduled_tasks`（定义+调度状态）+ `scheduled_task_runs`（运行记录，新建），取代 `jobs.json` / `definitions.json` / 各自 jsonl |
| 3 | 调度 | 单一主进程调度器（泛化 `ClaudeTaskScheduler`），openclaw 不再靠 Gateway 计时 |
| 4 | 执行 | 经 `EngineAdapter.sendMessage`（`electron/engines/types.ts:50`）——已是统一接口；`getAdapterForSession(engineType)` 选 openclaw/claude adapter，引擎差异封在 adapter 内 |
| 5 | 执行=发到聊天 | 执行器到点调 `runMainChatSend({sessionKey: 任务会话, message: 任务 prompt, engineType, systemPromptAppend})` → agent 跑、流式回 dated 会话。"发到聊天"**就是执行本身**，同一步，不是先后 |

### 3. 现状核实结论：现状即 Option B（两引擎 NL 直接建、无 modal、无确认）

- **claude NL**：`create_claude_scheduled_task` → `service.createTask`（`sto-plugin/claude/claude-scheduled-task-tool/tools.ts:239`）→ `definitions.json`。
- **openclaw NL**：用 openclaw runtime **内置 `cron` 工具**（已从 `tools.deny` 移除，`openclaw-auth.ts:1643`，"so local cron creation is possible again"）→ HostApi IPC `case 'cron' action:'create'`（`ipc-handlers.ts:525`）→ `cron.add` → Gateway `jobs.json`。**不是**插件那个被 deny 的 `create_scheduled_task` 工具（那是废弃遗留）。
- **confirmation→modal 链全死**：`Chat/index.tsx:56` 调 `useBuiltinToolListener()` 不传参 → handler 恒空 → modal 从不开。

> 两个曾错判（已纠正）：① modal 从不开（不是"→modal→Gateway"）；② openclaw NL 能建任务（走内置 cron 工具，非插件工具），只盯着插件被 deny 的工具会漏判。

### 6. 已锁决定

- **表名**：`scheduled_tasks` / `scheduled_task_runs`（带 d，对齐现有 `session_type='scheduled_task'` 枚举 + `ScheduledTaskService`，零改动）。> 用户写 `schedule_task`（无 d），按"沿用现有枚举名"理解为带 d；若坚持无 d，需改表名/迁移 `0005`/索引名/表模型文件名约 20 处——见"待定 1"。
- **sessionKey 前缀**：沿用 `agent:..:cron:id`（openclaw）/ `claude-task:id`（claude），不收敛为单一 `scheduled-task:` 前缀（与 P5 line 299 一致）。
- **`deliver`**：执行器复用交互 send 默认，不特殊设（已写进 P3）。openclaw `chat.send` 照常跑 agent turn；claude adapter 本不读 deliver。QA 验证 turn 实际触发。
- **插件交互模式**：Option B（两引擎直接建、无 modal），仅后端 create 收敛到 `ScheduledTaskService`。

### 7. 待定（不阻塞 Phase 0/1，到对应 Phase 再决）

1. **表名拼法**：`scheduled_tasks`（带 d，推荐，零改动）vs `schedule_task`（无 d，约 20 处改名）。需用户拍板。
2. **P5 line 296 session_type 收敛**：是否把 `cron`/`claude_task` 收敛为单一 `scheduled_task`？若收敛，`agent:..:cron:*` key 的 inferred type 变 `scheduled_task`（key 前缀仍留）；若不收敛，保留双类型 + 删仅历史回放用的 `scheduled-task:{taskId}` 虚拟聚合 key/枚举值。影响红点/侧栏迁移，Phase 5 前定。

### 8. 收益
任务会话 = 普通聊天会话（同一 `sessionKey`，经 `catalog_sessions.task_id` + `session_engine_bindings` 绑定任务）。执行结果按普通聊天流式进 UI——这是杀掉 `scheduled-task-stream-unification.md` G1–G6（后台流式丢失/卡 loading/无红点/base·dated sessionKey 不一致）的根，不用另写呈现。

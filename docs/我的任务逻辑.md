# 我的任务逻辑改造

## 背景

当前 MyTask 页面同时消费两套数据源：
- **云端任务**：`useScheduledTasksStore` → `/api/scheduled-tasks`（Python FastAPI）
- **本地任务**：`useCronStore` → `/api/cron/jobs`（Gateway）

改造后 MyTask 只保留**本地任务**（含/不含工作流），CRUD 全部走 gateway API，与 Cron 页面完全一致。唯一差异是创建时可选择工作流，选择后描述框自动填充 `"帮我执行 id 为：xxx 的工作流 【工作流name】"` 并 disabled。

## Task 1: 简化 types.ts

**文件**: `sto-claw/src/pages/MyTask/types.ts`

### 定时任务类型改动：
- 移除 `TaskSource` 类型（不再有 cloud/local 区分）
- 从 `TaskViewModel` 移除字段：`source`、`unread`、`taskId`（保留 `id` 即可）
- 保留字段：`id`、`name`、`description`、`cronExpr`、`enabled`、`nextRunAt`、`workflowName`、`workflowCode`、`createdAt`、`updatedAt`、`agentId`
- 新增字段：`engineType: 'openclaw' | 'claude'`（来自 ManagedLocalTask）

### 执行记录类型改动：
- 移除 `TaskType` 类型（不再有 normal/workflow 区分，全部为工作流）
- 从 `ExecutionRecord` 移除字段：`taskType`、`taskId`、`triggerMethod`
- 保留字段：`id`、`taskName`（即工作流名称，从 my-workflow 映射）、`status`、`workflowName`、`startTime`、`duration`、`durationMs`、`failReason`
- `RecordStatus` 保留不变（`running` / `success` / `failed`），后端 workflow_run 的 SUCCEEDED/FAILED/RUNNING 映射到前端
- 保留 `TaskView`、`StatusCounts`、`RecommendTask`

## Task 2: 重写 api.ts

**文件**: `sto-claw/src/pages/MyTask/api.ts`

### 工作流列表 API：
- `fetchWorkflows()` 改为调用 `GET /api/my-tasks/agent/v1/my-workflow`（GET 请求，不分页）
- 返回类型保持 `WorkflowOption[]`

### 执行记录 API（全部重写）：
- **移除** `fetchExecutionRecords()` 及其所有相关类型（`BackendTaskRun`、`BackendTaskRunPageResponse`、`mapToExecutionRecord`、`formatDuration`、`formatTime`）
- **新增** `fetchWorkflowRuns()` 调用 `GET /api/my-tasks/agent/v1/my-workflow-runs`
- 返回类型 `WorkflowRunRecord[]`，字段：
  ```typescript
  interface WorkflowRunRecord {
    id: string;          // run_id
    workflowId: string;  // workflow 业务 ID
    workflowName: string; // 工作流名称（后端 join 返回）
    status: string;      // RUNNING/SUCCEEDED/FAILED 等
    startedAt: string;   // ISO 时间
    completedAt: string | null;
    error: string | null;
  }
  ```
- 前端在 store 层将 `WorkflowRunRecord` 映射为 `ExecutionRecord`（status 映射、耗时计算等）

## Task 6: 重写 index.tsx（核心）

**文件**: `sto-claw/src/pages/MyTask/index.tsx`

### 6.1 移除的依赖和逻辑

- 初始化只调 `fetchJobs()` + `fetchWorkflows()`

### 6.3 操作回调对齐 Cron 页面

| 操作 | 实现方式（与 Cron 页面 handleTrigger 一致） |
|------|------------------------------------------|
| **立即执行** `handleTrigger` | `triggerJob(id, engineType)` → `navigateToMainChatHome()` 跳转对话页 → `switchSession(sessionKey)` → `loadSessions()` |
| **启用/暂停** `handleToggle` | `toggleJob(id, enabled, engineType)` |
| **删除** `handleDelete` | `deleteJob(id, engineType)` |
| **创建/编辑** `handleSave` | `createJob({engineType, payload})` / `updateJob(id, {engineType, payload})`，与 Cron 的 handleSave 逻辑一致 |

### 6.4 handleTrigger 具体逻辑（复制 Cron 页面）
```typescript
const handleTrigger = useCallback(
  async (task: TaskViewModel) => {
    try {
      const result = await triggerJob(task.id, task.engineType);
      if (task.engineType === 'claude' && result && 'sessionKey' in result) {
        navigateToMainChatHome(navigate, location.pathname, () => {
          useChatStore.getState().switchSession(result.sessionKey);
        });
        void useChatStore.getState().loadSessions();
      } else {
        const sessionKey = `agent:${task.agentId ?? 'main'}:cron:${task.id}`;
        navigateToMainChatHome(navigate, location.pathname, () => {
          useChatStore.getState().switchSession(sessionKey);
        });
        void useChatStore.getState().loadSessions();
      }
      toast.success('测试运行已触发');
    } catch (err) {
      toast.error(String(err));
    }
  },
  [triggerJob, navigate, location.pathname]
);
```

### 6.5 handleSave 逻辑
- 引入 `useAgentsStore` + `resolvePreferredAgentByEngine`（同 Cron 页面）
- 新建时根据 engineType 调 `createJob()`
- 编辑时根据 engineType 调 `updateJob()`
- 创建/编辑成功后调 `fetchJobs()` 刷新

### 6.6 执行记录视图改动
- 执行记录数据源从 `task_runs` 切换为 `workflow_run`（通过新的 `fetchWorkflowRuns` API）

- `RecordItem` 中移除 `taskType === 'workflow'` 条件判断和「工作流」标签（因为全部是工作流）
- `RecordDetailModal` 简化：移除「触发方式」行（无此字段），「关联工作流」始终显示 workflowName
- `constants.ts` 中移除 `RECORD_TYPE_OPTIONS`
- ViewTabs、RecordStatusNav、搜索/排序逻辑（TaskToolbar）、空状态（TaskEmptyState）、推荐任务添加（handleRecommendAdd）、确认删除弹窗（ConfirmDialog）保留不变

## Task 7: 后端新增 my-workflow 与 my-workflow-runs API

### 7.1 my-workflow（工作流列表）

**文件**: `memory-center/src/api/claw_api/v1/workflow_client.py`

- 新增 `GET /my-workflow` 端点
- 逻辑：调用 `svc.list_workflows_page(page=1, page_size=9999, created_by=user_code)` 获取当前用户所有工作流
- 返回格式（不分页）：
  ```json
  {
    "success": true,
    "data": [
      { "id": "xxx", "name": "工作流A", "description": "..." },
      ...
    ]
  }
  ```
- 原有的 `/workflows/page` 端点保持不变（其他地方可能还在用）

### 7.2 my-workflow-runs（执行记录）

**文件**: `memory-center/src/api/claw_api/v1/workflow_client.py` + `memory-center/src/repositories/workflow_repository.py`

- 新增 `GET /my-workflow-runs` 端点
- 逻辑：查询 `workflow_run` 表，按 `created_by = user_code` 过滤，join `workflow` 表获取工作流名称
- 排序：`started_at DESC`
- 支持可选查询参数：`status`（状态过滤）、`keyword`（按工作流名称模糊搜索）
- Repository 层新增 `list_user_runs(user_code, status=None, keyword=None, limit=200)` 方法
- 返回格式（不分页）：
  ```json
  {
    "success": true,
    "data": [
      {
        "id": "run-uuid",
        "workflowId": "wf-biz-id",
        "workflowName": "工作流A",
        "status": "SUCCEEDED",
        "startedAt": "2026-06-15T10:00:00",
        "completedAt": "2026-06-15T10:02:30",
        "error": null
      },
      ...
    ]
  }
  ```

# 工作流执行状态推送技术方案

> 方案 A：Gateway 轮询 + SSE 推送  
> 版本：v1.0  
> 创建日期：2026-06-05

---

## 一、背景与问题

### 1.1 当前现状

工作流执行系统当前为**纯执行链路**，存在以下问题：

1. **无推送机制**：后端执行工作流时，没有主动向客户端推送执行状态的通道
2. **与会话无关联**：工作流执行过程没有和模型会话创建 SSE 连接
3. **用户体验差**：用户提交工作流后无法实时了解执行进度，只能被动等待

### 1.2 需求目标

| 目标 | 描述 |
|------|------|
| 实时推送 | 工作流执行状态变更时，实时推送到用户会话中 |
| 进度可见 | 用户可以看到执行进度百分比、当前步骤等信息 |
| 结果交付 | 执行完成后，自动在会话中输出结果摘要和产物文件 |
| 异常通知 | 执行失败时，及时通知用户并说明原因 |

---

## 二、方案概述

### 2.1 推荐方案：Gateway 轮询 + SSE 推送

**核心思路：**

1. 在 Main Process 中创建 `WorkflowExecutionTracker` 服务
2. 执行工作流时，传入 `sessionKey` 和 `agentId` 参数
3. Tracker 服务启动轮询，定期查询后端执行状态
4. 通过 Gateway 的 `chat:message` 事件将状态推送到会话
5. 前端通过现有 SSE 通道接收消息，自动追加到聊天历史中

### 2.2 方案优势

| 优势 | 说明 |
|------|------|
| 复用现有通道 | 利用 Gateway 已有的 WebSocket 消息通道，前端无需改动 |
| 状态集中管理 | 轮询逻辑集中在 Main Process，多窗口/多会话共享状态 |
| 实时性好 | 2 秒轮询间隔，用户体验流畅 |
| 架构侵入小 | 不改变现有 Gateway 启动和管理逻辑 |

## 五、接口设计

### 5.1 工作流执行接口

**请求：**
```
POST /api/workflows/:id/execute
Content-Type: application/json

{
  "templateId": "cost-analysis-v1",
  "values": {
    "timeRange": "2026-05-01~2026-05-31",
    "dimensions": ["customer", "product"],
    "rules": ["mom_increase_20"]
  },
  "sessionKey": "agent:main:cron:job-123",
  "agentId": "main"
}
```

**响应：**
```json
{
  "executionId": "exec-20260605-001",
  "status": "pending",
  "createdAt": "2026-06-05T10:30:00Z",
  "estimatedDuration": 120
}
```

### 5.2 执行状态查询接口

**请求：**
```
GET /api/workflows/:id/status/:executionId
```

**响应：**
```json
{
  "executionId": "exec-20260605-001",
  "status": "running",
  "progress": 45,
  "currentStep": "数据计算中...",
  "startedAt": "2026-06-05T10:30:05Z",
  "result": null,
  "error": null
}
```

### 5.3 执行结果数据结构

```typescript
interface WorkflowResult {
  summary: string;           // 执行摘要
  kpis?: KpiItem[];          // 核心指标
  anomalies?: AnomalyItem[]; // 异常发现
  artifacts?: ArtifactItem[];// 产物文件
}

interface KpiItem {
  name: string;
  value: string | number;
  change?: number;           // 环比变化百分比
  changeType?: 'increase' | 'decrease';
}

interface AnomalyItem {
  type: string;
  description: string;
  severity: 'high' | 'medium' | 'low';
  affectedItems?: string[];
}

interface ArtifactItem {
  id: string;
  name: string;
  type: 'html' | 'xlsx' | 'pdf' | 'json';
  url: string;
  size?: number;
}
```

## 六、消息推送设计

### 6.1 推送消息类型

| 阶段 | 消息内容 | 消息类型 |
|------|----------|----------|
| 开始执行 | "已启动工作流执行，执行 ID: `xxx`" | assistant |
| 开始运行 | "🚀 工作流正在执行中..." | assistant |
| 进度更新 | "⏳ 执行进度：45%" | assistant |
| 执行完成 | "✅ 工作流执行完成" + 结果摘要 | assistant |
| 执行失败 | "❌ 工作流执行失败：错误信息" | system (isError) |

### 6.2 进度更新策略

| 条件 | 是否推送 |
|------|----------|
| 进度为 10 的倍数 | ✅ 推送 |
| 进度达到 100% | ✅ 推送 |
| 进度变化 < 10% | ❌ 跳过（避免刷屏） |

### 6.3 完成消息格式

```markdown
✅ **工作流执行完成**

[执行摘要]

📊 **核心指标**
- **指标 A**: 123,456 (+15%)
- **指标 B**: 78.9% (-2.3%)

⚠️ **异常发现**
- [HIGH] 客户 A 单量环比下降 45%
- [MEDIUM] 科目 B 金额异常波动

📎 **产物文件**
- [成本分析报告.html](https://...)
- [明细数据.xlsx](https://...)
```

## 七、超时与错误处理

### 7.1 超时策略

| 参数 | 值 | 说明 |
|------|-----|------|
| 轮询间隔 | 2000ms | 每 2 秒查询一次状态 |
| 最大轮询时长 | 10 分钟 | 超过 10 分钟视为超时 |
| 最大轮询次数 | 300 次 | 10 分钟 / 2 秒 = 300 次 |

**超时处理：**
- 停止轮询
- 发送超时消息到会话
- 清理 ExecutionSession

### 7.2 错误重试策略

| 错误类型 | 处理方式 |
|----------|----------|
| 网络错误 | 重试，最多 3 次 |
| 404 Not Found | 视为执行异常，发送错误消息 |
| 500 Server Error | 重试，最多 3 次 |
| 超时 | 发送超时消息，停止轮询 |

### 7.3 错误消息格式

```markdown
❌ **工作流执行失败**

**错误类型**: [错误类型]
**错误信息**: [详细描述]
**建议操作**: 
1. 检查工作流配置是否正确
2. 确认数据源是否可用
3. 联系管理员查看日志
```

## 八、资源管理

### 8.1 ExecutionSession 生命周期

```
创建 (执行开始)
    │
    ▼
活跃 (轮询中) ──────┐
    │              │
    │ 状态变更     │ 进度更新
    ▼              │
推送消息 ──────────┘
    │
    │ completed/failed/timeout
    ▼
清理 (从 Map 删除)
```

### 8.2 内存管理

| 措施 | 说明 |
|------|------|
| Map 存储 | 使用 `Map<executionId, ExecutionSession>` |
| 自动清理 | 执行完成/失败/超时后自动删除 |
| 应用退出 | 调用 `stopAll()` 清理所有会话 |
| 窗口关闭 | 可选：清理关联的会话跟踪 |

### 8.3 并发控制

| 场景 | 策略 |
|------|------|
| 同一工作流多次执行 | 每个 executionId 独立跟踪 |
| 多窗口同时执行 | 共享 Tracker 单例，统一轮询 |
| 窗口关闭 | 继续跟踪（执行是后端行为） |

## 十二、风险与缓解

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 后端 API 不可用 | 无法查询状态 | 重试机制 + 错误提示 |
| Gateway 连接断开 | 消息无法推送 | 监听连接状态，重连后补推 |
| 轮询频率过高 | 后端压力大 | 动态调整间隔，最小 2 秒 |
| 内存泄漏 | 长时间运行后内存增长 | 定期清理，设置最大跟踪数 |
| 多窗口状态不同步 | 用户体验不一致 | 共享 Tracker 单例 |

## 十三、未来扩展

### 13.1 可能的优化方向

1. **WebSocket 直连后端**：后端主动推送状态变更，无需轮询
2. **执行暂停/恢复**：支持用户手动暂停和恢复执行
3. **批量执行**：支持同时执行多个工作流
4. **执行历史**：持久化执行记录，支持回溯查看
5. **执行分析**：统计执行时长、成功率等指标

### 13.2 与定时任务的集成

工作流执行跟踪可与定时任务系统复用部分逻辑：
- 共享 `ScheduledTaskResultPoller` 的轮询机制
- 共享会话写入工具 `appendTriggerResultToSession`
- 共享结果缓存 `CloudResultCache`

# 修复 Chat `@ 群聊"误发/乱发钉钉消息问题

> 存档日期：2026-07-09
> 关联文档：`docs/指定钉钉联系人.md`（指定钉钉联系人创建与发送流程梳理）

## Context

在 Chat 页 `@ 一个群聊"并要求"总结群内容"时出现三个乱象：
1. 连续发送多条混乱的钉钉消息；
2. 发出 "hello world"/"测试消息"/"你好" 等无关占位内容；
3. 用户只想总结、并未要求发送，agent 却往该群发了消息。

根因（已代码确认）：
- 注入块 `buildDingTalkMentionSystemContext`（`shared/dingtalk-mention-context.ts:182-235`）的**规则 4**（`:212`）把任何 `@` 收件人框定为"默认代发"，且块内只给 send 命令、未告知 agent 可用 `dws chat message list`/`list-direct`/`list-all`/`search` 读取群/单聊历史（dws **有**读消息命令，此前"dws 无读消息命令"为误判）；
- 块内**预填了带 "你好" 占位符的可直接执行命令**（`buildSendCommandHints:76-99` + `buildDingTalkSendTextExample('你好'):53-55`），agent 经常照抄执行；
- 限流 `checkDingTalkSendRateLimit`（`dingtalk-send-guard.ts:145-159`）**只在发送成功时计 20s 窗口**（`recordDingTalkSendSuccess:161-167`），dws 实发但结果未被 `isSuccessfulDwsChatMessageSendResult` 识别时，agent 重试不被挡 → 连发。

目标：去掉"@ 默认代发"语义、消除可照抄的占位命令、限流改为"发起即计"，从 prompt 与硬兜底两层消除乱发。

已与用户确认：① 限流改"发起即计"（失败也占窗口，合法重试等 20s，可用 `--dry-run`）；② 意图判定走"改 prompt 规则"路径（不引入确定性关键词门控、不动 pending schema）。

## 改动一：注入块规则重写 + 占位命令模板化（prompt 层）

文件（两份镜像，规则 1–11 与 `buildSendCommandHints` 内容一致，改法相同）：
- `shared/dingtalk-mention-context.ts`
- `sto-plugin/openclaw/sto-dingtalk-send-guard/shared/dingtalk-mention-context.ts`

### 1a. 规则 4 / 规则 5 翻转语义（`:212-213`）

旧规则 4「对话 @ 场景默认是"代用户转发/发送消息"…不得先回答这个问题」→ 新规则 4：
```
4. **对话 @ 场景：@ 收件人仅表示用户已选定一个钉钉发送对象，不等于要求发送。** 只有当用户明确要求"发送/转发/通知/告诉/发给/推送给"该收件人时，才用 `dws chat message send` 发送。若用户是让你针对该收件人做总结、分析、查看、检索、回答等（未要求发送），**禁止发送**，直接在对话中回复用户；你可以读取钉钉群/单聊历史消息——群聊用 `dws chat message list --group <openConversationId>`、单聊用 `dws chat message list-direct --user <userId>`、按时间范围用 `dws chat message list-all --start ... --end ...`、按关键词用 `dws chat message search`（群 ID 用 `dws chat search --query` 查）。若用户要求总结群/会话内容，**先读取真实历史再总结**，**不要编造内容、不要发送任何占位/示例文本**。
```
旧规则 5 → 新规则 5（末尾加禁止照抄示例）：
```
5. 用户明确要求发送时，发送前可用 `--dry-run` 预览或与用户确认正文；若用户消息本身已是可直接发送的问候/问题/通知，直接发送原文即可。**禁止把本块下方的命令示例原样执行**——示例仅展示 `--text` 格式，占位符须替换为实际正文。
```

### 1b. 预填命令改为非可执行模板（`:53-55`、`:76-99`、`:229`）

- `buildDingTalkSendTextExample`（`:53`）：占位符 `'你好'` → `'<正文>'`，使 `--text` 产物为 `"<正文>\n\n---\n\n> *代发说明*"`（尖括号占位符约定上不可执行）。
- 示例引导句（`:229`）改为：
```
命令格式示例（仅展示 `--text` 写法与代发说明格式，**禁止原样执行**；发送时把 `<正文>` 占位符替换为实际内容）：
```
- `--title` 保留默认 `"消息"`（规则 6 本就允许无标题时用 `消息`，非尴尬内容）。

> 效果：现象 2 的"照抄你好"（机制 a）与现象 3 的"被强制发送"在 prompt 层消除；`--text` 格式丢失（机制 b）已有 `resolveDwsChatMessageSendTextFormatProblem` 拦截，无需改。

## 改动二：限流改"发起即计"（guard 硬兜底）

文件（两份镜像，改法相同；claude SDK 那份结构一致，照搬）：
- `sto-plugin/openclaw/sto-dingtalk-send-guard/dingtalk-send-guard.ts`
- `sto-plugin/claude/sto-dingtalk-send-guard/sdk/dingtalk-send-guard.ts`

### 2a. 新增发起时间戳 Map 与记录函数（紧邻 `lastSuccessAtByScope:122`）

```ts
const lastInitiatedAtByScope = new Map<string, number>();

export function recordDingTalkSendInitiate(
  sessionKey: string | undefined,
  category: DingTalkSendRateLimitCategory,
  now = Date.now(),
): void {
  lastInitiatedAtByScope.set(resolveRateLimitScope(sessionKey, category), now);
}
```

### 2b. `checkDingTalkSendRateLimit`（`:145-159`）改判据为 max(发起, 成功)

```ts
const lastInitiated = lastInitiatedAtByScope.get(scope);
const lastSuccess = lastSuccessAtByScope.get(scope);
const last = lastInitiated != null && lastSuccess != null
  ? Math.max(lastInitiated, lastSuccess)
  : (lastInitiated ?? lastSuccess);
if (last != null && now - last < DINGTALK_SEND_MIN_INTERVAL_MS) {
  return { allowed: false, retryAfterMs: DINGTALK_SEND_MIN_INTERVAL_MS - (now - last) };
}
```
（保留 `lastSuccessAtByScope` 与 `recordDingTalkSendSuccess` 作为兜底，不删——after-hook 继续调，无害。）

### 2c. `evaluateDingTalkSendGuard`（`:217-263`）放行时记录发起

在 `checkDingTalkSendRateLimit` 返回 allowed 之后、`rememberPendingDingTalkSend` 旁边，加：
```ts
recordDingTalkSendInitiate(input.sessionKey, category, input.now);
```
（与现有 `rememberPendingDingTalkSend` 同处，保持 evaluate 已有的副作用模式。）

### 2d. `resetDingTalkSendRateLimitForTests`（`:128-131`）加清 `lastInitiatedAtByScope`

### 2e. after-hook 不动

`handleDingTalkSendGuardAfter`（`:265-291`）保持现状（仍调 `recordDingTalkSendSuccess`，作为成功兜底；pending map 清理不变）。

> 效果：现象 1 的连发被硬挡——放行即记时间戳，20s 内任何第二次 `dws chat message send`（含失败重试、示例+总结双发）都被拦。`--dry-run` 仍在 `isDwsChatMessageSendDryRun` 处提前放行、不计窗口。代价：一次会话内 `@ 两人各发一条` 的第二条要等 20s（用户已接受此权衡）。

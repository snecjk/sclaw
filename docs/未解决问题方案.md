## 三、P0 问题方案

### 问题 #6 / P0-6: Main Agent 返回 401 无错误体

**问题描述**: 调用 Main Agent 发送消息时接口直接返回 `401 status code (no body)`，无错误内容，输入框下方红字报错，会话无法继续。

**影响范围**: 所有调用 Main Agent (qwen3.7-max) 的用户

**根因分析**:
- SSO Token 过期或未正确注入到请求中
- 后端鉴权失败时未返回标准错误格式（body 为空）
- 前端未对 401 状态码做特殊处理
- 与运营问题 #8/#9（权限变更后旧 token 不刷新）同根因

**方案选项**:

| 方案 | 工作量 | 说明 |
|------|--------|------|
| A. 前端拦截 401 自动重新登录 | 1-2天 | 用户体验好，检测到 401 自动弹出登录 |
| B. 后端补全 401 错误体 | 0.5天 | 快速方案，返回 `{code, message}` 格式 |
| C. Token 自动刷新机制 | 2-3天 | 根本解决，在过期前主动刷新 token |

**推荐方案**: C + A 组合
- 短期：方案 B 快速止血（后端补全错误信息）
- 中期：方案 A 前端拦截 401 自动重新登录
- 长期：方案 C 建立 token 自动刷新机制，与权限刷新联动

**涉及代码**:
- `electron/utils/sto-memory-api-auth.ts` — token 管理
- `src/lib/api-client.ts` — HTTP 请求拦截器
- `electron/services/auth-setup-orchestrator.ts` — 认证流程
- `src/lib/error-model.ts` — 错误模型

### 问题 #7 / P0-5: 内置模型路由错误

**问题描述**: 切换到「内置」模型 qwen3.7-max 后，Agent 回复报错 `Unknown model: custom-sto/qwen3.7-max`，会话直接终止。

**影响范围**: 所有选「内置 qwen3.7-max」模型的用户

**根因分析**:
- 前端展示 `qwen3.7-max`（内置），后端却路由到 `custom-sto/qwen3.7-max`
- 模型注册表缺条目或前端 model id 映射错误
- 错误信息直接暴露 `openclaw logs --follow` 命令，不适合终端用户

**方案选项**:

| 方案 | 工作量 | 说明 |
|------|--------|------|
| A. 后端补注册模型 | 0.5天 | 在模型注册表中添加 `custom-sto/qwen3.7-max` 条目 |
| B. 前端修正 model id 映射 | 0.5天 | 修正前端传给后端的 model id 格式 |
| C. 统一模型 ID 管理 | 2-3天 | 建立模型注册中心，前后端共享模型 ID 映射 |

**推荐方案**: A 快速修复 + C 长期治理
- 短期：方案 A 或 B 任选其一即可修复
- 长期：方案 C 建立统一的模型 ID 管理机制

**涉及代码**:
- `electron/services/providers/provider-store.ts` — 模型存储
- `electron/services/providers/provider-migration.ts` — 模型迁移
- `electron/utils/openclaw-model.ts` — 模型工具
- `src/lib/chat-model-options.ts` — 模型选项

### 问题 #10 / P0-1: 网关连接超时

**问题描述**: 客户端「网关连接中」长时间不就绪，输入框灰显「网关未连接…」无法发送消息，网关连接超时。

**影响范围**: 所有等待网关连接的用户

**根因分析**:
- Gateway 进程启动失败（端口 18789）
- 端口被占用或旧进程残留
- 启动超时阈值设置不合理（`waitForGatewayReady` ~60s）
- Gateway 进程异常退出未自动恢复
- Windows 上进程启动慢

**方案选项**:

| 方案 | 工作量 | 说明 |
|------|--------|------|
| A. 连接超 30s 显示失败 + 重试入口 | 1天 | 明确失败状态，提供重试按钮 |
| B. Main 暴露 `gateway:restart` 通道 | 0.5天 | 渲染层可触发重启 |
| C. 失败自动重试 2-3 次 | 1天 | 减少用户手动操作 |
| D. Windows 首启增加健康检查日志 | 0.5天 | 便于排查 Windows 特有问题 |

**推荐方案**: A + B + C 组合
- 短期：方案 A 明确失败状态 + 方案 C 自动重试
- 中期：方案 B 暴露重启通道 + 方案 D 增加日志

**涉及代码**:
- `electron/gateway/startup-orchestrator.ts` — 启动编排
- `electron/gateway/lifecycle-controller.ts` — 生命周期管理
- `electron/gateway/connection-monitor.ts` — 连接监控
- `electron/gateway/state.ts` — 网关状态
- `electron/gateway/ws-client.ts` — WebSocket 客户端
- `src/stores/gateway.ts` — 网关 Store

### W-02: 安装包更新后模型配置丢失

**推荐方案**:

**预估**: 1-2天

### W-03 / P0-3: 工作流执行完成后自动又发消息

**问题描述**: 工作流执行完成后，自动再发一条消息并再次执行。

**根因分析**:
- `applyWorkflowRunStarted` 追加本地 turn + 启动 tracker
- `message-queue.ts` 的 `createAutoSendWatcher` 在 workflow 路径可能再次 `sendMessage`
- 完成态未清理 pending/队列或 completion 触发二次 send

**推荐方案**:
1. 启动后立即 `clearPendingWorkflow()` + runId 防重入
2. workflow 路径不走 Gateway `sendMessage`
3. completion 只更新卡片
4. idempotencyKey 去重

**涉及代码**:
- `src/lib/workflow-run-started.ts`
- `src/hooks/use-workflow-send.ts`
- `src/stores/message-queue.ts`
- `src/stores/chat/runtime-send-actions.ts`

**预估**: 2-3天

---

### W-04 / P0-4: 工作流取消后仍在执行

**问题描述**: 用户取消工作流后，后端仍在跑。

**根因分析**:
- `workflow:stopTracking` 仅停前端轮询
- `isWorkflowCancelIntent` 只 `clearPendingWorkflow()`，未调后端 cancel

**推荐方案**:
1. 调后端 cancel API
2. UI：stopTracking + cancel + 卡片标 `cancelled`
3. 忽略已取消 runId 的 poll 事件

**涉及代码**:
- `electron/main/services/workflow-execution-tracker.ts`
- `src/hooks/use-workflow-send.ts`
- workflow API

**预估**: 1-2天（依赖后端 cancel 接口）

### 问题 #12 / P0-2: 文件预览路径错误 ENOENT

**问题描述**: 点击预览生成文件，右侧产物面板报 `ENOENT: no such file or directory`。

**影响范围**: 预览 .claw-output 下文件的用户

**根因分析**:
- 双重路径 bug：路径丢 home 前缀（`/.stoclaw` 应为 `~/.stoclaw`）
- 扩展名被截断（实际 `.tsv`，预览却开 `.ts`）
- `resolveWorkspaceFilePath` 支持 `~` 但不处理 `/.stoclaw`
- `PREVIEWABLE_FILE_EXTS` 正则可能短匹配优先

**推荐方案**:
1. `/.stoclaw`、`./.claw-output` 补全为 `~/.stoclaw/...`
2. 扩展名最长后缀优先（`tsv` > `ts`）
3. 预览前 fuzzy 匹配（`.ts` 不存在试 `.tsv`）
4. 统一 `preview://` 点击处理

**涉及代码**:
- `src/pages/Chat/message-utils.ts`
- `electron/api/routes/files.ts`
- `src/pages/Chat/ChatMessage.tsx`

**预估**: 1-2天

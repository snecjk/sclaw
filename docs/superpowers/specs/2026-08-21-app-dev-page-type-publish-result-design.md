# 开发应用 Site / Assets 发布结果设计

日期：2026-08-21  
状态：已确认设计

## 1. 背景

开发应用在创建云端 `code-application` 时通过 `pageType` 区分两种类型：

- `site`：独立站点，平台提供固定域名；每次成功发布后，固定域名指向最新发布。
- `assets`：静态资源应用；每次成功发布产生一条发布记录及其对应的 OSS 产物，并可在后续申请自定义域名。

两种类型共享创建后的全部开发与发布执行能力。差异仅出现在应用身份提示，以及发布成功后的结果解释和管理入口。

## 2. 已确认的产品规则

1. 创建应用时必须选择 `pageType`，默认值为 `site`。
2. 创建、开发、AI 对话、本地预览、代码提交、发布参数、发布请求和状态轮询全部共享。
3. 不为两种类型维护两套发布流程、发布 Hook 或后端路由。
4. 工作台需要持续显示当前应用是 `Site` 还是 `Assets`。
5. `site` 发布成功后只向用户展示固定域名，不暴露 OSS 产物地址。
6. `site` 固定域名始终指向最新一次成功发布。
7. `site` 当前不提供历史发布记录、历史产物查看或回滚；这些属于后续能力。
8. `assets` 发布成功后展示本次发布记录、发布版本及对应 OSS 产物地址。
9. `assets` 可以申请自定义域名；自定义域名入口属于发布后的管理能力，不改变发布执行链路。
10. 应用广场卡片、分组和筛选不在本次范围内。

## 3. 设计原则

### 3.1 单一发布流水线

现有 `useStoAppDeploy`、`runStoAppDeployFlow`、Host API 发布路由和 `sai-cli policy code-deploy` 调用保持统一。`pageType` 不参与发布前的分支判断，也不改变代码推送、部署创建或轮询行为。

```text
统一代码提交
  → 统一创建部署
  → 统一轮询部署状态
  → SUCCESS
  → 根据 pageType 解释并展示结果
      ├─ site: 固定域名
      └─ assets: 版本 + OSS 产物 + 后续域名管理
```

### 3.2 权威数据来源

云端 `code-application.pageType` 是应用类型的权威来源。创建请求中的值仅负责初始化；本地 marker 或 workspace binding 可以缓存该值，用于离线显示，但不得覆盖云端返回值。

兼容规则：云端旧数据缺少 `pageType` 时按 `site` 处理。这与创建默认值一致，也避免旧应用突然进入 Assets 展示路径。

### 3.3 结果层隔离

保留一个统一的发布控制器与状态面板，在成功态内部使用两个小型结果视图：

- `SitePublishSuccess`：负责固定域名展示、访问和复制。
- `AssetsPublishSuccess`：负责版本、OSS 产物地址、复制和自定义域名入口。

失败、取消、超时和进行中状态继续使用现有统一视图，不按类型分叉。

## 4. 数据模型

### 4.1 应用类型

`CodeApplicationRecord` 增加：

```ts
type CodeApplicationPageType = 'site' | 'assets';

interface CodeApplicationRecord {
  // existing fields...
  pageType: CodeApplicationPageType;
}
```

解析云端数据时只接受 `site` 和 `assets`；缺失或未知值归一化为 `site`。`DevAppSummary`、Renderer API DTO 和工作台状态需要透传该字段。

### 4.2 发布结果

现有部署响应中的 `resourcePages` 是发布后资源信息的原始载体。客户端增加一个纯数据归一化层，将服务端响应转换为稳定的展示模型，UI 不直接遍历未知结构：

```ts
type PublishSuccessPresentation =
  | {
      pageType: 'site';
      fixedUrl: string;
    }
  | {
      pageType: 'assets';
      version: string;
      artifactUrl: string;
      customDomain?: string;
    };
```

字段提取优先使用服务端明确返回的标准字段；`resourcePages` 的具体字段映射在实施前以当前 CLI schema/真实响应固化为解析器测试样例。解析失败不能把内部对象直接展示给用户。

发布 Job 需要保存成功响应归一化所需的数据，避免轮询结束后只留下 `status/deploymentId` 而丢失资源地址。

## 5. 工作台交互

### 5.1 类型标识

工作台标题中的应用名称旁显示只读标签：

- `Site`
- `Assets`

标签只用于身份提示，不改变编辑器、预览、AI 对话或发布按钮行为。页面类型加载期间不闪烁错误类型；可以先不显示，待云端应用详情解析完成后再出现。

### 5.2 发布前与发布中

两类应用完全复用现有发布弹窗：环境、可选部署版本、提交代码、发起部署、进度轮询和错误回填 AI 均不变。

### 5.3 Site 成功结果

成功面板展示：

- 发布成功状态；
- 固定访问域名；
- “访问站点”操作；
- “复制地址”操作；
- “再次发布”操作。

不展示 OSS 地址、资源版本列表、历史发布记录或回滚入口。

### 5.4 Assets 成功结果

成功面板展示：

- 发布成功状态；
- 本次发布版本；
- 本次 OSS 产物地址；
- “复制产物地址”操作；
- “申请自定义域名”入口；
- “再次发布”操作。

发布记录使用与现有部署状态相同的数据来源和查询能力，不新建第二套发布服务。若发布记录列表不在当前工作台数据中，则通过现有 code-deploy 查询能力扩展读取，而不是建立 Assets 专用协议。

## 6. 错误与降级

- `pageType` 缺失或未知：按 `site` 展示并记录诊断日志。
- 发布成功但 Site 固定域名缺失：保留成功状态，提示“发布成功，访问地址暂未返回”，允许刷新状态；不回退展示 OSS 地址。
- 发布成功但 Assets 产物地址缺失：保留成功状态，提示“发布成功，产物信息暂未返回”，允许刷新状态。
- Assets 版本缺失：显示服务端返回的部署标识作为诊断信息，但不伪造业务版本号。
- 自定义域名能力不可用：隐藏或禁用入口并给出明确说明，不影响产物访问。
- 发布失败、取消或超时：继续使用统一错误提示和“填入 AI 会话”能力。

## 7. 代码边界

预计涉及：

- `shared/code-application-catalog.ts`：解析并归一化 `pageType`。
- `electron/services/app-dev-service.ts`：将云端类型透传到开发应用摘要。
- `src/lib/app-dev-api.ts`：Renderer DTO 增加类型。
- 开发工作台容器：加载类型并显示标签。
- `shared/code-deploy-status.ts` 或独立纯函数模块：归一化成功结果中的站点/产物信息。
- `src/components/app-dev/StoAppDeployControl.tsx`：成功态按类型选择结果视图。
- 新增 Site/Assets 成功结果小组件；发布 Hook、发布弹窗与 Host API 保持共用。

不应修改：

- Vite 开发服务器和预览逻辑；
- AI 对话与代码编辑链路；
- 代码推送协议；
- 发布请求和轮询的控制流；
- 应用广场的列表、卡片和分类。

## 8. 测试策略

1. 应用数据解析：`site/assets` 正确透传，缺失和未知值默认 `site`。
2. 工作台类型标签：两类应用分别显示正确标签，加载前不误显示。
3. 发布流程回归：相同参数下两类应用调用同一个发布函数，不产生类型专用请求。
4. Site 成功结果：展示固定域名和访问/复制操作，不出现 OSS 地址。
5. Assets 成功结果：展示版本、OSS 地址和自定义域名入口，不把产物误标为站点固定域名。
6. 资源字段缺失：成功状态保留，并展示可恢复提示。
7. 失败、超时和取消：两种类型继续走相同的统一错误界面。

## 9. 非目标与后续能力

本阶段不实现：

- Site 历史发布记录、历史产物或回滚；
- Assets 独立的发布 API、发布 Hook 或发布弹窗；
- 自定义域名申请的完整表单与服务端协议；本阶段只预留入口；
- 应用广场中的类型标签、筛选或分组；
- 两种类型不同的模板、开发环境或本地预览方式。

后续增加 Site 历史版本或 Assets 域名管理时，应扩展各自的成功结果/发布后管理组件，不应复制底层发布流水线。

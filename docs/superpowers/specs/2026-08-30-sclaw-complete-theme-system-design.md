# SClaw 完整浅深主题体系设计规范

日期：2026-08-30

状态：待审核

范围：覆盖所有活跃界面、独立窗口、受控预览和组件状态；浅色视觉完全冻结

## 1. 背景与问题定义

SClaw 已具备 `light | dark | system` 设置、根节点主题 class、全局 CSS 变量和部分 Surface 语义，但当前样式消费仍然分裂：

- 全局 `--sto-surface-*` 变量；
- Tailwind / shadcn 的 `bg-card`、`bg-secondary`、`bg-muted`；
- 业务组件中的 `dark:bg-*`、`dark:text-*`、`dark:border-*`；
- 页面或组件直接书写的十六进制、RGB、HSL 中性色；
- `globals.css`、`surfaces.ts` 和页面局部样式中的重复映射。

初步静态审计结果：

- 116 个活跃样式文件直接书写十六进制颜色；
- 1397 处六位十六进制颜色；
- 1172 处深色工具类；
- 59 个文件使用任意值形式的深色背景、文字、边框或阴影；
- 统一 `--sto-surface-*` 变量的消费只有 138 处。

因此，当前问题不是单张卡片取色不正确，而是多个主题来源同时拥有组件颜色。典型表现是普通内容卡片在深色画布中使用 `dark:bg-secondary`，形成不必要的亮色块；相似组件在不同页面也会得到不同的深色层级。

## 2. 目标

1. 建立唯一的浅深主题来源和可追踪的映射关系。
2. 覆盖所有活跃界面、所有窗口、受控 iframe 和所有组件状态。
3. 浅色模式的颜色、层级和视觉结果与改造前完全一致。
4. 深色模式采用中性黑灰、有限层级、弱边框和低对比交互面。
5. 普通描边卡片在深色模式与宿主画布融合，主要依靠弱边框区分。
6. 删除重复主题实现、页面级主题补丁、死样式和迁移完成后的兼容代码。
7. 用项目 Rules、静态守卫、单元测试和视觉矩阵防止主题再次分裂。

## 3. 非目标

- 不修改布局、尺寸、间距、字号或业务流程。
- 不修改依赖、lockfile、构建配置、构建脚本或 CI/CD。
- 不把照片、PPT 幻灯片、Word 纸张等保真内容强制反色。
- 不把第三方品牌色或数据可视化色机械改为中性色。
- 不引入新的样式框架或主题依赖。

## 4. 硬性约束

### 4.1 浅色冻结

浅色模式是本次迁移的视觉基线：

- 迁移只能把既有浅色值接入语义变量或组件配方；
- 不得因为“统一”而合并两个视觉上不同的既有浅色角色；
- 改造前后，同一稳定页面状态的浅色截图必须一致；
- 动态内容区域允许遮罩，但稳定区域不接受可见像素差异；
- 若语义合并会改变浅色结果，必须保留独立角色。

### 4.2 单一所有权

每一层只拥有一种职责：

```text
Palette 原始色板
  -> Semantic 语义角色与浅深映射
    -> Recipe 组件视觉配方
      -> Primitive / Business Consumer
```

- 原始中性色只能由 Palette 层拥有；
- 浅深映射只能由 Semantic 层拥有；
- 卡片、控件和浮层状态只能由 Recipe 层拥有；
- 业务页面只能选择语义角色或组件配方，不能重新解释主题。

### 4.3 项目内命名

主题实现统一使用 SClaw 自有语义。组件名、变量名、CSS class、CSS 变量、`data-*` 属性、注释、测试名称和运行产物不得包含外部产品名称或对应标签。

## 5. 文件与模块结构

主题结构保持最小，只新增两个生产 CSS 文件：

```text
src/styles/theme/
├── tokens.css        原始色板与 light / dark 语义映射
└── recipes.css       Card、Control、Overlay 配方及明确例外
```

职责如下：

### `tokens.css`

- 文件内按 Palette 和 Semantic 两个区块组织，不再为了概念分层增加文件；
- Palette 区块只保存原始色值，不包含组件名；
- 不被业务组件直接消费；
- 品牌色使用 `#FF6F00`；
- 功能色使用信息 `#4760FE`、成功 `#00B54B`、错误 `#FA3C3C`、警告 `#FAAD14`。
- Semantic 区块定义 Surface、Text、Icon、Border、Control、Status 的语义变量；
- `:root` 保存冻结后的浅色映射；
- `.dark` 只保存深色映射；
- Tailwind / shadcn 兼容变量只能作为语义变量的别名，不能成为第二套色板。

### `recipes.css`

- 定义可复用的组件配方；
- 配方只消费 Semantic 变量；
- 同时定义 default、hover、active、selected、focus、disabled、loading 和 error 状态；
- 业务组件不得再组合自己的深色 Surface。
- 例外紧邻实际配方登记，不为少量例外新建空洞抽象文件；
- 例外仅允许内容保真、第三方品牌和数据可视化颜色，并须包含用途、所有者和主题边界说明；
- 普通应用卡片、按钮、文字和边框不得登记为例外。

### 现有文件整理

- `src/styles/globals.css` 只保留 Tailwind 入口、主题文件引用、全局排版和必要通用工具类；
- `src/lib/surfaces.ts` 优先通过迁移消费者和删除重复导出缩减；除非确有独立职责，不把它机械拆成更多 TypeScript 文件；
- 无引用的 `src/styles/globals.old.css` 在证明无消费者后删除；
- 不新增主题 React 包装组件；现有基础组件只增加必要的视觉变体；
- 临时兼容别名只允许存在于当前迁移批次，并在该批次结束前删除。

## 6. 语义颜色映射

### 6.1 Surface 层级

| 语义角色 | 浅色映射 | 深色映射 | 用途 |
| --- | --- | --- | --- |
| Shell | 保持现值 `#EDEDED` | `#212121` | 应用壳、侧栏 |
| Canvas | 保持现值 `#FAFAFA` | `#0D0D0D` | 主内容画布 |
| Panel | 保持现值 `#FFFFFF` | `#181818` | 输入区、编辑器、内容承载面 |
| Inset | 保持各既有浅色角色 | `#212121` | 面板内部的嵌套区块 |
| Elevated | 保持现值 `#FFFFFF` | `#282828` | Dialog、Popover、Dropdown、Menu |
| Hover | 保持既有组件值 | 比默认 Surface 抬升一级 | Hover 状态 |
| Active / Selected | 保持既有组件值 | `#282828` | 选中、按下、当前项 |

浅色 `Inset` 和交互状态可能包含 `#FAFBFC`、`#F5F6F7`、`#F2F3F5`、`#E5E6EB` 等既有层级。迁移不得为了减少变量数量而改变这些现值。

### 6.2 文字与图标

| 语义角色 | 浅色映射 | 深色映射 |
| --- | --- | --- |
| Primary Text | `#1D2129` | `#DFDFDF` |
| Secondary Text | `#4E5969` | `rgba(255,255,255,.70)` |
| Tertiary Text | `#86909C` | `rgba(255,255,255,.50)` |
| Primary Icon | 继承主要文字语义 | `rgba(255,255,255,.90)` |
| Secondary Icon | 继承次要文字语义 | `rgba(255,255,255,.70)` |
| Tertiary Icon | 继承三级文字语义 | `rgba(255,255,255,.50)` |

普通正文不使用纯白。纯白仅用于品牌主按钮文字或确有高强调需求的内容。

### 6.3 边框与阴影

| 语义角色 | 浅色映射 | 深色映射 |
| --- | --- | --- |
| Border Light | 保持现值 | `rgba(255,255,255,.04)` |
| Border Default | 保持现值 `#E5E6EB` | `rgba(255,255,255,.08)` |
| Border Heavy | 保持现值 `#C9CDD4` | `rgba(255,255,255,.16)` |

- 深色阴影只使用中性黑，不带蓝色倾向；
- 普通卡片不依靠重阴影制造层级；
- 浮层允许使用中性黑阴影，但不得叠加蓝黑或彩色环境光；
- Focus 使用品牌 Ring，不通过高亮白边替代。

## 7. 卡片体系

所有卡片必须选择一个明确变体。

### 7.1 Flat Card

- 用于首页推荐、轻量入口、无复杂嵌套内容的普通卡片；
- 浅色保持白底和现有浅边框；
- 深色背景与宿主画布融合，配方背景为透明或宿主等价值；
- 深色默认使用 Border Default；
- Hover 时只提升到 Panel，并可使用 Border Heavy；
- 不使用常驻亮色块或重阴影。

### 7.2 Panel Card

- 用于表单、编辑器、聊天输入区和主要内容承载面；
- 浅色保持现有白色面板；
- 深色使用 Panel `#181818`；
- 是否有边框由既有浅色设计决定，深色不得自行增加高对比描边。

### 7.3 Inset Card

- 用于 Panel 内的参数块、详情行、预览信息块；
- 浅色保留当前浅灰层级；
- 深色使用 Inset `#212121`；
- 禁止在 Inset 中继续嵌套相同层级造成无效色块。

### 7.4 Elevated Card

- 用于 Dialog、Popover、Dropdown、Menu 和需要脱离文档流的浮层；
- 浅色保持白色及现有阴影；
- 深色使用 Elevated `#282828` 和中性黑阴影；
- 不用于普通列表卡片。

### 7.5 Status Card

- 用于成功、警告、错误、信息反馈；
- 基础结构继承上述四类之一；
- 状态色只用于图标、文字、边框或低透明度软背景；
- 深色不允许整块使用高饱和纯色。

## 8. 控件与浮层体系

按钮、输入框、搜索框、分段选择、排序触发器、图标底和开关共享 Control 语义：

- default：Control Surface + Default Border；
- hover：Surface 提升一级；
- active / selected：Elevated Surface，并强化文字或图标；
- focus：品牌 Ring；
- disabled：保持底色，降低文字与图标语义，不通过整体透明导致边界消失；
- loading：保持控件占位和背景层级稳定。

Dialog、Sheet、Popover、Dropdown、Tooltip 和 Toast 必须使用共享 Overlay 配方。业务页面不再维护自己的浮层背景、边框和阴影组合。

## 10. 内容预览策略

所有预览都必须声明主题策略。

### Adaptive

应用型 HTML、生成表格、Markdown、代码、文本和可重排内容使用 Adaptive：

- 接收父窗口解析后的主题；
- 表格、表头、表体、文字、边框、代码块和表单控件完整映射；
- 运行时切换主题不重建内容状态；
- 深色下不得出现白色常态 Surface 或浅色文字叠在白色单元格上。

### Fidelity

PPT、Word 纸张、图片和明确要求保留原稿颜色的内容使用 Fidelity：

- 外部画布、工具栏和加载状态适配主题；
- 文档纸张、幻灯片和图片本体保持原色；
- 不使用全局反色滤镜；
- 跨域内容无法注入时，至少同步 `color-scheme` 并保持外壳正确。

## 11. 代码整洁性规则

1. 业务组件不得直接书写中性原始色值。
2. 业务组件不得新增 Surface 用途的 `dark:bg-*`、`dark:border-*`、`dark:text-*` 任意覆盖。
3. 同一视觉配方只允许一个实现，页面专属导出在迁移完成后删除。
4. 兼容别名必须记录消费者，并在最后一个消费者迁移后立即删除。
5. 不以“临时兼容”为理由保留永久重复来源。
6. CSS 文件按职责组织；颜色映射、组件状态和业务布局不得混在同一模块。
7. 主题改造不得引入新的业务分支、事件、副作用或数据状态。
8. 遵守 React 19 规则，不新增无必要的 `useCallback`、`useMemo` 或 `React.memo`。
9. 不新增依赖，不修改工程化配置。
10. 注释解释语义或例外原因，不记录临时修补历史。
11. 不为主题新增 React 包装层、Context、Hook 或运行时映射；现有主题控制链路能满足需求时只调整 CSS 消费。
12. 生产样式最终净代码量原则上不增长：新增 Token 和 Recipe 必须由删除更多重复色值、`dark:*`、旧变量和页面专属配方抵消。
13. 测试和 Rules 不计入生产代码预算，但同样必须避免重复断言、超长快照和无行为价值的检查。
14. 每批迁移都记录生产代码增删行；若新增行多于删除行，必须说明不可合并的真实职责，否则继续精简。

- 唯一主题分层和文件所有权；
- 浅色冻结原则；
- 深色 Surface、Card、Text、Border 和 Control 映射；
- 卡片变体选择规则；
- 禁止的硬编码和页面级深色补丁；
- Adaptive / Fidelity 预览选择规则；
- 品牌色、状态色和数据色例外流程；
- 新组件双主题验收清单；
- 迁移后删除兼容代码的要求；
- 项目内命名约束。

当前 `.cursor/` 被 `.gitignore` 整体忽略。修改 `.gitignore` 时只放行 `.cursor/rules/` 和其中的 `.mdc` 规则文件，继续忽略个人设置、缓存和本地状态。

## 13. 迁移策略

迁移采用单向分批和直接切换方式；每批完成后不得再引入旧写法，也不保留新旧双轨实现。

### 阶段 0：冻结基线和清单

- 捕获核心路由的浅色稳定截图；
- 建立主题反模式清单和例外清单；
- 记录所有旧变量、兼容导出和消费者。

### 阶段 1：主题基础层

- 在两个文件中建立 Palette、Semantic 和 Recipe 三个职责区块；
- 将现有 Tailwind / shadcn 变量改为兼容别名；
- 增加浅色冻结、深色映射和对比度测试；
- 同批迁移首个真实消费者，避免新增无人消费的抽象。

### 阶段 2：卡片与首页

- 迁移共享 Card；
- 迁移首页 Flat Card、Skeleton 和 Loading Overlay；
- 验证普通卡片深色与画布融合；
- 删除首页专属重复 Surface，保证本批生产样式代码不净增长。

### 阶段 3：共享控件与浮层

- 迁移 Button、Input、Tabs、Select、Dropdown、Dialog、Popover、Tooltip、Toast；
- 固化所有交互状态；
- 删除页面自行复制的控件配方，不新增组件包装层。

### 阶段 4：业务页面

- 按首页/聊天、技能/连接器、任务/自动化、工作流、数据中心、设置/账户/渠道分批迁移；
- 每批执行浅色冻结验证和深色视觉矩阵；
- 每批删除已无消费者的旧变量和兼容导出，并记录生产代码增删行。

### 阶段 5：预览与独立窗口

- 完成 Adaptive / Fidelity 预览映射；
- 验证表格和生成内容；
- 验证 Sprite、浮窗、新窗口、系统主题和首帧背景。

### 阶段 6：最终清理

- 删除 `globals.old.css` 和无引用旧样式；
- 删除所有迁移兼容别名；
- 确认活跃消费者不存在未登记的原始中性色和页面级深色 Surface；
- 更新 Rules 和相关设计文档；
- 运行完整验证矩阵。

## 14. 测试与验证

### 14.1 自动化测试

1. Palette 测试：品牌色和功能色只有一个来源。
2. Semantic 测试：所有语义角色同时具备 light 和 dark 映射。
3. Light Freeze 测试：浅色 Surface、文字、边框和状态值与基线一致。
4. Card Recipe 测试：四类卡片及全部状态映射正确。
5. Contrast 测试：预定义文字/背景、图标/背景和边框/背景组合达到既定阈值。
6. Static Guard 测试：阻止业务组件新增原始中性色和页面级深色 Surface。
7. Exception 测试：所有例外有明确的类别和主题边界。
8. Preview 测试：Adaptive 表格可读，Fidelity 内容不被强制反色。
9. Appearance 测试：light、dark、system、跨窗口和 iframe 同步保持正确。

静态测试保护可观察的主题契约，不对设计文档或 Rules 文本做无意义的字符串快照。

### 14.2 视觉矩阵

每个核心路由至少验证：

- light default；
- dark default；
- hover / active / selected / focus / disabled；
- loading / empty / error；
- Dialog 或 Popover 打开；
- 窄窗口和正常窗口。

核心路由包括：首页、聊天、技能广场、连接器、自动化、任务、工作流、数据中心、设置、渠道、登录/Setup 和文件预览。

### 14.3 浅色冻结验证

- 改造前保存稳定区域截图；
- 改造后使用相同窗口、数据和路由重放；
- 动态文本、时间和网络数据使用遮罩；
- 稳定区域像素差异必须为零；
- 出现差异时先定位消费者，不通过扩大容差掩盖问题。

### 14.4 深色验收重点

- 主内容比侧栏更深；
- Flat Card 与宿主融合且边界可辨；
- Panel、Inset、Elevated 层级连续，不出现随机亮块；
- 正文、辅助文字和占位文字层级清晰；
- 阴影不带蓝色倾向；

## 15. 完成定义

只有同时满足以下条件才算完成：

1. 所有活跃界面均完成 light / dark / system 覆盖。
2. 浅色稳定区域与冻结基线没有可见差异。
3. 所有卡片均归入明确变体，并使用统一状态配方。
4. 活跃业务组件中不存在未登记的原始中性色。
5. 活跃业务组件中不存在页面级 Surface 深色补丁。
6. 兼容别名、旧变量、死样式和 `globals.old.css` 已清理。
7. Rules、主题文档和自动守卫保持一致。
8. 自动测试、CSS 解析和差异检查通过。
9. 真实 Electron 视觉矩阵完成并记录结果。
10. 未修改布局、尺寸、业务逻辑、依赖或工程配置。
11. 未新增主题 React 包装组件、运行时主题分支或长期兼容层。
12. 生产样式代码相对实施前不净增长；如存在不可避免的少量增长，已逐项说明对应的独立职责和删除替代方案。

## 16. 风险与控制

- **浅色回归**：基线先行，每批迁移后立即做浅色对比。
- **全局组件回归**：按组件家族分批迁移，不一次性机械替换。
- **角色过度合并**：任何会改变浅色现值的合并都被禁止。
- **兼容层永久化**：每个别名记录消费者并设置删除阶段。
- **抽象导致代码膨胀**：限制为两个主题 CSS 文件，不新增 React 包装层；每批比较增删行，新增必须由去重抵消。
- **保真内容误反色**：所有预览必须显式选择 Adaptive 或 Fidelity。
- **例外泛化**：例外只允许三类，并由静态守卫限制。
- **深色层级膨胀**：Surface 固定为 Canvas、Panel、Inset、Elevated 四级；业务页面不得新增第五级中性 Surface。
- **测试只看源码文本**：核心测试验证计算映射、组件行为和实际渲染结果，源码扫描只负责阻止反模式。

# 工作流运行结果抽屉单击交接设计

## 目标

工作流试运行结束后，用户点击成功通知中的“查看结果”，一次点击完成以下交互：关闭当前页面内的试运行抽屉，并打开同一 `runId` 的全局运行详情抽屉。用户不需要再次点击通知。

## 根因

页面内试运行由 `useDesignerTryRun` 和路由中的 `TestRunDrawer variant="trial"` 管理；完成通知由全局 `WorkflowCompletionNotifier` 管理，并渲染另一份 `TestRunDrawer variant="detail"`。

当前通知按钮直接打开全局详情。试运行抽屉仍打开时，同一次指针事件会让两个 Radix Sheet 的打开与关闭发生竞争，首次点击可能只关闭原抽屉，同时把刚打开的详情抽屉一并消解。

## 方案

新增端侧、进程内的运行结果抽屉交接协议，不改变 Main/Renderer 通信协议，也不修改前后端接口。

1. 全局完成通知收到“查看结果”点击后，发起包含 `runId` 的交接请求。
2. 当前页面如果有相同 `runId` 且正在显示的试运行抽屉，则认领请求并关闭试运行抽屉。
3. 页面状态确认关闭后回执交接完成；全局通知随后加载运行详情并打开详情抽屉。
4. 如果没有活动试运行抽屉，或活动抽屉属于其他 `runId`，请求不被认领，全局通知直接打开详情。
5. 同一请求只能完成一次，卸载页面或重复回执不得重复打开详情。

交接协议放在独立的小型模块中。它只负责一次性请求、认领和完成回调，不持有运行数据，也不成为新的抽屉状态源。试运行状态仍归 `useDesignerTryRun`，详情状态仍归 `WorkflowCompletionNotifier`。

## 状态顺序

活动试运行抽屉存在时：

`点击查看结果 → 请求被当前 runId 认领 → isDrawerOpen=false → React 提交关闭状态 → 回执 → 加载运行详情 → detail.open=true`

没有可认领抽屉时：

`点击查看结果 → 请求无人认领 → 立即加载运行详情 → detail.open=true`

这里不使用固定毫秒延时；打开详情依赖明确回执，避免动画时长或机器性能改变后再次出现双击问题。

## 异常与边界

- 仅相同 `runId` 的试运行抽屉可以认领请求，避免误关另一次运行。
- 如果页面在交接期间卸载，清理函数必须完成待处理回执，让全局详情仍能打开。
- 运行详情读取失败时沿用现有详情抽屉的错误状态，不恢复旧试运行抽屉。
- OS 通知触发的 `workflow:completion-open` 和页面内成功通知复用相同的详情打开入口。
- 本次不调整通知文案、试运行结果样式、运行数据模型或服务端行为。

## 测试

- 交接模块：相同 `runId` 可认领且只完成一次；不同 `runId` 不认领；监听器卸载后不残留。
- 页面试运行：抽屉打开且 `runId` 匹配时关闭抽屉，并在关闭状态提交后完成回执。
- 全局通知：有认领者时等待回执再打开详情；无认领者时单击直接打开；详情读取失败仍展示现有错误。

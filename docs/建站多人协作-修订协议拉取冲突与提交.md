# 常规建站多人协作：修订协议、本地拉取、冲突与提交


| 项 | 内容 |
| --- | --- |
| 状态 | P0 客户端已落地（拉取文件级应用、三路合并、冲突面板、merge continue）；云端修订列表 / created_by 仍待服务端 |
| 产品 | SClaw 建站工作台 + sai-cli `siteapp` / memory-center `/api/v1/site-apps*` |
| 范围 | 常规建站（云端 Site App）。用户不接触 Git 账号，仓库由**建站公共账号**落盘 |
| 不在范围 | 本地导入且自带 `git config` 的应用；给业务用户开通 GitLab；实时共编 / OT |


本文回答：没有个人 Git 时，多人如何拉最新、如何解冲突、解完如何再提交、提交记录记谁。Git 只是服务端落仓手段，协作真相是应用修订链。

---

## 1. 结论

- **用户只走 SSO + 提交 / 拉取。** 不 clone、不 push、不配 SSH。Git 写权限只在建站公共账号。
- **本地是工作副本，云端是一条 HEAD 修订链。** 本地 `.sto/workspace.json` 记下基线三元组：`baseRevisionId` / `baseCommitSha` / `baseSourceSha256`。
- **提交必须带基线。** 落后于 HEAD → `VERSION_CONFLICT` / `REMOTE_AHEAD`，禁止覆盖。
- **拉取按文件增量补丁。** 本地没改才自动应用；两边都改了走三路合并，禁止整包覆盖。
- **提交人记在修订表（SSO 工号 / 姓名），不从 Git 用户反查。** Git committer 永远是公共账号；`commitSha` 只给发布钉死。
- **冲突解决后的提交 = 普通提交，基线必须已是当前远端 HEAD。** 现有空实现 `merge continue` 要变成「确认无冲突 → 更新基线 → 允许再提交」。

现状已具备乐观锁推拉（`electron/services/code-collab-service.ts`）。缺口是：分叉时直接报错、拉取整目录替换、`continueCodeApplicationMerge` 抛错、提交记录只有本机 `.sto/push-history.json`。

## 2. 身份与职责


```

        │
        ▼

        │

        │
        ▼
建站公共 Git 账号                落仓：git commit，用户不可见、不开通
```

| 层 | 账号 | 用户可见 | 用途 |
| --- | --- | --- | --- |

## 3. 同步状态机

与现网 `CodeCollabStatusSummary.syncState` 对齐，补齐分叉后的动作。

| `syncState` | 含义 | 允许的操作 |
| --- | --- | --- |
| `unbound` | 未绑定 Site App | 首次提交时创建云端应用 |
| `synced` | 本地 == 基线 == 远端 HEAD | 编辑后变成 `local-changes` |
| `local-changes` | 远端没变，本地有改 | **提交**；不拉（拉了也会 no-op 覆盖） |
| `remote-ahead` | 本地干净，远端新了 | **拉取**；禁止直接提交 |
| `merge-required` | 两边都改了，或冲突未清 | **拉取并合并** → 解冲突 → **继续合并** → **提交** |
| `unknown` | 详情失败等 | 重试 status |

判定（相对本地基线）：

```
远端 == 基线 且 本地 == 基线  → synced
远端 == 基线 且 本地 != 基线  → local-changes
远端 != 基线 且 本地 == 基线  → remote-ahead
远端 != 基线 且 本地 != 基线  → merge-required
```

现网 `decideSourcePullAction` 已按这个四分。要改的是 `diverged` / `merge-required` 不再只报错，而是进入 §5。

## 4. 本地拉取更新

### 4.1 用户怎么用

工作台在已绑定云端应用时**常驻「拉取」**（给懂的人手动同步）。

普通用户只需点「提交」：

1. 提交前**自动先 pull**（对齐远端 / 尝试合并）。
2. 无冲突 → 继续 push，toast「已提交」或「已同步远端并提交」。
3. 有冲突 → 打开冲突面板，**不推送**；用户处理完后再点提交。

手动「拉取」行为不变：按 §3 判定后 `applied` / `merged` / `conflicts` / `local-ahead`。

### 4.2 增量补丁（相对基线，不是 git pack）

双方同一套文件摘要（现有 `sto-source-v1`：排序路径 + 内容 sha256 → `sourceSha256`）。

拉取时对比「本地基线清单」和「远端 HEAD 清单」：

| 路径 | 基线 | 远端 | 动作 |
| --- | --- | --- | --- |
| 有 | 相同 hash | 相同 | 不动 |
| 有 | 不同 | 远端新内容 | 覆盖该文件（仅 `remote-ahead`） |
| 无 | — | 有 | 新增 |
| 有 | 有 | 无 | 删除该路径 |
| `.sto/`、`.env`、密钥 | — | — | 永不从远端覆盖或删除 |

应用后重新计算工作区 `sourceSha256`，必须等于远端 HEAD。失败则回滚到拉取前工作区（先解到 staging 再替换变更路径，不要先删光再拷）。

**禁止**再对脏工作区做现网这种整目录删除（`applyArchiveToWorkspace` 会删掉除 `.sto` 外的全部文件）。干净的 `remote-ahead` 可以用「staging 替换变更路径」；`merge-required` 必须走 §5。

### 4.3 接口 / CLI

沿用现有：

- HTTP `GET /api/v1/site-apps/source/snapshot/{app_code}`
- `sai-cli siteapp source download --app_code ...`

建议补（可与全量 snapshot 并存，P1）：

- `GET /api/v1/site-apps/source/manifest/{app_code}` 返回 HEAD 文件清单
- 按路径拉单文件或 diff bundle

P0 没有 manifest 时：仍下全量 tar.gz，但**应用层按文件 diff 落地**，效果等同增量，只是传输还是整包。

### 4.4 本地要记下什么

`.sto/workspace.json` 拉取成功后更新基线。拉取过程中不要清掉未提交改动。`.sto/merge/`（§5.2）仅在进入合并时创建。

## 5. 冲突解决

### 5.1 何时算冲突

A、B 都基于 `rev1`。A 提交成功 → HEAD = `rev2`。B 本地有改动：

- B 再提交 → 服务端 `VERSION_CONFLICT`，客户端提示先拉取。
- B 点「拉取」→ 三路：`base = rev1`（本地基线），`ours = B 工作区`，`theirs = rev2`。

文件分类：

| 情况 | 处理 |
| --- | --- |
| 只 ours 改 | 保留本地 |
| 只 theirs 改 | 采用远端 |
| 两边改、文本可自动合 | 合入结果写入工作区 |
| 同一 hunk 冲突 | 标为冲突文件，进入 `merge-required` |
| 二进制 / 图片 / lock | 不自动合，用户选「用我的 / 用远端」 |
| 一方删、一方改 | 标冲突，用户选保留或删除 |

有任一未解决冲突 → 状态保持 `merge-required`，**禁止提交、禁止发布**。

全部自动合入且工作区无冲突标记 → 视为「已合并、待提交」：基线改记 `rev2`，`syncState = local-changes`，用户直接提交（§6）。不必再点「继续合并」。

### 5.2 合并工作区（本地，用户不可见 Git）

进入分叉拉取时写入：

```
.sto/merge/
  ours/          拉取前工作区快照（待合并的本地）
  theirs/        远端 HEAD 解压
  base/          本地基线对应的树（见下）
  conflicts.json 未解决路径列表
```

`base/` 来源优先级：

1. 本地若缓存了基线 snapshot（建议拉取成功时留下 `.sto/base-snapshot/`，只保留当前基线一版）。
2. 否则向云端按 `baseRevisionId` 取历史快照（需 `GET snapshot?revisionId=`；若云端暂无，P0 可退化为「无基线的两边合并」：同文件都改则一律当冲突，不猜测）。

冲突文件在工作区的呈现：

- 文本：标准冲突标记（`<<<<<<< Local` / `=======` / `>>>>>>> Remote`），便于对话里让模型改。
- 工作台同时给每个冲突文件三个动作：**用我的 / 用远端 / 打开对比**。不要把 GitLab MR 术语暴露给用户。

`.sto/merge/` 与 `.sto/` 一样不进源码包。

### 5.3 「继续合并」做什么（替换空实现）

现网 `POST /api/app-dev/sto-app/merge-continue` → `continueCodeApplicationMerge` 直接抛错。改为：

1. 扫描工作区：不得再有冲突标记；`conflicts.json` 必须为空或与磁盘一致。
2. 用户已选的「用我的 / 用远端」全部落地。
3. 把本地基线更新为**进入合并时的远端 HEAD**（`theirs` 的 `revisionId` / `commitSha` / `sourceSha256`）。
4. 写 `mergeParentRevisionId = 合并前的 baseRevisionId`（记录分叉点，供这次后续提交带上）。
5. 删除 `.sto/merge/`（或标 `resolved`）。
6. 返回「已继续合并，可以提交」。此时 `syncState` 应为 `local-changes`（工作区相对新基线仍有 ours 的改动）。

未解决冲突就点继续 → 明确报错，列出剩余路径。不要退回「请手动处理后再重新拉取」——再拉一次会冲掉正在解的文件。

### 5.4 产品文案

| 场景 | 文案 |
| --- | --- |
| 提交时远端已前进 | 远端有更新，请先拉取再提交 |
| 干净拉取成功 | 已拉取远端更新 |
| 自动合并成功 | 已合并远端更新，请检查后提交 |
| 有冲突 | 有 N 个文件需要处理：用我的 / 用远端 / 编辑 |
| 冲突未清就提交 | 还有未解决的冲突，无法提交 |
| 继续合并成功 | 冲突已处理，可以提交 |

## 6. 解决后的提交

解冲突不是另一次魔法推送，就是一次带新基线的普通提交。

```
合并完成（基线已是 rev2，工作区 = 合并结果）
        │
        ▼
用户点「提交」，填写说明（默认「合并远端更新」）
        │
        ▼
校验：无冲突标记；baseRevisionId == 云端 HEAD（rev2）
        │
        ▼
打包工作区 → source/commit
  revision_id              新 ULID
  revision_message         用户说明
  base_revision_id         rev2
  parent_revision_id       rev2
  merge_parent_revision_id 进入合并前的 rev1（若这次经历过 §5）
  source_sha256 / archive_* 与现网一致
        │
        ▼
服务端：公共账号 git commit
        SSO → created_by / created_by_name
        返回新 revisionId + commitSha
        │
        ▼
本地：基线改成新版本；清 mergeParentRevisionId
      本机 push-history 可写一条，但不能当多人时间线
```

若合并完成后、提交前，别人又推了 `rev3`：

- 这次提交会再次 `REMOTE_AHEAD`。
- 再走 §4 / §5，不要强制覆盖。
- 可以循环：拉 → 合 → 提交，直到基线追上 HEAD。

提交成功校验与现网相同：`status = ready`、`commitSha` 非空、三个摘要与本地一致。

## 7. 提交记录（多人可见）

Git 历史里 committer 都是公共账号，**不能当协作记录**。本机 `.sto/push-history.json` 只有这台电脑推过的最多 30 条，**不能当多人时间线**。

云端修订表（每次 `source/commit` 成功写入）：

```text
revisionId
commitSha                 公共账号落仓 SHA，发布钉死用
sourceSha256
message
created_by                SSO empCode
created_by_name           SSO realName
created_at
parent_revision_id
merge_parent_revision_id  可选
```

工作台「最近提交」改为拉云端列表，展示：

> 张三 · 改了首页 Banner · 14:02

`commitSha` 默认折叠。回滚 = 基于某条 `revisionId` **新建一条提交**，作者是点回滚的人，禁止本地 `git reset`。

需新增：

- HTTP `GET /api/v1/site-apps/{appCode}/source/revisions?limit=50`
- CLI `sai-cli siteapp revision list --app_code ...`

客户端 `GET /api/app-dev/sto-app/pushes` 在云端列表可用后改为代理修订列表；本机文件只作离线兜底。

## 8. 端到端例子


```
t0  A、B 都在 rev1，工作区干净
t1  A 改首页，提交「改 Banner」     → rev2，作者 A
t2  B 改列表页（尚未提交）
t3  B 点提交                        → REMOTE_AHEAD
t4  B 点拉取
      首页：只 theirs 改 → 采用 A 的 Banner
      列表：只 ours 改   → 保留 B
      无冲突 → 基线=rev2，状态=local-changes
t5  B 提交「改列表」                 → rev3，作者 B
      parent=rev2

另例：两人都改了 `src/pages/Home.tsx` 同一段
t4' B 拉取 → 该文件进冲突列表
     B 选「用我的」或改完冲突标记
t4'' 点「继续合并」                  → 基线=rev2
t5'  提交「合并远端并保留列表改动」   → rev3，作者 B
      merge_parent=rev1
```

## 10. 落地顺序

**P0 — 两个人不丢代码**

1. 脏工作区禁止整包覆盖；`remote-ahead` 可先仍下全量包，但按文件落地。
2. `diverged` 三路合并 + 冲突列表 + 打通 `merge continue`。
3. 解决后按 §6 普通提交（基线已前进）。
4. 修订表写 SSO `created_by` / `created_by_name`；工作台改为云端修订列表。

**P1**

5. manifest / 按文件传输。
6. 拉取成功缓存 `.sto/base-snapshot/`，减少「按旧 revision 下快照」。
7. 回滚 = 基于旧修订再提交。

**不做**

- 给建站用户开通 GitLab。
- 本地 clone 云端仓，或把 `.git` 打进源码包。
- 实时共编同一个文件。
- 用本机 `push-history` 或 `git log` 充当多人记录。

## 12. 本机 Host API 与本地文件

路由仍挂在 `electron/api/routes/app-dev.ts` 的 `/api/app-dev/sto-app/*`。

### 12.1 现有路由的行为变更

| 路由 | 现网 | 按本文 |
| --- | --- | --- |
| `GET /status` | 四分状态 | 额外返回 `conflicts[]`；有 `.sto/merge` 且未解决 → 强制 `merge-required` |
| `POST /pull` | diverged 抛错；整包覆盖 | 见 §13 返回 `action` |
| `POST /push` | 不查冲突标记 | 有未解决冲突或冲突标记 → 400；带上 `mergeParentRevisionId` |
| `POST /merge-continue` | 抛错 | §14 |
| `GET /pushes` | 本机 30 条 | 优先云端 revision list；失败再读本机 |

`status` 增补字段（向下兼容）：

```ts
{
  syncState: 'synced' | 'local-changes' | 'remote-ahead' | 'merge-required' | …,
  revisionId?: string,          // 本地基线
  remoteRevisionId?: string,    // 远端 HEAD
  mergeTheirsRevisionId?: string,
  conflicts?: Array<{ path: string; kind: 'text' | 'binary' | 'add-delete' }>
}
```

`POST /pull` 成功体：

```ts
{
  ok: true,
  output: string,
  json: {
    action: 'already-synced' | 'local-ahead' | 'applied' | 'merged' | 'conflicts',
    remote: { revisionId, commitSha, sourceSha256 },
    conflicts?: Array<{ path: string; kind: string }>
  }
}
```

工作台按 `action` toast：`applied` → 已拉取；`merged` → 已合并请检查后提交；`conflicts` → 打开冲突面板，不要报失败。

### 12.2 新增 Host API（冲突面板）

不必新开云端接口，只读本地 `.sto/merge`：

- `GET /api/app-dev/sto-app/conflicts?workspaceId=`
- `POST /api/app-dev/sto-app/conflicts/resolve`  
  body: `{ workspaceId, path, choice: 'ours' | 'theirs' }`  
  把该文件写成 ours 或 theirs 内容，并从 `conflicts.json` 去掉。全部清完后可自动等同一次 merge-continue，或仍让用户点「继续合并」。

### 12.3 `.sto/workspace.json`

现网字段保留，合并中多用来：

```json
{
  "version": 2,
  "workspacePath": "/…/app",
  "appCode": "app_…",
  "baseRevisionId": "rev1",
  "baseCommitSha": "…",
  "baseSourceSha256": "…",
  "mergeParentRevisionId": null
}
```

进入分叉拉取、尚未 continue 时：**不要**把 `baseRevisionId` 提前改成 theirs。基线仍是合并前的 `rev1`，否则三路会丢 base。continue / 自动合入成功后再把基线写成 theirs，并把 `mergeParentRevisionId` 写成旧基线。

### 12.4 `.sto/merge/state.json`

```json
{
  "version": 1,
  "oursBaseRevisionId": "rev1",
  "theirsRevisionId": "rev2",
  "theirsCommitSha": "…",
  "theirsSourceSha256": "…",
  "startedAt": 1726
}
```

`conflicts.json`：

```json
{
  "files": [
    { "path": "src/pages/Home.tsx", "kind": "text", "status": "unresolved" }
  ]
}
```

目录：`ours/` `theirs/` `base/` 为三棵源码树（不含 `.sto`）。打包排除 `.sto`，因此不会上传。

## 13. 拉取算法（`pullCodeApplication`）

替换现网「diverged 抛错 + applyArchiveToWorkspace」。伪代码：

```
remote = download HEAD snapshot
decision = decideSourcePullAction(base, localSha, remote)

if already-synced  → return action=already-synced
if local-ahead     → 不改盘，return action=local-ahead
if remote-ahead    → applyFileDiff(workspace, remoteArchive, deleteMissing=true)
                     校验 sourceSha256 == remote
                     updateBaseline(remote)
                     cache .sto/base-snapshot（P1，P0 可跳过）
                     return action=applied
if diverged        → beginMerge(workspace, remoteArchive)
```

`applyFileDiff`（仅干净工作区）：

1. 解压到 staging，列出远端相对路径 + hash。
2. 列出当前工作区源码路径（与打包同一套 ignore）。
3. 远端有、本地 hash 不同或缺失 → 从 staging 拷入。
4. 本地有、远端无 → 删除（仍忽略 `.sto` / `.env` / 密钥）。
5. 失败则丢弃 staging，工作区保持拉取前。

**禁止**对 `diverged` 调用现网 `applyArchiveToWorkspace`。

`beginMerge`：

1. 若已有未完成 `.sto/merge/state.json` 且 `theirsRevisionId` 相同 → 不重置，返回现有 conflicts。
2. 否则：拷工作区 → `.sto/merge/ours/`；解压远端 → `theirs/`；取 base 树（本地缓存或 `snapshot?revision_id=base`）→ `base/`。
3. 对每个路径做三路分类，结果写进**工作区**（用户正在编的那份）：自动合的直接写；冲突的写标记或保持 ours 并登记。
4. 写 `state.json` + `conflicts.json`。
5. 有冲突 → 不改 `workspace.json` 基线，return `action=conflicts`。
6. 无冲突 → 基线改成 theirs，`mergeParentRevisionId=旧基线`，删 `.sto/merge`，return `action=merged`。

文本三路：对 utf-8 文本做行级 merge（可用简单实现：base/ours/theirs 三方；冲突块用 `<<<<<<< Local` / `=======` / `>>>>>>> Remote`）。二进制或非 utf-8：不自动合，`kind=binary`。

## 14. 继续合并与解决后提交

### 14.1 merge-continue

`continueCodeApplicationMerge(appPath, revisionId)`：

1. 读 `.sto/merge/state.json`；没有则报「当前没有待处理的合并」。
2. `revisionId` 必须等于 `theirsRevisionId`（工作台现网传的是 `stoStatus.revisionId`，今天等于**本地基线**，这是错的）。status 要返回 `mergeTheirsRevisionId`，按钮改传这个；兼容：若传入的是 theirs 或 state 里的 theirs 则通过。
3. 工作区扫描冲突标记 `<<<<<<< Local`；`conflicts.json` 里 `unresolved` 必须为空。
4. 基线 ← theirs；`mergeParentRevisionId` ← `oursBaseRevisionId`。
5. 删除 `.sto/merge/`。
6. 返回可提交。

单文件 `conflicts/resolve`：从 `ours/` 或 `theirs/` 拷到工作区对应路径，更新 `conflicts.json`。最后一条清掉后不自动 continue（避免用户没看过就改基线）；仍要点「继续合并」或提交前自动检测「冲突已空则先 continue」。

### 14.2 push 前闸门

`pushCodeApplication` 在打包前：

1. 若存在 `.sto/merge` → 拒绝：「请先处理冲突并继续合并」。
2. 工作区含冲突标记 → 拒绝。
3. `throwIfRemoteAhead` 保持。
4. `mergeParentRevisionId` 从 workspace 读取传入 commit metadata（现网写死 `null`）。
5. 成功后清 `mergeParentRevisionId`，更新基线，写本机 push-history（兜底），刷新云端列表。

提交对话框：`merge-required` 禁用确认；`local-changes` 且刚合并过，默认文案「合并远端更新」。

改 `AppDevWorkbench` 与 `AppPlazaDevAppPane`，Git 面板 `cloudPush` 时间线改读修订列表。

| 状态 | 按钮 | 主提示 |
| --- | --- | --- |

## 17. 验收

| # | 步骤 | 期望 |
| --- | --- | --- |
| 1 | 仅 A 提交，B 工作区干净点拉取 | 工作区变成 A 的 HEAD，已同步 |
| 2 | B 先改未提交，远端没变，点拉取 | 不覆盖，提示直接提交 |

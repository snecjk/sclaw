# StoClaw A2UI 架构方案：CLI 数据 → 模型理解 → 渲染页面

> 版本：v1.0
> 定位：技术思路汇报，聚焦数据流转与架构分层

---

## 一、问题定义

我们要解决的核心问题是：**如何让模型把"原始数据"转化为"可交互的渲染页面"？**

这里存在三个断层：

1. **数据获取层**：原始数据散落在 CLI 输出、日志文件、API 响应中，结构不统一
2. **语义理解层**：模型擅长理解意图，但不擅长直接操作具体数据源
3. **界面渲染层**：前端需要结构化描述才能渲染，但模型输出的是自然语言

A2UI 的目标就是在这三层之间建立可靠的转换管道。

---

## 二、整体数据流（核心）

```
第一层：数据获取
─────────────────────────────────────────────────────────────
  用户提问 → Skill Router → CLI 命令执行 / 文件读取 / API 调用 / 流监听
                              ↓
                         原始数据（Raw Data）
                              ↓
第二层：数据规整
─────────────────────────────────────────────────────────────
  数据类型识别 → 预处理策略

  结构化数据    半结构化数据    非结构化数据    时序数据
  JSON/CSV/   →  日志/表格   →  文本/文档   →  指标序列
  SQL结果         键值对         自然语言       事件流
                              ↓
                    统一数据包（Data Packet）
                    { schema, payload, meta }
                              ↓
第三层：模型转化
─────────────────────────────────────────────────────────────
  输入：用户意图 + 规整数据包 + A2UI 规则手册

  模型推理过程：
    步骤1 意图分析    → 概览/对比/趋势/明细/告警
    步骤2 组件选型    → 根据数据特征+意图选择组件
    步骤3 布局决策    → 组件空间关系
    步骤4 数据映射    → 字段→组件属性
    步骤5 交互声明    → 哪些区域可选中/下钻/筛选
                              ↓
                    A2UI 描述（纯声明式）
                              ↓
第四层：前端渲染
─────────────────────────────────────────────────────────────
  A2UI 描述 → 渲染引擎 → 可视界面
                              ↓
                    用户看到：左侧对话 + 右侧画布
                              ↓
                    用户选中画布区域
                              ↓
第五层：上下文回环
─────────────────────────────────────────────────────────────
  选中区域 → 提取上下文 → 拼接为用户问题补充背景
         → 再次进入第一层（新的数据/意图输入）
         
  形成闭环：对话 → 渲染 → 选中 → 再对话 → 再渲染
```

## 三、关键架构分层详解

### 3.1 第一层：数据获取层 — Skill 化设计

核心思路：**把每一种数据来源封装为一个 Skill，对外暴露统一接口。**

当前 StoClaw 的 Skill 体系已经支持 OpenClaw 官方市场和 STO 市场，可以在此基础上增加一类 **"Data Source Skill"（数据源技能）**。

**Skill 的职责边界：**

| Skill 类型 | 职责 | 示例 |
|-----------|------|------|
| CLI Skill | 执行命令、捕获 stdout/stderr、解析输出 | `openclaw stats --json` |
| File Skill | 读取文件、识别格式、提取结构化内容 | 读取 `.jsonl` 日志 |
| API Skill | 调用 HTTP API、处理认证、解析响应 | Gateway REST API |
| Stream Skill | 监听实时流、窗口聚合、格式化输出 | SSE 事件流 |

**为什么用 Skill 封装？**

- 每个 Skill 独立维护，不影响主系统
- Skill 可以组合使用（先执行 CLI 拿到 ID，再用 ID 调 API 拿详情）
- Skill 可以热插拔，用户按需启用

**数据获取的触发时机：**

有两种模式，需要同时支持：

1. **主动模式**：用户明确说"帮我分析上个月的日志"，Agent 调用对应 Skill 获取数据
2. **被动模式**：用户上传文件或粘贴内容，系统自动识别类型并选择预处理 Skill

### 3.2 第二层：数据规整层 — 统一数据包

这是最关键的一层。无论数据从哪里来，最终都要变成**统一数据包**，模型才能可靠处理。

**统一数据包的结构设计原则：**

- **自描述**：数据包自带 schema，模型不用猜测字段含义
- **类型安全**：每个字段标注数据类型，模型知道怎么展示
- **关系完整**：如果有外键/关联关系，显式声明
- **规模可控**：大数据量时自动摘要，避免超出模型上下文

**数据包的三个组成部分：**

1. **Schema（数据模式）**：描述有哪些字段、什么类型、什么关系
2. **Payload（数据载荷）**：实际的数据记录
3. **Meta（元信息）**：数据来源、获取时间、原始规模、是否被截断

**预处理的典型操作：**

| 原始形态 | 问题 | 预处理动作 | 规整后形态 |
|---------|------|-----------|-----------|
| 100 万行 CSV | 超出模型上下文 | 聚合/采样/分页 | 按维度聚合后的 20 行摘要 |
| 嵌套 JSON | 结构太深 | 扁平化/提取关键路径 | 表格形态 |
| 文本日志 | 无结构 | 正则提取/模式识别 | 结构化事件列表 |
| 时间序列 | 点太多 | 降采样/滑动窗口 | 聚合后的趋势点 |
| 多表关联 | 关系隐含 | 自动 JOIN/反规范化 | 宽表形态 |

**预处理的决策谁来做？**

- 简单规则（如超过 1000 行就聚合）：本地 Skill 直接处理，不经过模型
- 复杂策略（如选择哪个维度聚合）：让模型参与决策，但只决策不执行

### 3.3 第三层：模型转化层 — A2UI 规则引擎

这一层的核心问题是：**如何让模型稳定地输出符合规范的界面描述？**

**关键洞察：模型不是直接"画"界面，而是"选"界面。**

我们把界面抽象为一组**有限的设计模式**，模型做的事情是从模式库中做选择，而不是从零设计。

**A2UI 规则手册的结构：**

```
A2UI 规则手册
│
├── 组件库（Components）
│   ├── 数据展示：Table / Card / StatGrid / List
│   ├── 可视化：BarChart / LineChart / PieChart / AreaChart
│   ├── 交互：Form / FilterPanel / Tabs
│   └── 编排：HtmlPage / HtmlFragment
│
├── 布局模式（Layouts）
│   ├── Single：单组件占满
│   ├── Grid：网格排列（2/3/4 列）
│   ├── Split：左右/上下分栏
│   ├── Tabs：标签页切换
│   └── Free：自由组合（用于 HTML 页面）
│
├── 选型规则（Selection Rules）
│   ├── "如果数据有 1 个数值列 + 时间列 → 推荐 LineChart"
│   ├── "如果数据有分类列 + 多个数值列 → 推荐 BarChart 或 StackedBar"
│   ├── "如果数据超过 10 个字段 → 推荐 Table"
│   ├── "如果用户说'看板/概览' → 推荐 Card + StatGrid 组合"
│   └── "如果用户说'页面/编排' → 进入 HtmlPage 模式"
│
└── 交互声明（Interactions）
    ├── Selectable：是否允许选中
    ├── DrillDown：是否支持下钻
    ├── Filterable：是否支持筛选
    └── Editable：是否支持编辑（仅 HTML）
```

**模型输入的构成：**

模型看到的输入不是原始数据，而是经过编排的**结构化提示**：

用户意图 + 数据包(Schema+Payload+Meta) + A2UI 选型规则

模型根据这三者做判断：选什么组件、怎么布局、数据怎么映射。

**模型输出的约束：**

模型输出必须是**声明式描述**，不能包含：
- 具体的 CSS 样式值
- JavaScript 逻辑
- 平台相关的渲染代码

只能包含：
- 组件类型标识
- 数据字段映射关系
- 布局关系声明
- 交互能力声明

### 3.4 第四层：前端渲染层 — 声明式渲染引擎

渲染引擎的职责是**翻译**，不是**创造**。它把模型的声明翻译成具体的前端实现。

**渲染引擎的核心设计：**

- **组件注册表**：维护组件类型 → React 组件的映射
- **数据绑定器**：将 A2UI 描述中的字段名绑定到数据包的实际值
- **布局解析器**：根据 layout 声明计算组件的排列方式
- **交互注入器**：为组件添加选中/点击/悬停等交互能力

**渲染的分支路径：**

```
A2UI 描述
    │
    ├──▶ 组件类型 = Table/Card/Chart/Form/Tabs
    │       └── 使用 React 组件渲染，数据通过 props 注入
    │
    └──▶ 组件类型 = HtmlPage / HtmlFragment
            └── 使用 iframe 沙箱渲染，HTML 内容作为 blob URL 加载
```

**为什么 HTML 页面要走 iframe？**

- 用户生成的 HTML 可能包含任意 CSS/JS，需要隔离
- 避免污染主应用的 DOM 和样式
- 支持用户导出独立可运行的 HTML 文件
- 编辑模式（contenteditable）在 iframe 内更安全

### 3.5 第五层：上下文回环 — 选中即提问

这是 A2UI 区别于传统 Dashboard 的核心特性。

**回环的数据流：**

```
用户在画布上做了一个选择
    │
    ├──▶ 选中表格的 3 行
    │    ├──▶ 提取这 3 行的完整数据
    │    ├──▶ 记录选中的组件 ID 和类型
    │    └──▶ 格式化为自然语言描述
    │
    ├──▶ 选中图表的一段区间
    │    ├──▶ 提取区间内的数据点
    │    ├──▶ 计算起止时间和范围
    │    └──▶ 格式化为自然语言描述
    │
    └──▶ 选中 HTML 页面的一个元素
         ├──▶ 提取元素的 tag 和文本内容
         ├──▶ 记录元素在 DOM 中的路径
         └──▶ 格式化为自然语言描述
    │
    ▼
上下文描述（自然语言）
    │
    ▼
拼接进用户的新问题
    │
"帮我看看华东区的数据"
+ "[上下文] 用户当前查看销售明细表，已选中以下 3 行：..."
    │
    ▼
进入第一层（数据获取）→ 第二层（规整）→ 第三层（模型转化）→ 第四层（渲染）
```

**关键设计决策：**

- 上下文描述必须是**自然语言**，不是机器格式，这样模型更容易理解
- 上下文的粒度要可调：可以只传"选中了3行"，也可以传完整数据，取决于数据量
- 上下文是**附加信息**，不替代用户的原始问题，两者合并后给模型

## 四、与现有 StoClaw 架构的融合

### 4.1 复用点清单

| 现有模块 | 复用方式 | 改动量 |
|---------|---------|--------|
| OpenClaw Gateway | 复用 chat.send RPC，增加 mode 参数 | 小 |
| Skill 体系 | 新增 Data Source Skill 类别 | 中 |
| Agent 管理 | 新增 studio Agent，复用现有创建/管理流程 | 小 |
| 消息协议 | ContentBlock 增加 ui_schema / html_page 类型 | 小 |
| 文件暂存 | 复用 /api/files/stage 系列接口 | 无 |
| IPC 通道 | 复用 hostapi:fetch 和 gateway:rpc | 无 |

### 4.2 新增点清单

| 新增模块 | 层级 | 职责 |
|---------|------|------|
| Data Source Skill | Gateway/Skill | 封装 CLI/API/文件/流的数据获取 |
| Data Packet 规范 | 协议层 | 统一数据结构，连接 Skill 和模型 |
| A2UI 规则手册 | Prompt 层 | 给模型的组件选型指南 |
| Studio 页面 | Renderer | 左右分栏的 A2UI 主界面 |
| 渲染引擎 | Renderer | 将 A2UI 描述翻译为 React 组件 |
| HTML 沙箱引擎 | Renderer | iframe 隔离渲染用户 HTML |
| HTML 持久化服务 | Main | 保存用户编排的 HTML 页面到本地磁盘 |

### 4.3 数据持久化策略

**A2UI 描述本身不需要持久化**——它是模型根据数据和意图实时生成的，每次对话都可以重新生成。

**需要持久化的是：**

1. **用户编排的 HTML 页面**：存储在 `~/.stoclaw/openclaw/studio-html-pages/`，用户可随时打开继续编辑
2. **Studio 会话历史**：复用现有 chat history，消息中包含 A2UI 描述和 HTML 内容
3. **数据源配置**：Skill 的数据源连接信息，存入 Agent 配置

## 五、关键设计决策

### 决策1：模型只输出声明式描述，不输出渲染代码

**原因：**
- 模型输出 HTML/CSS/JS 容易出错，且难以校验
- 声明式描述是"意图"，渲染引擎负责"实现"，分层清晰
- 前端样式升级时，不需要重新训练模型

**例外：**
- 用户明确要求"生成一个独立的 HTML 页面"时，模型输出完整 HTML
- 此时 HTML 走 iframe 沙箱，与主应用隔离

### 决策2：数据规整在本地做，模型只参与决策

**原因：**
- 数据清洗、聚合、格式转换是确定性操作，不需要模型
- 把规整后的干净数据给模型，减少模型负担，提高输出质量
- 大数据量预处理（如 100 万行聚合为 20 行）必须在本地完成，否则会超出模型上下文

**模型参与的场景：**
- 选择聚合维度（按天还是按周？）
- 选择展示字段（这么多字段，用户最可能关心哪些？）
- 异常检测（哪些数据点看起来有问题？）

### 决策3：上下文回环使用自然语言，不使用机器格式

**原因：**
- 模型对自然语言的理解远好于结构化格式
- "用户选中了华东区的3个订单" 比 JSON 形式的选中描述更容易让模型理解
- 不需要额外的"选中描述 → 模型输入"转换层

**取舍：**
- 自然语言描述可能丢失精确性（如具体的数值）
- 解决方案：自然语言描述 + 关键数据摘要同时传入

### 决策4：HTML 页面与 A2UI 组件使用不同的渲染管道

**原因：**
- A2UI 组件是系统预设的，样式可控、交互统一
- HTML 页面是用户自由编排的，可能包含任意内容，必须隔离
- 两者混在一起会增加渲染引擎的复杂度，且安全隐患大

## 六、实现阶段规划

### Phase 1：数据管道（2 周）

目标：建立"CLI/文件/API → 统一数据包"的能力

- 定义 Data Packet 规范
- 实现 CLI Skill（执行命令、捕获输出、解析）
- 实现 File Skill（识别 CSV/JSON/日志格式、提取结构化数据）
- 实现数据规整器（聚合、采样、扁平化）

### Phase 2：A2UI 规则（2 周）

目标：建立"数据包 → A2UI 描述"的模型能力

- 定义 A2UI 描述规范（组件、布局、交互）
- 编写 A2UI 规则手册（Prompt 工程）
- 创建 Studio Agent，配置 System Prompt
- 调优模型输出稳定性

### Phase 3：渲染引擎（2 周）

目标：建立"A2UI 描述 → 可视界面"的能力

- Studio 页面框架（左右分栏）
- 组件注册表 + 渲染引擎
- Table / Card / Chart / Form 组件实现
- 布局解析器（Grid/Split/Tabs）

### Phase 4：HTML 编排（2 周）

目标：支持用户通过对话生成、编辑、保存 HTML 页面

- HTML 沙箱引擎（iframe 渲染）
- HTML 编辑模式（contenteditable）
- HTML 持久化服务（本地存储）
- 导出/下载功能

### Phase 5：上下文回环（1 周）

目标：实现"选中即提问"的闭环交互

- 表格/图表/HTML 元素的选中能力
- 选中上下文提取（自然语言描述）
- 上下文注入 Prompt

**总计约 9 周。**

## 七、风险与应对

| 风险 | 影响 | 应对策略 |
|------|------|---------|
| 模型输出 A2UI 描述不稳定 | 高 | 客户端严格校验 + 降级到纯文本；Prompt 工程持续迭代 |
| 大数据量预处理性能差 | 中 | 本地 Worker 线程处理；超大数据走流式聚合 |
| HTML 沙箱安全漏洞 | 高 | iframe sandbox；禁止内联事件；CSP 策略 |
| CLI 命令执行安全风险 | 高 | 命令白名单；只读操作优先；沙箱环境执行 |
| 用户选中后上下文过长 | 中 | 上下文截断策略；只传摘要而非完整数据 |
| A2UI 组件库不够丰富 | 低 | 先覆盖 80% 场景（Table/Card/Chart）；后续按需扩展 |

## 八、与纯文本 Chat 的关系

A2UI 不是替代 Chat，而是增强：

| 场景 | 推荐模式 | 原因 |
|------|---------|------|
| 通用问答、创意写作 | Chat | 纯文本更自由 |
| 数据分析、报表查看 | Studio (A2UI) | 结构化展示更高效 |
| 代码审查、调试 | Chat + CodeBlock | 现有能力已满足 |
| 页面编排、看板设计 | Studio (HTML) | 需要所见即所得 |

用户在 Chat 中也可以收到 A2UI 卡片，点击后跳转到 Studio 查看详情。

## 九、总结

A2UI 的核心架构可以概括为一句话：

> **Skill 拿数据 → 本地做规整 → 模型选界面 → 引擎做渲染 → 选中再回环**

五个层次各司其职，通过统一数据包和声明式描述协议连接，最终让用户通过自然语言就能生成、交互、迭代数据可视化界面。

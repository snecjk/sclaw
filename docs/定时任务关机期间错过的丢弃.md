# 定时任务关机期间错过的丢弃

## 背景

产品要求：**关机期间到达执行时间的定时任务，在开机时不执行，全部丢弃；只有在开机 app 运行中到达执行时间的任务才会正常运行。**

当前两个引擎都会在开机后补跑关机期间错过的任务，但机制不同、且都无法直接关闭补跑：

- **openclaw（Gateway 引擎）**：Gateway 进程启动时 `CronService.start()` → `runMissedJobs()` → `planStartupCatchup()`，把所有 `nextRunAtMs` 落在过去的 job 收集起来，前 `maxMissedJobsPerRestart`（默认 5）个立即跑、其余按 `missedJobStaggerMs`（默认 5s）错峰补跑。补跑逻辑硬编码在打包进来的 Gateway bundle 里，且 `CronConfig`（`types.cron.d.ts`）没有 `runMissedOnStartup` 之类的开关字段，**无法通过配置关闭**。
- **claude（自研引擎）**：`ClaudeTaskScheduler.tick()`（30s 一次）读到 `nextRunAt <= now` 即视为 due → 执行一次 → 以旧 `nextRunAt` 为 baseline 重算下一个 → 若仍 <= now，下个 tick 再跑一次。即**逐 tick（30s 间隔）串行重放每一个错过的周期，无上限、无错峰**。

补充约束：

1. 运行环境固定在中国大陆时间，时区问题可忽略。
2. cron 表达式格式固定，都来自 `scheduleValueToCron` 的三种形态（`mm hh * * *`、`mm hh * * D,D,…`、`mm hh N * *`）。
3. **如果 app 崩溃/关机时某个任务正在执行，其状态可能停留在 `running`。重启时该次执行直接丢弃，不恢复、不重跑。**

## 核心思路

在调度器/Gateway 真正开始跑之前，做**一次启动期清扫**。

> ⚠️ 字段事实：两引擎都**没有** `status` 字段。
> - claude `scheduler-state.json` 的 `tasks[id]` = `{ nextRunAt?, lastScheduledFor?, lastRecoveredAt? }`（`claude-scheduled-task-store.ts:35-42`）。`status:'running'|...` 只存在于 run 记录文件 `runs/<id>.jsonl`（`:53`），不在 scheduler-state。
> - openclaw `jobs.json` 的 `job.state` = `CronJobState` = `{ nextRunAtMs?, runningAtMs?, lastRunAtMs?, lastRunStatus?, ... }`。「运行中」标记是 `runningAtMs`（时间戳，非枚举）。

对每个 enabled 的 cron 任务，按以下规则处理：

| 引擎 | 条件 | 处理 |
|------|------|------|
| claude | `nextRunAt <= 开机时刻 now` | 关机期间错过 **或** 崩溃时正在跑（两种情况 `nextRunAt` 都落在过去，因为崩溃时 `tick` 里 post-run 的 `nextRunAt` 推进从未落盘）。**不执行**，重算 `nextRunAt` 为未来时刻。 |
| claude | 存在 stale lease（`leaseUntil > now`） | 崩溃任务残留的 lease 会挡住下次 `runTask`（`prepareRun` 抛 `"already running"` → tick 崩）。开机时主进程刚起、无任务真在跑，**清掉所有 stale lease**。 |
| claude | `nextRunAt > now` 且无 stale lease | 保持不变，后续正常 tick 命中执行。 |
| openclaw | `nextRunAtMs <= now` | 关机期间错过。重算 `nextRunAtMs` 为未来时刻。 |
| openclaw | `runningAtMs != null` | 崩溃时正在跑。Gateway 本身已不会补跑（`isRunnableJob` 见 `runningAtMs` 即返回 false），且 `STUCK_RUN_MS` 后自愈。**可选**：顺手清掉 `runningAtMs`，省去自愈等待。 |
| openclaw | `nextRunAtMs > now` 且 `runningAtMs` 未置位 | 保持不变，后续正常 timer 命中执行。 |

> 重算均以 `now`（开机时刻）为 baseline，调用 `computeNextRunAt(cronExpr, now)` 得到下一个未来执行时刻。claude 的崩溃场景**无需**单独检测「running」——`nextRunAt <= now` 已覆盖；真正要补的是清 stale lease。openclaw 的崩溃场景 Gateway 已自愈，清 `runningAtMs` 属可选优化。

这样天然满足产品要求：

- `nextRunAt < 开机时刻`（含崩溃任务）→ 关机期间错过/中断的 → 丢弃；
- `nextRunAt >= 开机时刻` → 运行中到点的 → 正常跑；
- 运行中因 tick 阻塞等原因积压的 due 任务（时刻在开机之后），不会被启动期清扫误伤。

两个引擎共用同一个「下一次时刻」计算器：claude 侧已 `export` 的 `computeNextRunAt`（`electron/services/claude-task-scheduler.ts:103`，自实现 5 字段 cron 解析器）。可行是因为两引擎用的是同一套 5 字段 cron 表达式，`computeNextRunAt` 可完整解析。

## 改动点 1：claude 引擎

文件：`electron/services/claude-task-scheduler.ts`

在 `ClaudeTaskScheduler` 里新增 `discardMissedOnStartup(now = new Date())`，逻辑与 `refreshSchedule` 同构：

1. 读 `listClaudeScheduledTaskDefinitions()`（返回**数组**，需先建 `id→definition` 的 map 或直接遍历数组）+ `readClaudeScheduledTaskSchedulerState()`；
2. 对每个 enabled 任务，若 `nextRunAt <= now`：`nextRunAt = computeNextRunAt(definition.cronExpr, now)`（此条件已覆盖崩溃任务——崩溃时 post-run 的 `nextRunAt` 推进从未落盘，故 `nextRunAt` 仍停在过去的触发时刻）；
3. **清 stale lease**：读 `listClaudeScheduledTaskLeases()`，对每个 `leaseUntil > now` 的 lease 调 `deleteClaudeScheduledTaskLease(taskId)`（开机时无任务真在跑，全清安全；不清的话崩溃任务的下次 `runTask` 会被 `prepareRun` 的 `leaseUntil > now` 判断挡住、抛 `"already running"` → tick 崩）；
4. 有变更才 `writeClaudeScheduledTaskSchedulerState(...)`，并记录变更日志（旧/新 `nextRunAt`、清了哪些 lease）。

> claude scheduler-state **没有** `status` 字段，无需也无法「重置为 scheduled」——动作就是「推进 nextRunAt + 删 stale lease」。

伪代码：

```ts
async discardMissedOnStartup(now = new Date()): Promise<boolean> {
  const definitions = await listClaudeScheduledTaskDefinitions();
  const state = await readClaudeScheduledTaskSchedulerState();
  const defById = new Map(definitions.map((d) => [d.id, d]));
  const nextTasks = { ...(state.tasks ?? {}) };
  let changed = false;

  for (const [id, taskState] of Object.entries(nextTasks)) {
    const def = defById.get(id);
    if (!def?.enabled) continue;
    const nextRunAt = taskState.nextRunAt;
    if (nextRunAt && new Date(nextRunAt).getTime() <= now.getTime()) {
      nextTasks[id] = {
        ...taskState,
        nextRunAt: computeNextRunAt(def.cronExpr, now),
      };
      changed = true;
    }
  }

  // 清 stale lease（崩溃任务残留）
  const leases = await listClaudeScheduledTaskLeases();
  for (const lease of leases) {
    if (new Date(lease.leaseUntil).getTime() > now.getTime()) {
      await deleteClaudeScheduledTaskLease(lease.taskId);
      changed = true;
    }
  }

  if (changed) {
    await writeClaudeScheduledTaskSchedulerState({
      lastTickAt: now.toISOString(),
      tasks: nextTasks,
    });
  }
  return changed;
}
```

> 说明：
> - 必须在 `start()` 之前完成清扫（`start()` 会以 delay 0 排第一个 tick），否则第一个 tick 仍会按旧逻辑补跑。
> - 可选清理：崩溃任务的 `runs/<id>.jsonl` 末条会永远停在 `status:'running'`（finalRecord 没追加上去），UI 可能显示「永久运行中」。要彻底干净可补一条 `cancelled` 终态记录，属 UX 清理、非必需。

文件：`electron/services/claude-scheduled-task-service.ts` 的 `startScheduler()`：

```ts
startScheduler(): void {
  void this.scheduler.discardMissedOnStartup().finally(() => this.scheduler.start());
}
```

> 注意：`finally` 保证即使清扫抛异常，调度器仍会启动。但这也意味着**清扫失败时任务可能仍会执行**。如果业务上要求“清扫失败必须阻断启动”，应改为 `await` 后抛错。

## 改动点 2：openclaw 引擎

新增 helper（建议放 `electron/utils/advance-openclaw-cron-next-runs.ts`）：

1. 读 `getOpenClawConfigDir()/cron/jobs.json`（格式 `{ version, jobs: [{ schedule:{kind,expr}, state:{nextRunAtMs?, runningAtMs?, ...}, enabled }] }`）；
2. 对每个 `enabled && schedule.kind === 'cron'` 的 job：
   - 若 `state.nextRunAtMs <= Date.now()`：`state.nextRunAtMs = Date.parse(computeNextRunAt(schedule.expr, new Date()))`；
   - 若 `state.runningAtMs != null`（崩溃残留）：**可选**置 `state.runningAtMs = undefined`。Gateway 本身已不会补跑崩溃任务（`isRunnableJob` 见 `runningAtMs` 即返回 false），且 `STUCK_RUN_MS` 后会自愈清掉；这里清只是为了立刻愈合、省去自愈等待。
3. 原子写回（复用 `writeJsonAtomic` 模式或直接 `rename`）。

> openclaw `job.state` **没有** `status` 字段，崩溃判断用 `runningAtMs`（时间戳），不是枚举。

伪代码：

```ts
export async function advanceOpenClawCronNextRuns(now = new Date()): Promise<void> {
  const jobsPath = path.join(getOpenClawConfigDir(), 'cron', 'jobs.json');
  const raw = await fs.readFile(jobsPath, 'utf-8');
  const data = JSON.parse(raw);
  let changed = false;

  for (const job of data.jobs) {
    if (!job.enabled || job.schedule?.kind !== 'cron') continue;
    job.state = job.state ?? {};

    const overdue = typeof job.state.nextRunAtMs === 'number' && job.state.nextRunAtMs <= now.getTime();
    const crashed = typeof job.state.runningAtMs === 'number';

    if (overdue) {
      job.state.nextRunAtMs = Date.parse(computeNextRunAt(job.schedule.expr, now));
      changed = true;
    }
    if (crashed) {
      job.state.runningAtMs = undefined; // 可选：立刻愈合，省去 STUCK_RUN_MS 自愈等待
      changed = true;
    }
  }

  if (changed) {
    // 原子写回
    const tmpPath = `${jobsPath}.tmp.${now.getTime()}`;
    await fs.writeFile(tmpPath, JSON.stringify(data, null, 2));
    await fs.rename(tmpPath, jobsPath);
  }
}
```

调用点：`electron/gateway/manager.ts` 的 `runGatewayStartupSequence` 钩子里的 `startProcess` 回调。该回调**仅在 spawn 自有 Gateway 时触发**（连到已存在外部 Gateway 时走 `connect` + `onConnectedToExistingGateway`，不进入此分支），天然满足「连到外部 Gateway 时跳过」的约束；且此时孤儿 Gateway 已被 `terminateOrphanedOwnedGateway` 杀掉、新进程尚未 spawn，时机正确。

```ts
startProcess: async () => {
  // spawn 自有 Gateway 之前丢弃关机期间错过的 cron 任务
  try {
    const { advanceOpenClawCronNextRuns } = await import('../utils/advance-openclaw-cron-next-runs');
    await advanceOpenClawCronNextRuns();
  } catch (err) {
    logger.warn('Failed to advance openclaw cron next runs on startup:', err);
  }
  await this.startProcess();
},
```

> 时机很重要：`startProcess` 回调在孤儿 Gateway 被杀之后、`launchGatewayProcess` 真正 spawn 之前执行，让新进程一启动 `runMissedJobs` 就发现没有任何 `nextRunAtMs` 落在过去 → 不补跑。新 Gateway 的 `armTimer` 会用推进后的未来时刻正常设 timer。retry 循环里可能多次进入此回调，但清扫幂等（推进后无 `nextRunAtMs` 在过去，第二次为 no-op）。

## 为什么这样最省

- **零改动 Gateway 内部**（vendored bundle 改不了也不该改）；
- **零改动 tick/timer 热路径**，运行中行为完全不变；
- **复用现成的 `computeNextRunAt`**，两引擎共用，不引入新依赖；
- 只新增一个 helper + 两处各几行调用；
- 同时覆盖了「错过任务」和「崩溃时正在跑的任务」两种需要丢弃的场景：claude 靠 `nextRunAt <= now`（崩溃任务的 nextRunAt 本就停在过去）+ 清 stale lease；openclaw 靠 `nextRunAtMs <= now` + 可选清 `runningAtMs`（Gateway 本身已不补跑崩溃任务）。

## 边界与待确认

1. **状态字段已确认**：两引擎都**没有** `status` 字段。claude「运行中」= stale lease（`leases.json` 里 `leaseUntil > now`）或 run 记录 `runs/<id>.jsonl` 末条 `status:'running'`；openclaw「运行中」= `state.runningAtMs != null`。清扫用 `nextRunAt(<= now)` / `nextRunAtMs(<= now)` 作为主条件，崩溃场景已被覆盖，无需单独判 running。
2. **外部（非自有）Gateway**：若 StoClaw 连到一个独立常驻的 Gateway（`!ownsProcess`），其 `jobs.json` 被占用、且它早就在自己启动时跑过 `runMissedJobs` 了——无法追溯丢弃。实际场景里 StoClaw 总是先杀 orphan 再 spawn 自有进程，所以罕见；helper 调用已放在 `startProcess` 回调（仅 spawn 自有进程分支），连到外部 Gateway 时不会进入该回调，自然跳过。
3. **claude 侧既有的其他问题**（tick 串行阻塞、tick 失败丢状态/重复执行）**不在本次范围**——本次只满足「丢弃关机期间错过的任务」这一产品要求；那几个问题可另开任务修。
4. **「丢弃」的语义**：任务不会被删除或禁用，只是关机期间错过/崩溃中断的那一次执行被丢弃，任务按新的 `nextRunAt` 继续正常调度。claude 崩溃任务还会顺带清掉残留 lease，避免挡住下次执行。

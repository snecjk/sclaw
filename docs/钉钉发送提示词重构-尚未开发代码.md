### 1.3 钉钉发送场景矩阵

| 场景 | 触发方式 | 收件人来源 | 是否必发 | 涉及引擎 |
|------|---------|-----------|---------|---------|
| **定时任务执行** | 系统调度触发 | 收件人块（情况 1）/ 指令文本内嵌 send 命令（情况 3，无块）+ 描述中点名 | ✅ 必发 | OpenClaw + Claude |
| **对话 @** | 用户在输入框 @ 选人 | JSON 块（运行时选定） | ❌ 看发送意图 | OpenClaw + Claude |
| **口头点名** | 用户话里点名（无 @）+ 发送意图词 | 搜人工具解析（见问题 8 护栏） | ❌ 看意图词+点名，受护栏 | OpenClaw + Claude |
| **分享选人窗** | 用户要求"选人发送" | 钉钉原生选人窗 | ✅ 必发 | OpenClaw only |

**自然语言口头发送规则**：
> 自然语言（无 @）口头发送**有条件允许**：消息文本含明确发送意图词（发给/发送给/分享给/转给/推送给 等）**且**点名了具体收件对象时，允许触发钉钉发送——但收件人 userId/groupId **必须经搜人工具解析**，不得复用 prompt 别处出现的 id；重名歧义时拒发并要求澄清（见问题 8 护栏）。纯提及（如"通知一下张三""看看文鹏的报告"，无发送意图词）不触发发送。

**允许钉钉发送的四种情况**（按 UI 入口/数据通路区分，四者语义不同）：

1. ✅ **定时任务创建收件人字段（`TaskCreateModal.tsx` 488-491 `DingTalkRecipientField`）**
   - 用户在创建定时任务时主动通过 @ 选定联系人 → 收件人 JSON 序列化进 `promptTemplate`
   - 语义：**必发**。定时任务被调度执行后，结果**必须**发送给这些收件人，发送不是可选项（见模块 C / `buildDingTalkMentionSystemContextForScheduledTask` rule 4）
   - 入口性质：该字段的存在目的就是"把执行结果发给谁"，故 @ 即确立发送意图
2. ⚠️ **对话输入框 @ 触发器（`Chat/index.tsx` → `ChatInput`）**
   - 用户在对话里 @ 选定联系人 → 生成收件人 JSON 块，但**仅表示"选定了对象"，不等于要求发送**
   - 语义：**看发送意图**。是否实际发送，仍取决于用户消息文本是否表达发送意图词（如"发给"/"发送给"/"分享给" + @ 收件人）
   - 入口性质：对话中的 @ 可能只是提及/拉人入框，未必是要发送。例：用户 @ 了文鹏又说"**帮我总结对话**"——此时只执行总结，**不**发送给文鹏；只有当消息含"把总结发给 @文鹏"之类发送意图时才发送
   - 对应模块 D `buildDingTalkMentionSystemContext` rule 4-5：@ 提供收件人（必要条件），发送仍需意图词

3. ⚠️ **自然语言创建定时任务（指令文本含 @ + 发送意图，收件人字段为空）**
   - 用户在对话里说"帮我创建一个每天十点执行定时任务，查询上海天气，并把结果发送给 @文鹏" → 任务描述（含 @）进 `TaskCreateModal` 指令框（435-450），此时 488-491 收件人字段为空
   - 语义：**必发**。用户既用了 @ 触发器选定结构化收件人，又表达了明确发送意图（"并把结果发送给 @文鹏"），二者齐备 → 执行后必须发送
   - 与情况 1 同属"定时任务 = 必发"，与情况 2 的"对话 @ 需意图"区别在于：此处 @+意图已同时满足且产物是定时任务（无交互用户），故确立必发
   - **数据通路（与情况 1 不同）**：情况 3 的收件人数据**不走收件人字段、不走收件人 JSON 块**，而走「**指令文本内嵌**」通路——① 对话发送时 `preprocessChatSendParams` 把收件人 JSON 块 prepend 进消息，模型读到的消息顶部含 userId（如 `2562112037743984`）；② 模型调 `create_scheduled_task` 写 `description` 时，把 @姚磊 解析成它看到的 userId 写进 description（beautify 端点 `/api/cron/beautify-instruction` 只收 `{ instruction }`、不收收件人数据，故 userId 是模型写进去的）；③ 美化把带 userId 的描述展开成「步骤 + curl + `dws chat message send --user <id> --group <id>` 命令」；④ 保存时 `buildCronMessage(instruction, recipients=[])` → `prepareDingTalkAgentTurnMessage(空 mentions)` → 原样返回，promptTemplate = 带 `dws send` 命令的指令文本（**无收件人 JSON 块**）；⑤ 执行时模型读 promptTemplate → 照着指令里的 `dws chat message send --user <id>` 命令发 ✅
   - **结论：情况 3 不需要 lift 到 488-491 字段，也不依赖模块 C 的收件人块必发规则**。"必发"由指令文本本身自带的 `dws send` 命令实现。🔴 **硬约束（重构必保）**：模块 C 的**必发语义规则**（现状 [scheduled-task-instruction.ts:24/28/29](sto-claw/shared/scheduled-task-instruction.ts#L24) 三条）必须保持「**块在才必发、块不在沉默**」——它们以"若 message 中含 StoClaw DingTalk Recipients JSON"为前提。注意：第 25/26/27/30/31 行是**通用/格式规则**（"禁止发送前询问"、"工作流结果格式化"、"产物链接格式"、"本地产物上钉盘"），**不**以块为前提、也**不**在无块时禁止发送，属于"只要发钉钉就适用"的规则，应归入 module A（格式 SSOT）随发送注入，不属于"必发"语义。重构**绝不能**加"无收件人块→禁止发送"类规则——否则会砍死情况 3（instruction-driven 发送）。块不在时让模块 C 的必发规则沉默、由指令文本驱动模型发送即可。

4. ⚠️ **自然语言口头发送（无 @ 触发器，意图词 + 点名）**
   - 用户在对话里说"把结果发给文鹏"（无 @ 选人，纯自然语言点名 + 发送意图词）→ 经搜人工具解析 userId
   - 语义：**有条件允许**。意图词 + 点名齐备即允许发送；但收件人 id **必须经搜人工具解析**（不得复用 prompt 别处 id）、重名歧义拒发、搜不到不发、发送前回显（护栏见问题 8）
   - 入口性质：无结构化收件人块，靠护栏保证发给用户所指对象；纯提及（无意图词）仍不触发发送
   - 对应模块 A 子段 `DINGTALK_ORAL_SEND_GUARD`（对话场景随 send-guard 常驻注入）

> 即：@ 触发器场景中，**定时任务创建（情况 1、3）= 必发**，**对话（情况 2）= 需意图**；**无 @ 的口头路径（情况 4）= 意图词+点名即可，受问题 8 护栏**。

**禁止发送的情况**：

- ❌ 模型从 prompt 别处文本/历史消息/其他收件人块/示例代码里复用 id 拟发送——id 来源不合法（见问题 8 护栏 2）

## 二、核心问题诊断

### 问题 1：`SCHEDULED_TASK_EXECUTION_SYSTEM_PROMPT` 职责混乱
- **现状**：22 行中混入了定时任务语义（~5行）+ 钉钉发送规则（~17行）
- **后果**：在定时任务 session 中，即使没有钉钉收件人，钉钉发送规则也会被注入
- **耦合点**：规则 5-10 与 `buildSendFormatRules()` 高度重复但写法不同

### 问题 2：`buildDingTalkMentionSystemContextForScheduledTask` 重复定时任务语义
- **现状**：规则 4 中重复了"定时任务必发"语义，与 `SCHEDULED_TASK_EXECUTION_SYSTEM_PROMPT` 重叠
- **后果**：同一 session 中两份提示词都注入"必发"语义，冗余且可能冲突

### 问题 3：钉钉发送格式规则分散在多处
- `SCHEDULED_TASK_EXECUTION_SYSTEM_PROMPT` 中有 P0 产物链接/钉盘规则
- `buildSendFormatRules()` 中有规则 6-11
- 两者对 `--title`、代发说明、URL 编码的要求表述不一致

### 问题 4：`isScheduledTaskSessionKey` 逻辑重复
- `shared/scheduled-task-instruction.ts` 有一份
- `sto-plugin/openclaw/sto-dingtalk-send-guard/dingtalk-send-guard.ts` 又有一份

### 问题 6：自然语言提及收件人的发送边界
- **口径**：自然语言（无 @）口头发送**有条件允许**——消息文本含明确发送意图词（发给/发送给/分享给/转给/推送给）**且**点名了具体收件对象时，允许触发搜人 + 发送。纯提及（无意图词）不触发。
- **关键护栏**：口头发送路径的收件人 id **必须经搜人工具解析**，禁止从 prompt 别处复用 id；重名歧义拒发并澄清。护栏细节与偶发乱发根因见**问题 8**。
- **允许发送的情况**：见 1.3「允许钉钉发送的四种情况」——含 ① 对话 @ 发送 / ② 定时任务收件人字段 / ③ 自然语言创建定时任务 / ④ 自然语言口头发送（意图词+点名，受问题 8 护栏）。
- **改动**：废弃旧 `DINGTALK_ORAL_SEND_PROMPT` + `looksLikeDingTalkOralSendIntent`（语义过宽、无 id 来源护栏），不复活；改为将「口头发送护栏」并入统一模块 A `DINGTALK_SEND_FORMAT_RULES` 子段 `DINGTALK_ORAL_SEND_GUARD`（见 3.3），随 send-guard 常驻注入，避免旧常量双写。

### 问题 7：工作流 JSON 结果直接贴入钉钉消息
- **现状**：模型拿到工作流返回的结构化 JSON（含 `kind`、`status`、`data`、`summary`、`artifacts` 等字段）后，直接把整段 JSON 贴入钉钉正文
- **后果**：收件人收到的是机器可读的 JSON 而非人类可读的总结 + 产物链接
- **根因**：
  1. 提示词中"工作流结果先精炼为一句话总结，再发送（禁止直接贴原始 JSON）"混在 22 行中，权重不够
  2. 没有明确告诉模型 JSON 结构中 `summary`（字符串，非 `summary.text`）是总结、`artifacts` 是产物链接
  3. 模型可能把工作流返回的 JSON 当作"业务结果"直接转发，而非需要解析的中间结构
- **改动**：在 `SCHEDULED_TASK_DINGTALK_RULES` 中强化工作流结果解析指令，明确 JSON 字段映射关系（模块 C 代码块中相关字段已对照真实 `get_workflow_status` schema，见模块 C 头注释，实施时无需再替换）
- **字段映射**：`summary` 是**字符串**（非对象，`summary.text` 取值不成立——现有 watchdog 兜底逻辑 `claude-task-workflow-watchdog.ts formatRunSection` 中 `result.summary?.trim()` 即按字符串使用，类型定义见 `workflow-run-client.ts` `WorkflowRunStatusResult.summary?: string`）。原始工具 JSON（`WorkflowRunResponse`）中 `summary` 嵌套在 `result` 下、`artifacts` 在顶层；而 watchdog 的 `WorkflowRunStatusResult` 已把两者提到顶层——两条路径字段路径不同，须在 prompt 中按"模型实际拿到的是哪一种"分别写明（模块 C 已分别标注）。写错字段名会让模型找不到值，反而更容易回退为贴原始 JSON
- **实施策略**：优先让定时任务执行路径把工作流结果交给 watchdog 兜底发送（已正确做 summary + artifacts 提取，见 `formatRunSection`），模型自发 `dws chat message send` 拼正文仅作为兜底。模块 C 的规则已写明"优先依赖 watchdog 兜底格式化"。靠 prompt 约束模型解析 JSON 的可靠性低于走既有的格式化路径

### 问题 8：偶发乱发钉钉——收件人 id 来源不合法 / 重名歧义
- **现状**：自然语言口头发送（问题 6）下，偶发出现"模型把消息发给了非用户所指的对象"——即乱发。
- **根因**：
  1. **id 重合复用**：模型在决定收件人时，未走搜人工具，而是从 prompt 别处文本（示例代码、其他收件人 JSON 块、历史消息、工具返回的示例 userId）里"看到"了一个看似合理的 id 就直接塞进 `--user`，导致发给 prompt 里出现的某个人而非用户实际点名的对象。
  2. **重名歧义**：搜人工具返回多个匹配（同名/同名缩写），模型未澄清就任选其一发送。
  3. 旧 `DINGTALK_ORAL_SEND_PROMPT` 未约束 id 来源，模型可自由联想，是乱发温床（故不复活旧常量、并入统一模块并加护栏）。
- **护栏**（并入模块 A 子段 `DINGTALK_ORAL_SEND_GUARD`，见 3.3）：
  1. **触发门槛**：仅当消息文本含明确发送意图词（发给/发送给/分享给/转给/推送给）**且**点名具体对象时，才进入口头发送流程；纯提及不进入。
  2. **id 必经搜人工具**：收件人 userId/groupId **必须**由 `dws` 搜人/查群工具在本轮解析得到；**禁止**使用 prompt 别处文本、历史消息、其他收件人块、示例代码里出现过的 id。搜不到则不发送并在对话中说明。
  3. **重名拒发**：搜人返回多个匹配时，**不得**任选其一发送，必须停下向用户澄清（如"找到多个'文鹏'，请指明部门/工号"），得到确认后才解析发送。
  4. **发送前回显**：调用 send 前，在对话里用一句话回显解析结果（姓名 + 来源"已搜人确认"），使乱发可见可追溯（非阻塞确认，符合"意图词+点名即可"的口径，不增加用户交互负担）。
- **改动**：护栏规则写入模块 A 子段 `DINGTALK_ORAL_SEND_GUARD`，随 send-guard 在对话场景常驻注入（口头路径无 @ 触发器，需常驻才能被模型用作判断依据）；定时任务路径不注入此子段（定时任务收件人来自块/指令，不走搜人）。

### 问题 5：第三盘上传流程描述分散
- `SCHEDULED_TASK_EXECUTION_SYSTEM_PROMPT` 中有详细流程
- `dingtalk-send-guard.ts` 中 `resolveDwsChatMessageSendFileProtocolInText` 有另一份描述
- 两者对 `dws drive upload` 的参数说明不完全一致

## 三、目标架构设计

### 3.1 设计原则

1. **单一事实来源**：每类规则只在一处定义，各处引用
2. **场景解耦**：定时任务语义 ≠ 钉钉发送规则，各自独立
3. **按需注入**：只在有钉钉发送时（收件人块存在，或指令文本含 `dws chat message send`）才注入钉钉规则；纯业务定时任务（无发送）不注入
4. **双引擎一致**：OpenClaw 和 Claude 使用同一套提示词源

### 3.2 目标文件结构

```
shared/dingtalk-prompts/
├── index.ts                          # 统一导出入口
├── dingtalk-send-rules.ts            # 钉钉发送格式规则（单一事实来源）
├── dingtalk-share-tool.ts            # share_to_dingtalk 工具说明
├── dingtalk-mention-context.ts       # @ 场景系统上下文（构建器）
├── dingtalk-disclaimer.ts            # 代发说明底栏（保持现状）
└── scheduled-task/
    ├── scheduled-task-core.ts        # 定时任务核心语义（不含钉钉）
    └── scheduled-task-dingtalk.ts    # 定时任务专属钉钉规则（P0 产物/钉盘）

注：
- 口头点名发送护栏（`DINGTALK_ORAL_SEND_GUARD`）作为模块 A `dingtalk-send-rules.ts` 的子段纳入统一模块，对话场景随 send-guard 常驻注入。旧文件 `shared/dingtalk-oral-send-prompt.ts` 标记 `@deprecated`，其职责由子段承接，不复活旧 `DINGTALK_ORAL_SEND_PROMPT` 常量。
- `CLAUDE_SCHEDULED_TASK_SYSTEM_PROMPT`（定时任务管理工具说明，Claude 引擎专用）保留在 `sto-plugin/claude/claude-scheduled-task-tool/tools.ts`，不纳入 shared 模块——该提示词描述的是 Claude 引擎专属的 `create_claude_scheduled_task` 等工具，与 OpenClaw 引擎无关，不属于"双引擎共享"范畴。
```

## 七、产物 URL 双重编码问题分析与修复

### 7.1 问题描述

工作流产物的 OSS 签名 URL（如 `https://sai-agent.oss-cn-shanghai.aliyuncs.com/agentRun/2363305263/outputs/tang_poem.json?Expires=1786712839&OSSAccessKeyId=LTAI5tKZku9MaQ4WCtzyMPbh&Signature=45RLBC1JyRNxU2i06XhBpCQu11E%253D`）在钉钉消息中出现**双重 percent-encoding**：`%3D`（`=` 的编码）被进一步编码成 `%253D`（`%` → `%25`），导致 OSS 签名校验失败、链接不可访问。

### 7.2 现有防护机制

项目中已有完善的 URL 规范化基础设施：

| 函数 | 文件 | 作用 |
|------|------|------|
| `normalizeArtifactUrl(url)` | `shared/dws-send-text.ts` | 迭代 `decodeURI` 剥尽冗余编码层 → `encodeURI` 一次，收敛到单次编码稳定态 |
| `normalizeUrlsInText(text)` | `shared/dws-send-text.ts` | 用正则提取正文中所有 `http(s)://` URL，逐个调用 `normalizeArtifactUrl` |
| `normalizeDwsChatMessageSendText(text)` | `shared/dws-send-text.ts` | 解析 `dws chat message send --text` 命令 → `normalizeUrlsInText` → 追加代发说明 |
| `encodeArtifactUrl(url)` | `claude-task-workflow-watchdog.ts` | watchdog 路径中直接调用 `normalizeArtifactUrl` |

**设计原理**：无论输入是「原始中文 / 已编码 / 双重（多重）编码」，都收敛到单次编码稳定态，且幂等、重复调用安全。

### 7.3 规范化覆盖路径

URL 规范化在以下路径保持生效：

| 路径 | 规范化点 | 状态 |
|------|---------|------|
| **OpenClaw 引擎**：模型生成 `dws chat message send --text "..."` | `before_tool_call` → `fixDwsChatMessageSendToolParamsForOpenClawExec` → `fixDwsChatMessageSendToolParams` → `normalizeDwsChatMessageSendText` → `normalizeUrlsInText` | ✅ 已覆盖 |
| **Claude 引擎**：模型生成 `dws chat message send --text "..."` | `before_tool_call` → `fixDwsChatMessageSendToolParams` → `normalizeDwsChatMessageSendText` → `normalizeUrlsInText` | ✅ 已覆盖 |
| **Claude 引擎**：watchdog 兜底发送工作流结果 | `formatRunSection` → `encodeArtifactUrl` → `normalizeArtifactUrl` | ✅ 已覆盖 |
| **Claude 引擎**：watchdog 直接 `runDws` 发送 | `runDws` 调用时 `--text` 参数经 `normalizeDwsChatMessageSendText(body)` | ✅ 已覆盖 |

### 7.4 潜在风险点

1. **模型不遵守提示词指令**：提示词中写了「禁止对 URL 做 encodeURI/encodeURIComponent」，但模型可能仍然编码。send-guard 的 `normalizeUrlsInText` 会修正，但若模型编码后的 URL 被正则漏掉（如 URL 被包裹在特殊字符中），就可能逃逸。

2. **正则覆盖不足**：`DWS_TEXT_URL_RE = /https?:\/\/[^\s"'<>`)\]]+/gi` 可能在某些边界情况下漏掉 URL（如 URL 末尾紧跟 `)` 或 `]` 时会被截断）。

3. **OSS 签名 URL 的特殊性**：OSS 签名 URL 的 `Signature` 参数值本身可能含 `%` 字符（如 `%3D` 是 `=` 的编码）。若上游某层错误地对整个 URL 做了 `encodeURIComponent`，`%` 变成 `%25`，签名就失效。`normalizeArtifactUrl` 能正确处理，但前提是 URL 必须被正则捕获。

4. **`dws-send-text.ts` 双份拷贝**：`shared/dws-send-text.ts` 和 `sto-plugin/openclaw/sto-dingtalk-send-guard/shared/dws-send-text.ts` 各有一份完全相同的代码。若只修改一处而忘记同步另一处，会导致 OpenClaw 引擎的规范化失效。

### 7.5 修复方案

**方案 A：消除 `dws-send-text.ts` 双份拷贝**

`sto-plugin/openclaw/sto-dingtalk-send-guard/shared/dws-send-text.ts` 是 `shared/dws-send-text.ts` 的完整拷贝（500+ 行），维护两份相同代码极易导致不同步。解决：

1. 在 `sto-plugin/openclaw/sto-dingtalk-send-guard/shared/dws-send-text.ts` 中，将所有导出改为 re-export：
   ```typescript
   export {
     normalizeArtifactUrl,
     normalizeUrlsInText,
     normalizeDwsChatMessageSendText,
     fixDwsChatMessageSendToolParams,
     fixDwsChatMessageSendToolParamsForOpenClawExec,

   ```
2. 或者在构建时将 `shared/dws-send-text.ts` 打包进插件目录（类似其他 shared 模块的处理方式）。

**方案 B：增强 URL 正则覆盖**

更新 `DWS_TEXT_URL_RE` 以更宽松地捕获 URL、排除末尾标点：
```typescript
// 当前正则
const DWS_TEXT_URL_RE = /https?:\/\/[^\s"'<>`)\]]+/gi;

// 增强版：更宽松地捕获 URL，但排除末尾的标点符号
const DWS_TEXT_URL_RE = /https?:\/\/[^\s"'<>`]+(?<![.,;:!?])/gi;
```

**方案 C：在 watchdog 路径增加 URL 规范化日志**

在 `encodeArtifactUrl` 中增加 debug 日志，便于排查双重编码出问题的层级：
```typescript
function encodeArtifactUrl(url: string): string {
  const normalized = normalizeArtifactUrl(url);
  if (normalized !== url) {
    logger.debug?.(`[watchdog] URL normalized: ${url.substring(0, 80)}... → ${normalized.substring(0, 80)}...`);
  }
  return normalized;
}
```

**方案 D：提示词中强化 URL 处理指令**

`shared/scheduled-task-instruction.ts` 第 30 行指令强化为：
> **产物 URL 处理：直接使用后端返回的 URL 原始值，禁止调用 `encodeURI` / `encodeURIComponent` / `decodeURI` / 任何 URL 编码函数。无论 URL 看起来是「原始中文」还是「已编码（含 %XX）」还是「双重编码（含 %25XX）」，都原样贴入正文。send-guard 规范化层会自动处理所有编码问题，模型层不要自行 encode/decode。**

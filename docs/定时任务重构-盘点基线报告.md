- ✓ 核对 doc P2（openclaw 侧）：
  - `schedule.expr` → `cron_expr` —— 成立
  - `payload.message` → `prompt` —— 成立

- 备注：`jobs.json.bak`(954B) 与 `sto_jobs.json.bak`(661B) 各含同一 plain job `69b6ff00…`（无 description），与 job[0] 一致；`.bak` 仅作结构参考，迁移以 `jobs.json` 为准。

## 5. 风险与发现汇总（供后续 Step 参考）

1. **openclaw `description` 为可选 JSON**（§1.2）：job[1] 实证含 `dingTalkMentions`+`workflowCode`；job[0] plain 无。doc P2 的 `description`→dingTalkMentions/workflowCode **成立**；但 `agentId` 不在 description，须从 sessionKey `agent:{agentId}:cron:{jobId}` 派生。Step 4 迁移按 `description` 存在性分支取收件人/workflowCode，agentId 从 sessionKey 取。
2. **孤儿会话**（§3.2/§3.3）：3 个已删 openclaw job（14 条 cron 会话）+ 3 个已删 claude task（19 条 claude_task 会话）仍留 catalog（含非删 + 软删）—— Step 5 按 `task_id` 列做 session_type 迁移时须覆盖孤儿，不能只迁当前 active 任务。
3. **dated 会话模式**（§3.4）：claude 的 `claude-task:{taskId}:{date}` 须在 Step 7 保留。
4. **run jsonl 字段差异**：openclaw run 记录含 `model/provider/usage`；claude run 记录含 `triggerSource/runtimeSnapshot` —— 两引擎 run 历史结构不同，Step 7 行为对照需分别取基线。
5. **原子写残留**（§2.2）：`scheduler-state.json.tmp` 存在 —— 迁移/读状态时过滤 `.tmp`。
6. **jobs.json 2 active job**：迁移以 `jobs.json` 为准（job[0] plain + job[1] recipient/workflow），`.bak` 仅结构参考；另 3 个已删 job 的 14 条孤儿会话须在 Step 5 覆盖。
7. **dated 会话双引擎都有**（行为基线 §D）：openclaw `agent:main:cron:{jobId}:{date}` + claude `claude-task:{taskId}:{date}`，均 `engine_session_id=NULL`。Step 5 须按 session_key 后缀（`:run:` vs `:date`）分支处理，不能只看 session_type。
8. **model 落点两引擎不同 + claude schema 演进**（行为基线 §E）：openclaw 的 model 在 `payload.model`；claude 新任务 `222ba369` 把 `model`+`providerAccountId` 放顶层（旧 6 任务无）。Step 4 须分别取：openclaw `payload.model`、claude 顶层 `model`/`providerAccountId`（可选）。
